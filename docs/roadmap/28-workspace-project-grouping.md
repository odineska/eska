## Требуемое поведение

В дереве ESKA Explorer подпроекты одного workspace группируются по типу.
Порог проверяется отдельно для каждого типа, независимо от общего числа
подпроектов в workspace.

При использовании [фильтра отключённых проектов T151](29-workspace-project-activation.md)
порог применяется к видимым подпроектам после фильтра. Скрытые узлы
не учитываются при создании групп.

| Тип подпроекта | Группа ru-RU | Группа en-US |
| --- | --- | --- |
| `extension` | Расширения | Extensions |
| `report` | Отчеты | Reports |
| `processing` | Обработки | Data processors |

- При двух и более подпроектах одного типа создаётся соответствующая группа;
  все подпроекты этого типа размещаются внутри неё.
- Единственный подпроект своего типа остаётся непосредственно в workspace,
  без промежуточной группы. Пустые группы не отображаются.
- Например, два расширения, один отчёт и одна обработка дают группу
  «Расширения» и два отдельных узла отчёта и обработки.
- Проекты типа `configuration` остаются на прежнем уровне дерева.

## Границы

Группы виртуальные: не меняют `eska.toml`, файлы, состав или идентификаторы
подпроектов. Explorer использует типы, полученные от ESKA; имя и расположение
каталога не определяют тип. Группировка относится к подпроектам одного
workspace, без объединения разных workspace в общие группы.

При изменении состава workspace переход 1 → 2 создаёт группу, а 2 → 1
убирает её и поднимает оставшийся подпроект на прежний уровень.
Навигация учитывает новый родительский узел: поиск объекта, переход от файла
к дереву и раскрытие пути сохраняют работу. Обновление дерева сохраняет выбор
и состояние раскрытия существующих узлов.

## Приёмка

1. По одному расширению, отчёту и обработке: все три узла без групп.
2. Поочерёдно добавить второй подпроект каждого типа: группа появляется только
   у соответствующего типа; остальные одиночные подпроекты остаются без групп.
3. По два подпроекта каждого типа: три группы с правильным составом;
   основная конфигурация отображается на прежнем уровне.
4. Добавление и удаление подпроектов проверяют оба перехода 1 ↔ 2;
   пустые группы и дубли узлов отсутствуют.
5. Поиск, переход от файла и обновление дерева проверены для сгруппированных
   и одиночных подпроектов; выбор и раскрытие сохранены.
6. Подписи групп проверены в `ru-RU` и `en-US` в VS Code/VSCodium.
7. С фильтром T151 два расширения, одно из которых отключено и скрыто,
   отображаются как один видимый узел без группы; показ отключённого
   возвращает группу с двумя узлами.

## Реализация и результаты

`bbcca4b` в Explorer добавляет виртуальную модель `ProjectGroups`, переводы,
родителей и сохранение metadata-выбора при изменении manifest. Ключ группы
включает workspace и тип, а идентификаторы проектов остаются прежними.
Публикация корней учитывает также дерево, в котором все проекты сгруппированы.
Состояние раскрытия хранится по устойчивым ключам.

`8c4064d` исправляет обнаруженный при приёмке цикл проверки защиты каталогов:
native file decorations заново запрашивали каталог после каждого отсутствующего
file-policy ответа и непрерывно обновляли корень. Классификация каталога теперь
действует до инвалидации; появившийся на его месте файл проверяется заново.

Полный набор Explorer — **422 passed, 10 skipped**, TypeScript и сборка успешны.
В VS Code 1.144.0 на Linux ARM64 отдельно в `ru` и `en` проверены независимые
пороги всех трёх типов, переходы 1↔2, состав и подписи групп, конфигурация вне
групп, поиск, переход от файла, refresh, выбор и раскрытие. Проверка выбора
подтверждает новый экземпляр модели после reconnect. Дополнительно проверен
cold reveal, когда все корни workspace находятся в единственной группе.
Записанные backend PID завершены; пользовательские demo не затронуты.

Интеграция с фильтром скрытия отключённых проверяется в T151. Native-проверка
Windows, macOS и VSCodium пока не выполнялась.
