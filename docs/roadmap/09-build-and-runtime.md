# Build и development runtime

## T28 — Build subsystem через `ibcmd`

**Статус:** `DONE`
**Зависит от:** T03, T19

Первый пользовательский результат — кроссплатформенная сборка Designer XML
проекта типа `configuration` в `.cf`:

```text
eska build
eska build --output <path>
```

За основу берётся проверенный pipeline из пользовательского `Taskfile.yml`:

```text
выбрать совместимый ibcmd
-> открыть или создать управляемую файловую базу проекта
-> infobase config import Designer XML --out <artifact>
-> сохранить базу и очистить staging-файлы текущего запуска
```

Это compatibility path для используемой сейчас платформы `8.3.27.2325`. Перед
фиксацией backend нужно проверить встроенную справку каждой поддерживаемой версии:
Установленный `8.3.27.2325` без созданной базы возвращает ошибку отсутствующего
`1Cv8.1CD`, поэтому для него временная база обязательна. Версии 8.5.1/8.5.4 в
текущем окружении отсутствуют: их возможный прямой режим намеренно не заявлен и
должен добавляться только после проверки встроенной справки конкретной версии.

Реализация не переносит Bash/Taskfile в продукт. Процессы запускаются через Rust
`Command`, пути передаются отдельными аргументами, а прерывание и cleanup работают
на Windows и Linux. Прямой запуск `ibcmd` — основной portable backend; Distrobox
остаётся опциональным Linux adapter, а не обязательной частью build core.

Контракт настройки должен разделять переносимые project settings и параметры
конкретной машины:

- требуемая версия платформы и каталог artifacts задаются в project config;
- путь к `ibcmd`, архитектура и Distrobox container переопределяются CLI/env или
  local machine config и не требуют hardcoded абсолютных путей в репозитории;
- поиск проверяет явный путь, `PATH` и стандартные пути установки, затем сверяет
  фактический `ibcmd --version`;
- output path по умолчанию выводится из имени проекта, но переопределяется явно;
- human output локализован, JSON result содержит artifact type/path, platform
  version и duration без credentials и host-specific secrets.

Сначала реализуется корректная полная сборка `.cf`. Поддержка нативных artifacts
остальных уже распознаваемых project types (`.cfe`, `.epf`, `.erf`) добавляется
последующими узкими шагами того же subsystem после проверки доступных команд на
минимальной поддерживаемой версии платформы. Generated `build/` не является
source of truth и игнорируется VCS; существующий artifact заменяется только после
успешной сборки.

T28 реализуется тремя законченными частями:

1. build settings, безопасный поиск/version check `ibcmd` и план artifact без
   запуска сборки;
2. `eska build` для `configuration` с реальным `.cf`, cleanup, RU/EN human output
   и стабильным JSON result; acceptance-сценарий повторяет результат текущего
   Taskfile на `8.3.27.2325`;
3. проверка и добавление нативных artifacts для `extension`, `processing` и
   `report` без изменения контракта полной сборки `.cf`.

Все три части завершены. Реальная приёмка на `8.3.27.2325` подтвердила `.cf`
для Designer XML размером 373 МиБ, `.cfe` для существующего расширения и
минимальные `.epf`/`.erf`. Для всех типов команда передаёт в `ibcmd` каталог
XML-выгрузки Конфигуратора. Служебная база хранится под настроенным каталогом
артефактов и повторно используется; `--recreate-infobase` принудительно создаёт
её заново. Смена версии платформы пересоздаёт несовместимый экземпляр. Для
`processing`/`report`, зависящих от объектов
основной конфигурации, `--base-configuration <file.cf>` предварительно загружает
этот `.cf`; изменение его байтов также пересоздаёт служебную базу.
`eska clean` удаляет только управляемые базы выбранных проектов и сохраняет
опубликованные артефакты; в workspace применяются `-p` и `--workspace`.

Machine-local часть контракта также реализована: `eska config init/edit`
управляют глобальным TOML вне репозитория с проверкой и резервной копией;
`runner = "auto" | "host" | "distrobox"` выбирает окружение. `eska platform
list` сканирует стандартные установки эффективного раннера. Явный
`--platform-version` и интерактивный `--select-platform` меняют версию только для
текущей сборки и не могут случайно изменить переносимую версию проекта.
Скрытый default версии удалён: `new/init` всегда создают
`[build].platform_version = ""`. Пустое или отсутствующее в старом config поле
считается незаполненным и блокирует только команды, которым нужна платформа;
одноразовый выбор версии остаётся допустимым.

## T42 — Patch-extension `.cfe` из разницы веток

**Статус:** `DONE` — спецификация и feasibility-прототип; production CLI не реализован.
**Зависит от:** T20, T21, T28

Это отдельный artifact, а не режим обычной полной сборки. Для configuration
project команда должна брать base из `workflow.integration_target`, сравнивать
его merge-base с `HEAD` и позволять явный `--base <revision>`. Git branch не
хранит ссылку на «родительскую ветку», поэтому угадывать её по имени нельзя.

До утверждения CLI нужен feasibility prototype на минимальной поддерживаемой
версии `ibcmd`: создать extension с purpose `patch`, корректно заимствовать
изменённые объекты из base configuration, применить их версии из `HEAD` и
сохранить `.cfe`. Добавления, удаления, переименования, изменения корневых свойств
и несовместимые изменения структуры должны иметь явный support matrix и
отклоняться до записи artifact, если безопасная семантика не доказана.

`.cfe` — файл расширения конфигурации. Официальный файл обновления основной
конфигурации имеет формат `.cfu`; его генерация не входит в T42 и при
необходимости проектируется отдельной задачей.

Результат T42: [спецификация, support matrix и протокол](t42-patch-extension.md),
[воспроизводимый прототип](../../examples/t42_patch_extension.py). На
8.3.27.2325 проверены Git delta одного метода, заимствование по UUID, сборка,
установка в новую базу, обратная выгрузка и выполнение `1 -> 2 -> 1 -> 2` при
переключении активности патча с отключённым safe mode. При default safe mode
этот патч не применяется в клиенте. `ibcmd config check` не заменяет проверку
BSL и runtime; прототип дополнительно использует пакетный `1cv8`.
На момент завершения T42 оставалось согласовать allowlist изменений, проверяющий
инструмент и acceptance-контракт. Публичный CLI в T42 не утверждался; эти решения
приняты в T43 ниже.

## T43 — `eska patch`

**Статус:** `DONE`
**Зависит от:** T42

Отдельная команда реализует согласованный узкий allowlist: committed-изменения
тел существующих методов серверных общих модулей без вызовов, обращений к членам,
директив и переменных модуля. План строится от единственного merge-base с
локальным `workflow.integration_target` или явным `--base`; unsupported delta и
dirty worktree блокируются до запуска платформы.

На 8.3.27.2325 команда создаёт изолированную базу, импортирует точный базовый
снимок, формирует patch-extension, проверяет metadata, BSL и применимость через
`ibcmd` и пакетный `1cv8`, затем публикует новый `.cfe` без перезаписи. Runtime
не запускается, safe mode не меняется; эти ограничения входят в human и JSON
результат. Полный контракт и приёмка описаны в
[T42/T43](t42-patch-extension.md).

## T29 — `eska doctor`

**Статус:** `DONE`
**Зависит от:** T03, T07, T28, T44

Собрать диагностику уже работающих сценариев за один read-only запуск:

- config/source: discovery standalone/workspace, members, наличие и корректность
  корневого Designer XML descriptor; отличать пустой scaffold после `new` от
  исходников для сборки, не обещая полной проверки XML/BSL без платформы;
- 1С: требуемая и найденная версия, выбранный host/Distrobox runner, `ibcmd`;
  наличие совместимого `1cv8` показывать как требование именно `patch`;
- VCS: repository/workflow, author identity для `save`, незавершённые операции,
  наличие Git для команд с capability fallback; Git LFS проверять, когда
  реальные attributes требуют его;
- remote: показывать настройку без fetch/push и обязательного сетевого запроса;
  отсутствие remote допустимо для локального workflow.

Независимые проверки продолжаются после ошибки, зависимые явно пропускаются с
причиной. Каждый результат указывает затронутую команду, статус и конкретный
способ исправления. Отсутствие build tools не означает недоступность локальных
VCS-команд. Поддержать RU/EN и versioned JSON со стабильными check IDs, статусами,
кодами и документированными exit codes; selectors следуют существующим правилам
выбора workspace members.

Locking и development environments не реализуются ради `doctor` и не считаются
неисправностью до T39/T30. Установка программ, изменение config, создание базы,
`fix` и `setup` не входят в T29. Проверки используют текущие discovery/tool/VCS
модули, а не параллельный механизм поиска и настройки.

**Готово, когда:** один запуск собирает доступные результаты и объясняет пропуски;
проверены scaffold, неверный config/descriptor, несколько members, отсутствующие
или несовместимые tools, optional remote/LFS и RU/EN JSON. Исходники, config,
index/refs, artifacts и базы остаются неизменными. Успешный `doctor` не объявляется
доказательством успешной сборки или корректного выполнения приложения 1С.

Принятые решения:

- результат представлен упорядоченными независимыми checks со статусами
  `pass`, `warning`, `fail`, `skipped`; exit code 1 определяется только наличием
  `fail`, поэтому предупреждение пустого scaffold само по себе не блокирует CLI;
- JSON schema 1 не зависит от локали и содержит стабильные check ID/code,
  affected commands, expected/actual values, runner, remediation и summary;
- Designer XML проверяется ограниченным чтением корневого descriptor без полной
  проверки XML/BSL; build и patch получают отдельные prerequisites;
- repository, workflow, operation и remote читаются локально через VCS layer без
  сетевых операций; системный Git проверяется через единый capability boundary,
  а Git LFS — только при фактическом `filter=lfs` в attributes;
- workspace использует существующий selection contract. Интеграционные сценарии
  покрывают RU/EN, scaffold, повреждённые config/descriptor, members,
  отсутствующие/несовместимые tools, optional remote/LFS и побайтовую
  неизменность исходников, config, index и refs.

## T31 — `eska apply` / `eska run`

**Статус:** `PLANNED`  
**Зависит от:** T19, T20, T28, T30

`apply` определяет changed objects и выбирает минимально достаточный partial/full
update с DB update при необходимости. `run` запускает 1С для активного environment;
отдельный `designer` уточнить при проектировании CLI.

Развёртывание из обсуждения от 2026-10-26 относится к T31. При уточнении
контракта описать preview выбранной ИБ/environment, совместимость, разрешения,
резервирование и восстановление после ошибки. Создание backlog не разрешает
запись в рабочую ИБ и не меняет приоритет задачи.


На 1С 8.3.27.2342 через ALT 10 Distrobox проверены начальный полный импорт
и последующее применение одной правки BSL в файловой базе и в запущенном
автономном сервере. Автономный импорт использует `ibcmd --pid=<PID>` и ожидает
поколение после переинициализации. Для файловой базы также проверены повтор без
изменений, смена ветки, отказ по устаревшему токену и выявление внешнего импорта
по поколению конфигурации. В установленном Explorer 1.144.0 проверены
предпросмотр и подтверждение полного импорта, затем применение одной правки.
Регрессионный тест проверяет сохранение предыдущего снимка при ошибке и отмене,
блокировку конкурентного применения и явное восстановление.

### Проверка частичного импорта XML по #138

На 1С 8.3.27.2342 через `ibcmd infobase config import files` в файловой
тестовой базе проверены операции с дескрипторами языка:

| Изменение | Переданные файлы | Результат после `config apply` и выгрузки |
| --- | --- | --- |
| Свойство существующего объекта | Один `Languages/Русский.xml` | В выгрузке появился новый комментарий, изменилось поколение, несвязанный BSL остался побайтово прежним |
| Добавление объекта | `Configuration.xml` и новый дескриптор | Появилась запись в корне и новый объект. Один дескриптор платформа отклонила с требованием загрузить родителя |
| Переименование объекта | `Configuration.xml` и дескриптор под новым именем | В выгрузке осталось только новое имя, UUID сохранился |
| Удаление объекта | `Configuration.xml` и дескриптор остающегося языка | Запись и дескриптор удалённого объекта исчезли. Запрос с одним `Configuration.xml` платформа отклонила |

В `eska-build apply` частичный план для существующих XML опирается на
`ObjectModel`, сохранённую идентичность объекта и поколение базы. На 1С
8.3.27.2342 подтверждены свойства языка, общей и вложенной управляемой формы,
а также правки макета формы. Для существующего справочника с формой
платформа отклонила одиночный дескриптор из-за конфликта генерируемого типа.
Частичный набор с дескриптором справочника, дескриптором и макетом его формы
применился. План перечисляет такие сопутствующие файлы.

На 1С 8.3.27.2342 через `eska-build apply` пройдены добавление, переименование
и удаление языка и общей управляемой формы с XML-макетом и модулем BSL.
Переименование сопоставляется по UUID и проверяется по повторной выгрузке. При удалении
1С принимает `Configuration.xml` с неизменённым дескриптором языка по
умолчанию, в том числе при удалении всех общих форм. План перечисляет
добавленные и удалённые файлы в группе объекта. Изменения корня вне
подтверждённых записей и неполные наборы файлов требуют отдельного плана.

В установленном Explorer на русском и английском проверены предпросмотр
с сопутствующими файлами, подтверждение частичного импорта свойств справочника
вместе с BSL и следующий запуск отладки. Evaluate подтвердил новое значение
в test. Отдельная проверка CLI сверила выгруженный XML и неизменность
несвязанного BSL, отказ по устаревшему токену и запрет записи в `prod`.

В установленном Explorer 1.144.0 на русском и английском проверены
группы переименования и удаления общей формы, отдельное отображение
сопутствующего языка, применение и следующий Evaluate в test.

Выбор проекта расширения в workspace-приложении направляет `eska-build apply`
в `test` основной конфигурации. Для установленного расширения `InfoBase`
план сверяет имя и UUID по `ConfigDumpInfo.xml`, учитывает поколения
расширения, основной конфигурации и объявленных транзитивных зависимостей.
Снимки разделены по расширениям, а запись сериализована общей блокировкой базы.
Первый подтверждённый импорт передаёт весь набор файлов выбранного расширения.
Затем частично применяются правки существующих BSL и свойств существующей роли
без отдельных ресурсов. Для роли сверяются UUID, имя и структура дескриптора
по снимку. Если этих сведений нет, нужен полный импорт. Установка и удаление
расширений остаются отдельными сценариями.

На базе с двумя расширениями `generation-id --extension` возвращает отдельный
токен каждого расширения. Частичный импорт BSL меняет токен выбранного
расширения уже на фазе импорта. После `apply` выгрузка подтверждает новый BSL,
а токены основной конфигурации и второго расширения сохраняются.

На файловой базе и автономном сервере 1С 8.3.27.2342 через Distrobox план
правки комментария роли содержит один XML-файл. После применения выгрузка
подтвердила новый комментарий и прежний BSL, поколения основной конфигурации
и второго расширения не изменились. При подключении через `--pid` команда
`export info` может завершиться успешно без файла, поэтому для сверки имени и
UUID применяется выборочная выгрузка объекта `Configuration`.
В установленном Explorer 1.144.0 на русском и английском проверены частичный
импорт роли вместе с BSL, точка в обновлённом модуле расширения и Evaluate.

Explorer предлагает применить изменения и сразу запустить обычный клиент или
сеанс отладки. Rust-план определяет проект запуска, тестовую базу и раннер.
Для расширения используется проект основной конфигурации. При актуальной базе
команды сразу переходят к запуску. Отмена, ошибка применения и смена тестовой
цели останавливают сценарий. Обычные команды запуска и подключения остаются
доступными отдельно.

С `apply --application <имя>` Rust строит один план основной конфигурации и
установленных расширений в порядке зависимостей. Он связывает снимки исходников
и поколения с общим токеном и удерживает блокировку на протяжении применения.
Компоненты без изменений пропускаются. После сбоя результат показывает исход
каждого компонента, а следующий план учитывает уже применённые снимки.
На файловой базе 1С 8.3.27.2342 проверены смена исходников после предпросмотра,
отказ применения второго компонента и восстановление. Новый план пропустил
успешно применённую основную конфигурацию, полностью импортировал прерванное
расширение и частично обновил зависимое расширение. Повторная выгрузка
подтвердила правки обоих расширений. На автономном сервере той же версии
через Distrobox проверены начальный полный импорт, три частичных правки BSL
в порядке зависимостей и повтор без изменений.

В установленном Explorer 1.144.0 на русском и английском подтверждены выбор
приложения, порядок компонентов, показ частичного отказа и предпросмотр
восстановления. После успешного восстановления команда открыла сеанс отладки
на 1С 8.3.27.2342. У двух приложений была общая основная конфигурация.
Адаптер получил явное имя выбранного приложения, остановился в его расширении

### Сравнение с v8-runner v0.17.1 на файловой базе

12 ноября 2026 года сравнили релизные сборки ESKA 0.29.1 (`b0dd37bd`) и
v8-runner 0.17.1 (`fd41189a`) на Fedora Linux 44 Asahi Remix, Linux 7.2.12,
ARM64. Обе команды вызывали `ibcmd` 1С 8.3.27.2342 через одну обёртку
ALT 10 Distrobox. Для v8-runner заданы `providers.push: ibcmd` и
`providers.apply: ibcmd`. Linux ARM64 отсутствует среди артефактов тега,
поэтому v8-runner собран из исходников с `cargo build --release --locked`.
[Исходный код](https://github.com/IngvarConsulting/v8-runner-rust/tree/fd41189af0649fa1ed0f68412636efa7c682e5f7) ·
[Релиз v0.17.1](https://github.com/IngvarConsulting/v8-runner-rust/releases/tag/v0.17.1)

**Подготовка.** Стенд создан в отдельном временном каталоге соседнего
`eska-playground`. Основная конфигурация взята из
`tests/fixtures/forms/native-dendrogram/source`, модуль приложения —
из `crates/eska-debug/tests/fixtures/application/base.bsl`.
В файловой базе установлены два расширения, из которых в сравнение входит
`One` с модулем `application/one.bsl`. В v8-runner заданы два набора
`source-set`: `main` типа `CONFIGURATION` и `One` типа `EXTENSION`.
Путь `tools.platform.path` указывает на общую обёртку в каталоге
`8.3.27.2342` и используется в строгом режиме. В ESKA это `test.runner.ibcmd`.

В каждой копии отдельно зафиксирован снимок исходников и базы через
`eska-build apply --initialize` с подтверждением либо `v8-runner push --force`
на временной копии. До измерений нативные выгрузки показали совпадение байтов
всех 15 файлов основной конфигурации и 3 файлов расширения, кроме служебных
`ConfigDumpInfo.xml`. Перед каждой выборкой восстанавливались исходники,
файловая база и собственная память соответствующего инструмента. Стенд без Git.
Порядок инструментов чередовался. Время копирования, инициализации и контрольной
выгрузки исключено. Первый запуск выделен отдельно, системный кеш сохранялся.

Для ESKA измерены предпросмотр и подтверждение без паузы на ввод пользователя.
Для v8-runner измерен `push main` или `push One` в режиме `--json-message`.
Отдельная строка живой проверки сравнивает `apply --application bench` и
`status --deep` на неизменённой базе с двумя объявленными наборами.
В BSL основной конфигурации меняли `A = 41` на `A = 62`, а в BSL расширения

Время платформы — объединение интервалов вызовов обёртки `ibcmd`, включая
запуск через Distrobox. Разница с полным временем включает запуск CLI, анализ,
подготовку снимка и прочую работу вне обёртки. RSS — максимум GNU `time` для
команды, включая учтённые ОС дочерние процессы. Для цикла ESKA берётся больший
пик двух команд. Переданные байты — размеры файлов в частичном импорте.
В каждой строке три прогона. p95 по ближайшему рангу здесь равен максимуму
выборки. [Исходные измерения](../measurements/t31-apply-comparison.json)

- Для BSL основной конфигурации и свойства языка оба инструмента импортировали
  один и тот же файл. Цикл ESKA занимал примерно на 2,2 с больше. На пути
  `preview → confirm` трасса ESKA показала две проверки версии и дополнительное
  чтение поколения в предпросмотре.
- При добавлении языка оба инструмента передавали `Configuration.xml` и
  дескриптор нового языка. ESKA закончила примерно на 1,34 с быстрее.
  v8-runner после записи дополнительно выгружал сведения о конфигурации и
  ещё раз читал поколение.
- Для BSL расширения ESKA заняла 16,15 с против 7,02 с при том же файле.
  Помимо действий пути основной конфигурации, ESKA проверяла UUID
  установленного расширения и поколение основной конфигурации в обеих фазах.
- Без изменений `push` v8-runner ответил из памяти за 0,032 с по p50. Для живой
  проверки двух наборов `apply --application bench` занял 5,37 с, а
  `status --deep` — 12,13 с. Оба получили текущие поколения. `status --deep`
  также выполнил дополнительные операции платформы и перечислил установленные
  расширения. В отдельном контроле BSL изменили непосредственно в обеих базах
  и оставили сохранённые исходники прежними. ESKA сообщила `database_changed`
  и потребовала пересмотра снимка. `push main` v8-runner пропустил набор,
  а `status --deep` показал `moved_ahead`.
- Размеры измеренных бинарников — 5 663 984 байта у `eska-build` и 12 861 264
  байта у `v8-runner`. Состав команд у бинарников различается.

Следующая контрольная цель для этого стенда — не более 6 вызовов `ibcmd`
в цикле правки BSL основной конфигурации и не более 10 для расширения с
сохранением проверки версии, UUID и поколений. Для времени вне `ibcmd`
контрольный p95 — 0,35 с. Отдельной серии требуют большая конфигурация в Git,
число и объём чтений исходников и поведение с другими исполнителями v8-runner.
