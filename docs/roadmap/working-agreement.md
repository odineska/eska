# Сквозные правила реализации

Эти требования применяются к каждой задаче и не должны дублироваться во всех
файлах этапов.

## Архитектура

- Core не зависит от `clap`, TTY и локализованных строк.
- CLI отвечает за parsing, presentation, exit codes и выбор human/JSON output.
- Ошибки core структурированы; их человекочитаемое представление локализуется на
  presentation layer.
- Не добавлять traits, generics, plugins, caches и dependencies до появления
  реального потребителя.
- Designer XML — единственный source format до отдельной задачи.
- Machine-facing значения (команды, options, config/JSON keys, enum serialization,
  error codes) всегда английские и не зависят от locale.
- Для команд, полезных CI/IDE, проектировать стабильный `--format human|json`.

## Общий backend и адаптеры IDE

По требованию пользователя от 2026-10-23 основную работу выполняет ESKA.
Расширения предоставляют интерфейс к одному backend-контракту. Подключение
другой IDE не должно требовать повторной реализации правил поддержки,
владения исходниками, сессий запросов, восстановления черновиков, проверки
конфликтов, кодирования или операций конструктора. Доменные правила и модели
принадлежат core, их RPC и хранение состояния — соответствующему инструменту
ESKA. Существующий клиентский код переносится при реализации затронутых задач;
это требование не объявляет перенос уже выполненным.

По уточнению от 2026-10-27 форматирование BSL/SDBL принадлежит самостоятельному
`eska-fmt`; `eska fmt` делегирует ему операцию. Для IDE проектный сервер связывает
план форматтера со снимком и защитой документа. Форматирование не требует
bsl-analyzer, индекса проекта или определения типов. Эта граница реализуется
в [T120–T123, T144](22-configurable-formatting.md); семантические языковые сервисы
остаются во внешнем анализаторе.

Защита наподобие `eska-protected:` имеет общую семантику: ESKA определяет
источник, причины запрета, снимок документа, владельца временной блокировки
и допустимость применения. Завершение сессии снимает только её ограничение;
правила поддержки и пользовательские ограничения продолжают действовать.
URI scheme и API конкретного редактора не становятся доменными идентификаторами.

Адаптер отвечает за вкладки, запрет ввода в защищённом представлении,
показ состояния и применение проверенного плана через штатный Undo/Redo.
По уточнению пользователя от 2026-10-24 дочерний редактор ведёт себя как
модальный: вместо родительских представлений показывается только дочернее,
а навигация к родителю возвращает фокус дочернему. Применение, отмена и
закрытие дочернего представления возвращают родителя; отмена самого закрытия
оставляет дочернее открытым. Это относится и к конструктору над черновиком.
Способ управления вкладками принадлежит адаптеру. При закрытии несохранённой
native-вкладки решение принимает пользователь в штатном диалоге IDE; нельзя
молча сохранять или отбрасывать её текст. Снимок ESKA создаётся после этого
решения. Native read-only overrides пользователя не меняются.

ESKA хранит полный снимок владельца и перед применением проверяет версию,
текст, исходник, descriptor, поддержку и контекст. Внешняя или программная
правка по-прежнему вызывает конфликт и сохраняет черновик. Завершение
освобождает только ограничение сессии ESKA.
Для каждой IDE подтверждается этот контракт, включая dirty-буферы, split-вкладки,
повторное открытие и перезапуск. Это решение не ослабляет запреты поддержки,
пользователя и файловой системы.

Доменные сценарии проверяются без IDE через общий core/RPC. Нативные проверки
адаптера подтверждают тот же контракт средствами конкретного редактора.
Общий backend не означает приёмку IDE, в которой проверки не выполнялись.

## Безопасность и производительность

- Любая потенциально разрушающая операция имеет preflight, понятный preview и
  явный `--force`, если безопасной альтернативы нет.
- Не использовать `reset --hard` как универсальный механизм.
- Не привязывать `status`, `diff` и `save` к полному parse конфигурации.
- Сначала рассматривать changed paths и инкрементальную обработку; cache добавлять
  только по измеренной необходимости.
- Для каждой VCS-операции сначала проверяется возможность сохранить контракт и
  safety guarantees через текущую закреплённую версию `gix`.
- System Git допустим только как capability fallback через один infrastructure
  layer: для отсутствующей высокоуровневой orchestration worktree/index,
  hooks/editor/signing, LFS или конкретно неподдержанного transport/credential
  сценария. Fallback не является безусловным повтором после любой ошибки `gix`.
- Не использовать shell parsing и не разбирать локализованный human output Git;
  оставшиеся system Git-вызовы перечислять и обосновывать в решениях задачи.

## Definition of Done

Для каждой implementation task обязательно:

1. сверить задачу с фактической архитектурой;
2. реализовать только заявленный scope;
3. добавить human strings одновременно в `ru-RU` и `en-US`;
4. покрыть locale-independent core unit-тестами;
5. покрыть CLI exit code/stdout/stderr integration-тестами;
6. для JSON проверить стабильную схему и независимость от locale;
7. для Git использовать маленькие настоящие временные repositories, когда это
   надёжнее mock;
8. выполнить `cargo fmt --check`, `cargo check`,
   `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test`;
9. вручную проверить затронутые CLI-сценарии на обоих языках;
10. удалить ставшие ненужными код и dependencies;
11. обновить состояние Issue и статус на доске GitHub, а решения и результаты
    проверок сохранить в документах roadmap со ссылкой из Issue;
12. не менять версию crate вручную — ей управляет release automation.
