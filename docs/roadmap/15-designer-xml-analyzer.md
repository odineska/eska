План от 2026-10-20 по решению пользователя. T90, T83, T91, T84, T92, T93, T94, T95, T96, T97 и T85–T89 — `DONE`.
В T88 проверены защита правок, XML/BSL refresh, смена ветки и приложения,

Приёмка T89 завершена 2026-10-22 в согласованной среде Linux/VSCodium:
минимальные release-установки, нативная сборка/распаковка и полный CLI прошли.
Измеренные превышения дерева, запуска языка и definition по решению пользователя
вынесены в [T106](17-language-performance.md). В ходе последующего ревью
исправлены три причины в Explorer; новая серия проходит 9 из 12 gates.
T106 — `IN-PROGRESS`, оставшиеся превышения и измерения записаны в её отчёте.
Цель до этапа «7. Приёмка» включительно выполнена с этим явно отложенным
остатком. T98–T99 ожидают отдельного решения.
Цель: самостоятельные инструменты проекта, анализа, сборки и VCS можно
устанавливать выборочно, в том числе для CI. Explorer устанавливает проектный
backend ESKA и внешний bsl-analyzer, предоставляет дерево, подсветку и языковые
функции одним расширением. `eska.toml` остаётся первичным конфигом.

Designer XML и BSL остаются исходниками. Экспериментальный формат ESKA,
встраивание Rust-крейтов анализатора, vendoring его ядра и собственный форк
bsl-analyzer исключены. Интеграция использует опубликованные бинарники upstream
и их CLI/LSP. Принятие наших изменений upstream не является условием поставки.
Готовность команд определяется статусом соответствующего этапа. Компонентные
архивы проверены локально; их публикация остаётся отдельной задачей.

Продолжение по запросу от 2026-10-21 —
[редактор и конструктор запросов T100–T105](16-query-editing.md).
Запросы СКД, динамических списков и BSL редактируются как представления
существующих исходников; отдельный формат хранения не вводится.
Эти задачи запланированы после T89, не входят в её приёмку и не зависят
от T98–T99. Статусы и порядок текущего плана сохраняются.

формат, встроенное ядро анализа и результаты приёмки сюда не переносятся.

Новый визуальный дизайнер форм, multi-root и новые Git/build-команды Explorer
в эту поставку не входят; самостоятельные CLI не расширяют меню редактора.

## Инструменты и зависимости

| Компонент | Ответственность | Обязательные зависимости при запуске |
|---|---|---|
| `eska-project` | Манифест, discovery, контексты приложений, структурная проверка Designer XML, существующие операции с метаданными, правила поддержки, подготовка конфига анализатора | Без полной `eska`, Git и платформы; внешний анализатор нужен только для проверки его конфига |
| `eska-project serve` | Проектный сервер для Explorer: дерево, свойства, поиск объектов, разрешения и планы правок; перенос существующего `eska ide` | Собственное ядро проекта; без языкового сервера |
| `bsl-analyzer` | Семантика BSL/SDBL, диагностики и языковые функции по LSP; пакетный анализ по CLI | Отдельный опубликованный `bsl-analyzer-app` upstream |
| `eska-check` | Структурная проверка и пакетный статический анализ, порог диагностик, проверка полноты результата и отчёты CI | Встроенные общие библиотеки ESKA и внешний анализатор; без `eska`, IDE, `eska-project` как процесса и платформы |
| `eska-build` | Нативные артефакты, распаковка CF/CFE/EPF/ERF в Designer XML, существующие проверки платформой, runner и временные ИБ | Встроенное ядро проекта и установленная платформа; без анализатора, сервера метаданных и обязательного VCS |
| `eska-vcs` | Git/workflow, status/diff/save, задачи и полки; смысловой diff метаданных | Ядро проекта и `gix`; без анализатора и платформы |
| `eska-debug` | Отдельная отладочная сессия через DAP | Выбранный в T98 отладочный backend и среда 1С; опциональная очередь T98–T99 |
| `eska` | Общая команда, делегирующая операции специализированным инструментам | Только компоненты выбранной операции; собственных модели, индекса и движков нет |
| Explorer | Два клиента, базовая грамматика, установка компонентов, выбор контекста и обработка конфликта | `eska-project` для дерева; bsl-analyzer для языка; build/VCS/debug не обязательны |

TypeScript не разбирает манифесты ESKA и XML заново. Метаданные остаются в
ESKA и доступны по версионируемому Metadata API; языковые запросы идут
непосредственно в bsl-analyzer по LSP. `eska-project serve` не проксирует LSP
и не становится общим сервером анализа. `eska-check` запускает отдельный
одноразовый CLI-процесс анализатора, не подключаясь к живой сессии редактора.

Designer XML не преобразуется в другой исходный формат. Получение XML из
CF/CFE/EPF/ERF принадлежит `eska-build`. Полная команда `eska new --from`
может организовать распаковку и создание проекта; обычный `eska-project`
не должен требовать платформу или автоматически инициализировать Git.
VCS-проверки замены существующих исходников остаются в orchestration-слое;
при их отделении сохраняются preview, контроль изменений и откат.
Самостоятельная распаковка `eska-build` публикует XML в новый выходной каталог.
Замена существующего `source` — составная операция с project/VCS preflight;
отсутствие нужного компонента останавливает её до записи, а не отключает проверки.

Отдельные библиотеки переиспользуют правила поддержки и разрешения изменений.
Если операция использует принятую базу, её identity, проверенный снимок XML
и fingerprint определяются общим проектным контрактом. База из эксперимента
не считается принятой автоматически. Перенос сохраняет неизвестные XML-данные
и двоичные ресурсы; он не объявляет реализованными новые CRUD-операции или
полную проверку конфигурации платформой.

### Устройство репозитория и переход

Один Rust workspace содержит самостоятельные Cargo packages инструментов
и общие библиотеки. Отдельные репозитории и выпуск своей сборки анализатора
не требуются. Начальные границы библиотек:

- ядро проекта: манифест, пути, контексты, Designer XML, identity и support policy;
- адаптер внешнего анализатора: генерация TOML, проверка контракта, запуск CLI
  и чтение результатов; общий для `eska-project` и `eska-check`;
- исполнители платформы и VCS: зависимости только соответствующих инструментов.

Типы build/workflow-настроек отделяются от исполнителей. Ядро не зависит от
`gix`, platform runner, LSP/DAP, `clap`, VS Code или локализованного вывода.
Внутренние модули не превращаются в отдельные crates без текущего потребителя.
Ни одна общая библиотека не ссылается обратно на CLI инструмента.

В T90–T95 существующий CLI остаётся рабочим потребителем выделяемых библиотек.
Новая точка входа использует ту же реализацию; второй движок не создаётся.
T96 переводит `eska` на делегирование с сохранением документированных команд,
stdout/stderr, exit codes и JSON-схем. Для составных операций явно фиксируются
порядок, границы записи и восстановление после ошибки. Неизвестный или
отсутствующий компонент даёт понятную ошибку; CI не запускает установщик сам.
Перед T96 инвентаризируются все текущие команды, включая `doctor`, `config`,
`platform`, `version`, `patch`, `clean`, `import`, `ide` и `update`, чтобы
разделение не оставило их без владельца.

## Статическая проверка для CI

`eska-check` использует тот же resolver и генератор, что проектный backend.
Он проверяет структуру, подготавливает производный конфиг и запускает
закреплённый внешний `bsl-analyzer-app analyze` с машинным результатом.
В CI все компоненты задаются заранее; сеть, автообновление, IDE и платформа
для статического анализа не требуются. Пути и состав приложения вручную
не дублируются в аргументах pipeline.

Нулевой exit code анализатора не равен успешной проверке проекта.
В опубликованной 0.3.2 JSONL-анализ может завершиться через `Ok(())` после
диагностик и сообщений о неуспешно разобранных файлах. Адаптер проверяет
события `start`/`file`/`done`, ошибки файлов, `failed_files`, полноту потока
и соответствие ожидаемому набору исходников. Неожиданно пустой набор,
отсутствие `done`, повреждённый результат, timeout и отмена не дают зелёный CI.
Проверяется и ненулевой exit code процесса; JSONL не отменяет ошибку запуска.

T93 фиксирует публичный отчёт и отдельные результаты: проверка пройдена,
порог диагностик превышен, анализ не завершён/инструмент неисправен, отмена.
Порог и выбор правил берутся из политики `eska.toml`; новые ключи определяются
в схеме T93, не подменяют диагностики bsl-analyzer и не задают второй состав
workspace. Первая поставка проверяет полный выбранный контекст.
Инкрементальный анализ допустим позже при доказанной полноте зависимостей;
он не делает Git обязательным для обычного `eska-check`.

## Выборочная поставка и совместимость

| Сценарий | Устанавливаемые компоненты |
|---|---|
| Структурная работа с XML | `eska-project` |
| Статический CI | `eska-check` и внешний bsl-analyzer |
| Сборка CI | `eska-build` и платформа |
| Git/workflow | `eska-vcs` |
| Explorer | `eska-project` и внешний bsl-analyzer |
| Полный комплект разработчика | `eska`, project/check/build/vcs и внешний анализатор; платформа отдельно |
| Отладка | `eska-debug` и проверенный DAP backend, отдельно от Explorer |

Библиотеки входят в бинарники потребителей и не требуют отдельного сервиса.
На первом этапе собственные инструменты имеют общую версию релиза, но
устанавливаются выборочно. Версия bsl-analyzer независима. Для смешанных версий
проверяются поддерживаемые config schemas и API; несовместимость объясняется
до записи. CI закрепляет версии и checksums, IDE использует проверенные
capabilities и предлагает обновления отдельно для каждого backend.

CLI-контракт upstream проверяется через `contract`, конфиг — через
`check-config`; схемы результатов и поведение покрываются интеграционными
тестами, поскольку перечень flags не доказывает семантику их сочетаний.
LSP использует объявленные capabilities. Дополнительные API допускаются
только по подтверждённому контракту; непринятый upstream PR не нужен для запуска.

Разделение ESKA не уменьшает автоматически upstream-бинарник и его индекс.
Его CLI/LSP/MCP/DAP-зависимости остаются частью опубликованного приложения.
ESKA и bsl-analyzer имеют независимые модели метаданных; общая память или
единый индекс не обещаются. Размер установки и память измеряются отдельно.

T97 определяет архивы по компонентам, manifest состава, checksums, лицензии,
целевые ОС/архитектуры, установку/обновление и удаление только управляемых файлов.
Существующий общий каталог ESKA пользователя переиспользуется; выборочная
установка не удаляет другие инструменты. Перед заменой проверяются версия,
способ установки, целостность и возможность восстановления. Для собственного
бинарника поддерживается явный путь без перезаписи.
Правки Actions, release/changelog automation и publication pipeline требуют
отдельной задачи. T97 проверяет локальную упаковку и установку компонентов.

## Проверка HTTP-отладки 1С

Согласованный этап описан в [#206](https://github.com/odineska/eska/issues/206)
и [#207](https://github.com/odineska/eska/issues/207). Explorer использует DAP
поверх stdio. Внешний адаптер обращается к `dbgs` по HTTP. Клиент 1С
подключается к базе по её собственным параметрам.

### Проверка на 8.3.27.2342

На Linux ARM64 в ALT Linux 10 Distrobox проверена новая файловая база.
Клиент `1cv8c` работал на отдельном Xvfb, `dbgs` слушал loopback.
[onec-debug-adapter 0.4.1](https://github.com/yellow-hammer/onec-debug-adapter/releases/tag/v0.4.1)
(MIT, commit `cca490f2715352bb78f39ef3219a5e6e20b4b940`) собран из исходников
для .NET 8 и запущен на хосте. Опубликованная сборка Linux предназначена для
x64. В контейнере отсутствовала `libatomic.so.1`. Библиотека из пакета ALT
Linux подключена через `LD_LIBRARY_PATH` только для клиента стенда.

Для воспроизведения скопируйте
[`tests/fixtures/forms/native-dendrogram/source`](../../tests/fixtures/forms/native-dendrogram/source)
в новый каталог внутри соседнего `eska-playground`. Имя каталога может содержать
пробелы и кириллицу. В копию добавьте `Ext/ManagedApplicationModule.bsl`.

```bsl
Процедура ПриНачалеРаботыСистемы()
    A = 41;
    B = Увеличить(A);
    Сообщить(B);
КонецПроцедуры

Функция Увеличить(Число)
    Результат = Число + 1;
    Возврат Результат;
КонецФункции
```

Внутри выделенного каталога выполните `ibcmd infobase create --data=База`,
`ibcmd infobase config import --data=База Исходники` и
`ibcmd infobase config apply --data=База`. Запустите `dbgs` на свободном
локальном порту. После DAP `initialize` передайте `attach` с
`connectionString = /F<абсолютный путь к База/db-data>`, адресом и портом
`debugServerHost` / `debugServerPort`, абсолютным `rootProject` и
`autoAttachTypes = ["ManagedClient", "Client", "Server", "ServerEmulation"]`.
После `initialized` и ответа на `setBreakpoints` запустите клиент на той же
базе с `/DEBUG -http -attach /DEBUGGERURL <HTTP-адрес dbgs>`.

| Запрос или событие | Фактический результат |
| --- | --- |
| `setBreakpoints` на строке 3 | Точка подтверждена, получено событие `stopped` с причиной `breakpoint` |
| `stackTrace`, `scopes`, `variables` | Путь совпал с BSL в Designer XML, локальная переменная `A` равна `41` |
| `evaluate` в текущем frame | `A + 1` вернуло число `42` |
| `stepIn`, затем `evaluate` в вызывающем frame | Стек из двух кадров на строках 8 и 3, `A + 2` в вызывающем кадре вернуло число `43` |
| `next`, `stepOut`, `continue` | Остановки на строках 9 и 3, затем выполнение продолжилось |
| `disconnect` с `terminateDebuggee: false` | Адаптер подтвердил отключение, клиент оставался запущен после завершения адаптера |

Адаптер 0.4.1 выполняет `next`, `stepIn` и `stepOut`, но не посылает
успешный DAP response. На стенде завершение каждого шага отслеживалось по
`continued` и последующему `stopped` для того же потока. В отдельном
`bsl-analyzer-app dap` 0.2.67 подключение к `dbgs` прошло, а запрос
`setBreakpoints` не ответил за 12 секунд. Код
[bsl-analyzer 0.4.6](https://github.com/itrous/bsl-analyzer/blob/v0.4.6/crates/bsl-debug/src/dap/mod.rs)
при вычислении выражения использует верхний кадр независимо от `frameId`.

### Контракт интеграции

Для реализации выбран внешний `onec-debug-adapter` 0.4.1. ESKA передаёт
сопоставление исходников и параметры сессии через DAP в памяти. Адаптер
устанавливается независимо от Explorer. Для запуска с отладкой ESKA должна
дождаться установки начальных breakpoint и только затем запустить клиент
выбранным runner. Для attach используется существующий HTTP endpoint.
При отключении ESKA завершает адаптер и освобождает только созданные ею
процессы. Evaluate доступен в обоих профилях и может менять данные.

Перед интеграцией в Explorer требуется обработать отсутствие ответа на
успешный шаг у 0.4.1. Ошибка backend или отсутствие подтверждающего события
должны завершать ожидание с ошибкой. Успешное DAP-подключение само по себе
не подтверждает наличие нужного сеанса или совпадение исходников.
На стенде пока не проверены запуск из установленного Explorer, подключение
к клиенту, запущенному до DAP-сессии, и внешний сервер через VPN.

## Первичный конфиг и контекст приложения

`eska.toml` и манифесты его members — единственный редактируемый источник
состава проектов, путей и версии платформы. `Project` остаётся одной
сборочной единицей с одним `source`, как в [T44](11-workspaces.md).

Workspace группирует пути проектов по приложениям в `workspace.members.<имя>`.
Роли основной конфигурации, расширений и внешних обработок/отчётов заданы явно.
Зависимости расширений задаются явно; их нельзя выводить из соседства
каталогов или совпадения имён модулей. Два приложения одного workspace
не объединяются в одну основную конфигурацию.

Первоначальная схема T83 с отдельными `members` и `applications` заменена
единой [схемой состава приложения](../application-context.md) `designer-xml-3`.
Путь, `scope` (по умолчанию `InfoBase`) и `depends_on` принадлежат одной записи
расширения. Строковые списки расширений и отдельные карты их параметров не
поддерживаются. Политика `tools.bsl-analyzer` и
[производный конфиг](../analyzer-configuration.md) остаются механизмом T84.
Пример корневого `eska.toml` для `buhmfo`:

```toml
[workspace.members.buhmfo]
configuration = "src/buhmfo"
extensions = [
    { path = "src/ExternalSystems" },
    { path = "src/dzp_АвтоматическаяЗагрузкаВыписок" },
    { path = "src/dzp_АдаптацияКодаТиповойКонфигурации" },
    { path = "src/dzp_ЗаполнениеБанковскихВыписок" },
    { path = "src/dzp_ИсправлениеОшибокКонфигурации" },
]

[tools.bsl-analyzer.diagnostics.parameters]
LineLength = false
```

Пути вычисляются из проверенных member root и `project.source`; нельзя
просто приписывать `/src`. В T83 также фиксируются ссылки на внешние объекты,
граф зависимостей и поведение standalone-проектов всех четырёх типов.
Одиночная обработка без базы остаётся допустимым проектом; ограниченный
контекст её анализа не превращается в запрет редактирования.

Целевая платформа анализа по умолчанию берётся из эффективного
`build.platform_version` основной конфигурации, с учётом наследования.
Намеренно другая целевая платформа задаётся один раз в контексте ESKA.
Режим совместимости берётся из XML; он не подменяется версией сборки.

## Производная конфигурация анализатора

Для первой поставки выбран **полностью генерируемый обычный
`bsl-analyzer.toml` в корне выбранного workspace**. Общие поля вычисляет ESKA;
политику диагностик, форматирования и анализа берёт из
`[tools.bsl-analyzer]`. Эта секция не может переопределять управляемые пути,
состав приложения и целевую платформу.

Такой файл поддерживается опубликованным bsl-analyzer 0.3.2 и обнаруживается
его LSP-клиентом обычным способом. Возможность `extends` уже принята в
upstream, но отсутствует в этом релизе; она не является зависимостью плана.
Не добавлять одновременно второй режим конфигурации ради будущего `extends`.

Генератор должен:

- давать одинаковый результат для CLI и Explorer, независимо от locale;
- сохранять относительные переносимые пути от корня итогового конфига;
- проверять результат через поддерживаемый `check-config` выбранного сервера;
- записывать файл атомарно и только при изменении содержимого;
- хранить отметку владения и проверять отпечаток ранее созданного содержимого;
- при ручной правке производного файла возвращать конфликт, а не терять правки;
- при ошибке сохранять предыдущий корректный файл, но не запускать новый анализ
  с контекстом, не соответствующим текущему `eska.toml`.

Промежуточная проверка должна разрешать пути так же, как итоговый файл;
перенос временного TOML в другой каталог не должен менять их смысл.
Версия генератора и входной fingerprint входят в JSON-результат подготовки.
Новый daemon или BSL-индекс для этой операции не нужен.

Первая версия обслуживает один выбранный контекст на корень workspace.
Разные окна с одинаковым контекстом переиспользуют файл; разные активные
контексты одного корня не должны перезаписывать конфигурацию друг друга.
При конфликте подготовка второго контекста останавливается с объяснением.
Переключение контекста согласует остановку клиента, подготовку и новый запуск.
Обхода через фиктивный `rootUri`, копии BSL или переписывание URI нет.

### Миграция существующего проекта

Существующий пользовательский `bsl-analyzer.toml` не считается генерируемым.
Подготовка сначала показывает preview: какие значения перейдут в ESKA,
какие пути совпадают и где требуется выбор. Сохраняются все поддерживаемые
параметры анализа, а не только известные примеры вроде `LineLength`.
Неизвестные или несовместимые параметры дают диагностику до записи.

Применение миграции — явное действие пользователя с сохранением оригинала
и проверкой, что файлы не изменились после preview. Частичная ошибка не
оставляет согласованным только один из двух конфигов. После миграции
вручную редактируется только ESKA; обратной синхронизации нет.
Команда проверки актуальности ничего не записывает и пригодна для CI.

## Установка и запуск

Explorer устанавливает только `eska-project` в общий каталог инструментов ESKA
пользователя; совместимый уже установленный компонент переиспользуется.
Оболочка `eska`, build/VCS/check/debug для дерева не требуются.
Для bsl-analyzer добавляется управляемая установка выбранной проверенной
версии в хранилище расширения на стороне workspace extension host.
Явный путь к своему серверу поддерживается; такой файл не заменяется
автоматическим обновлением. Одинаковые версии переиспользуются.

Один сценарий подготовки показывает необходимые компоненты и их версии,
получает согласие на установку и выполняет её без ручного поиска бинарников.
Он учитывает ОС/архитектуру, SSH/WSL/контейнер, отмену, параллельные окна,
временные файлы, целостность загрузки и проверку результата. Ошибка установки
анализатора не отключает исправную ESKA и дерево.

Совместимость фиксируется проверенной парой версий и фактическими capabilities.
Установка произвольного `latest` без проверки не является политикой обновления.
Для управляемых компонентов сохраняется возможность восстановления предыдущей
рабочей версии; способ установки и явный пользовательский путь учитываются.
Повторный запуск с установленными компонентами работает без сети.
Первоначальная установка без сети предусматривает явные локальные бинарники;
отдельный offline-дистрибутив не входит в первую поставку.

T92 задаёт переход с `eska ide` на `eska-project serve`, включая настройку пути,
проверку identity/capabilities и сообщение о старом backend. Пользовательский
путь не переписывается молча. Старый документированный вход `eska ide`
сохраняет делегирование в T96; новая версия Explorer обращается к project
напрямую. Разработка T92 проверяется с явным путём к локальному бинарнику;
готовая установка подключается после T97 в T85.

Порядок запуска языковой части:

1. Проверить доверие workspace, выбранный корень и конфликт расширений.
2. Обеспечить доступность `eska-project` и получить проверенный контекст
   без записи конфигурации анализатора.
3. Проверить выбранный сервер и при необходимости предложить установку.
4. Повторно проверить конфликт и контекст, затем подготовить конфигурацию
   с проверкой через уже доступный сервер.
5. Проверить актуальность результата и отсутствие конфликта после подготовки,
   затем запустить единственный собственный LSP-клиент для контекста окна.

Текущая модель выбора одного корня Explorer сохраняется. Полноценный
параллельный multi-root режим не добавляется этой задачей.

### Строка состояния и независимые обновления

В нижней строке состояния остаются два отдельных элемента: `BSL Analyzer v…`
и `ESKA v…`. Анализатор получает оформление и действия по образцу ESKA:
версия выбранного бинарника, подсказка с путём и состоянием, нажатие для
проверки обновлений своего компонента. Команды проверки доступны и в палитре.
Версия в индикаторе ESKA принадлежит фактически подключённому `eska-project`,
а не оболочке или полному комплекту; компонент и путь указаны в подсказке.
Доступная версия не подменяет установленную; отсутствие бинарника, ошибка
и приостановка клиента не отображаются как успешное подключение.

Для каждого бэкенда отдельно хранятся настройка фоновой проверки, время
последней проверки, доступный релиз и состояние выполняемой операции.
Фоновая проверка — не чаще раза в сутки для каждого компонента на своём host;
ручная проверка не зависит от суточного интервала. Существующая настройка
`eska.explorer.checkForUpdates` продолжает управлять только ESKA.
Отключение проверки, сетевая ошибка, отмена или занятость одного компонента
не подавляют проверку другого и не скрывают его индикатор.

Уведомление называет конкретный бэкенд, установленную и предлагаемую версии.
Как у ESKA, установка обновления требует отдельного действия пользователя.
Обновление одного бэкенда не запускает обновление второго: совместимость
предлагаемой версии проверяется с текущей установленной парой. Несовместимый
релиз показывается с причиной ограничения, без автоматической замены пары.
После обновления повторно определяется фактическая версия; другой сервис
не перезапускается без необходимости, подтверждённой его контрактом.

В новой поставке проверка ESKA управляет компонентом `eska-project` в общей
установке, без обновления всего комплекта. Это явное изменение существующего
сценария обновления монолитной ESKA и документируется в T85/T97.
При выбранной сборке для разработки обновляется только управляемая установка;
пользовательский бинарник не перезаписывается. Это относится и к анализатору.
Подсказка и предложение обновления различают используемый бинарник и установку,
которой управляет Explorer.

При конфликте со сторонним расширением индикатор собственного анализатора
остаётся видимым с причиной приостановки и указанием принадлежности Explorer.
Проверка обновлений доступна; завершение проверки или установки не возобновляет
клиент, пока конфликт сохраняется. Индикатор стороннего расширения Explorer
не изменяет, его версию не выдаёт за версию своего сервера.

## Конфликт со сторонним расширением

Первый известный ID — `elishevkirill.bsl-analyzer-lsp`. Проверка использует
публичный API VS Code и доступность расширения для текущего workspace host;
сам установленный бинарник анализатора конфликтом не является.
`Extension.isActive === false` означает также «ещё не активировано»,
поэтому ожидание активации не должно запускать второй клиент.

| Событие | Собственный клиент Explorer | Интерфейс |
|---|---|---|
| Конфликта нет | Подготовка и запуск | Обычный статус анализа |
| Конфликт найден до запуска | Не запускается | Предупреждение и состояние `suspended-conflict` |
| Конфликт появился во время работы или подготовки | Отмена подготовки/рестарта, остановка своего клиента | Дерево, свойства и базовая подсветка остаются доступны |
| Стороннее расширение отключено или удалено | Повторная проверка и запуск, если языковая часть разрешена пользователем | Сброс состояния конфликта |
| Для изменения VS Code требует перезапуск | Клиент остаётся приостановленным до подтверждённой доступности | Подсказка перезапустить расширения |

Наблюдение выполняется до старта и через `extensions.onDidChange`.
После любого асинхронного ожидания проверяется поколение состояния:
устаревший callback не может возобновить клиент после конфликта.
Останавливается только принадлежащий Explorer клиент; процессы стороннего
расширения и общие сервисы анализатора не завершаются по имени.

Предупреждение сообщает причину приостановки и предлагает открыть управление
сторонним расширением либо продолжить с внешним клиентом. Оно не повторяется
при каждом открытии BSL или раскрытии узла; новый конфликт после устранения
старого является новым событием. Состояние видно и после закрытия уведомления.
Все строки добавляются в `ru-RU` и `en-US`.

Публичный API не предоставляет принудительное отключение чужого расширения.
Не использовать внутренние команды disable или запись в хранилище VS Code.
Приостановка собственного клиента не означает, что сторонний сервер исправен:
его диагностики не подменяются статусом успешного анализа ESKA.

## Языковая интеграция

Explorer регистрирует BSL, базовую TextMate-подсветку, комментарии, скобки и
отступы. SDBL и встроенные запросы покрываются в пределах подтверждённых
возможностей сервера. Семантические токены и языковые операции подключаются
через `vscode-languageclient` согласно объявленным capabilities.

Настоящие `file:` URI и несохранённый текст передаются через LSP. Изменение
метаданных средствами ESKA и смена ветки должны обновлять контекст анализа;
изменения манифестов сначала проходят повторную подготовку. Поздние ответы
от прежнего документа, контекста или сервера отбрасываются.

Для `eska-protected:` сохраняется проверенный мост к исходным документам.
Форматирование, rename, code actions и серверный `workspace/applyEdit`
проверяют все затрагиваемые файлы и операции с ресурсами. Если хотя бы одна
цель запрещена policy или версия документа устарела, весь edit отклоняется
с объяснением. Нет частичного применения и обхода защиты через другой URI.

LSP lifecycle не зависит от раскрытия дерева. Сбой одной службы не отключает
другую. При перезапуске/закрытии освобождаются свои подписки, diagnostics,
таймеры и процессы с ограниченным ожиданием; число повторов после сбоя ограничено.
Текущую упаковку `--no-dependencies` нужно согласовать с новой runtime-зависимостью:
LSP-клиент и его зависимости должны попадать в проверяемый VSIX.

## Проверки и приёмка

Маленькие fixtures покрывают standalone-конфигурацию, расширение, EPF, ERF,
workspace с одной базой и пятью расширениями, несколько независимых приложений,
нестандартный `source`, кириллицу/пробелы, повреждённый TOML, отсутствующие
members, циклы зависимостей и непереносимые пути.

Для Rust обязательны полный набор из [рабочего соглашения](working-agreement.md)
и CLI-проверки exit code/stdout/stderr на двух языках. JSON не зависит от locale.
После выделения workspace проверками охватываются все его packages, а не
только оболочка; для check/clippy/test используется явный `--workspace`.
Граф зависимостей проверяется отдельно для каждого инструмента: отсутствие
запуска лишнего процесса не доказывает отсутствие зависимости в сборке.
Для Explorer — typecheck, Node tests, настоящие backend/LSP-процессы и
Extension Host. Mock подтверждает orchestration, но не заменяет проверку
реального сервера и собранного VSIX.

Для каждой строки матрицы выборочной поставки создаётся изолированное окружение
только с перечисленными компонентами. `eska-check` и `eska-build` проверяются
без оболочки, проектного сервера и пользовательских PATH-подстановок; полный
и прямой CLI сравниваются на одинаковых входах. Для check проверяются реальные
диагностики и намеренные сбои потока/процесса, различие полного и частичного
анализа, идентичность состава и настроек с LSP. Наличие общего ядра upstream
само по себе не доказывает равенство CLI- и LSP-результатов.

Native-проверки T94 выполняются на маленьких собственных fixtures реальной
платформой; mock runner проверяет orchestration, но не сборку. Этот этап
не подразумевает запуск тяжёлой сборки `buhmfo`. Для T95 используются маленькие
временные Git repositories. Недоступная платформа или ОС отмечается как
непроверенная, а не как успешная приёмка.

Обязательны два изолированных профиля редактора: только Explorer; Explorer
со сторонним bsl-analyzer. Во втором проверяется и отключённое расширение,
и включённое, которое ещё не активировалось. Отдельно проверяются конфликт
во время установки/рестарта и отсутствие циклических автоматических запусков.
Приёмка своего клиента не должна случайно получать подсветку или diagnostics
от расширений обычного пользовательского профиля.

Для строки состояния проверяются обновления только ESKA, только анализатора
и обоих компонентов: подписи, подсказки, команды, отдельные настройки и
суточные интервалы. Ошибка/отмена одной проверки не мешает другой; установка
обновления меняет версию только выбранного компонента. Отдельные сценарии —
пользовательский бинарник, несовместимый релиз и обновление при конфликте:
индикатор остаётся видимым, собственный LSP-клиент не возобновляется.

Крупный вход — предоставленный пользователем Designer XML проекта `buhmfo`
с основной конфигурацией и пятью расширениями. CF не конвертируется, платформа
1С для этих проверок не запускается. Исходный рабочий проект не изменяется:
проверки записи выполняются в собственной копии внутри соседнего
`eska-playground`, после проверки свободного места; при возможности — reflink.
Путь playground вычисляется относительно корня репозитория, передаётся через
абсолютный `ESKA_TEST_ROOT`; тесты удаляют только собственные подкаталоги.

До изменений кода фиксируется baseline текущей пары Explorer + внешнее
расширение. Сравнение использует один набор исходников, одинаковую версию
сервера и эквивалентные настройки анализа. Установка компонентов измеряется
отдельно от открытия уже подготовленного проекта.

| Измерение | Как проверять |
|---|---|
| Холодное и повторное открытие | Не менее пяти запусков каждого режима; время до дерева и отдельно до готовности языкового сервиса |
| Память | Пиковый и установившийся RSS, при доступности PSS; Extension Host, ESKA и все относящиеся к тесту процессы анализатора |
| CPU, диск и размер кэшей | Суммарные показатели за одинаковые сценарии; размер установленных компонентов отдельно |
| Правка BSL, hover, completion, definition, диагностика | Не менее 30 повторов; медиана и p95, наличие правильного ответа |
| XML refresh и смена ветки/контекста | Корректность нового состояния, отсутствие старых diagnostics и лишней индексации |
| Конфликт и shutdown | Отсутствие второго клиента ESKA, освобождение его ресурсов, сохранение работоспособности дерева |

Baseline и допустимый разброс фиксируются в T90 до изменений реализации.
Предварительный критерий: overhead новой интеграции не превышает 10% либо
измеренный фоновый разброс, если он больше, при одинаковом сервере и настройках.
Превышение требует объяснения и отдельного решения, а не объявления улучшения.
Упаковка в одно расширение сама по себе не обещает снижение памяти анализатора.
Число OS-процессов не равно числу клиентов: proxy/общий сервис учитываются отдельно.

T89 публикует команды запуска с отдельными `--user-data-dir` и
`--extensions-dir`, точные версии/ревизии, параметры стенда и результаты.
Linux/VSCodium, VS Code, Windows, macOS и Remote отмечаются по фактическим
проверкам; неподдерживаемые upstream архитектуры указываются явно.
По ответу пользователя от 2026-10-21 доступная приёмка ограничена текущим
Linux/VSCodium; остальные среды фиксируются как непроверенные.
Без этих результатов интеграция остаётся пилотом, а T89 не получает `DONE`.
Решением от 2026-10-22 пользователь отложил измеренные превышения
производительности в T106; это исключение при завершении T89, а не изменение
исходных допусков или отметка passed у численных gates.

### Воспроизведение измерений

Из корня репозитория ESKA, на сохранённом Linux/VSCodium-стенде:

```sh
acceptance_dir="$(realpath ../eska-playground/t89-acceptance-64abnlk1)"
source_series="$acceptance_dir/series-fresh-x3nxjx6_"
series_dir="$(mktemp -d "$acceptance_dir/series-replay-XXXXXXXX")"

  "$source_series/provenance.json" "$source_series/summarize.py" \
  "$source_series/replay-summary.py" "$series_dir/"
cp -a "$source_series/tools" "$series_dir/tools"
python3 -B "$series_dir/run.py"
python3 -B "$series_dir/replay-summary.py"
```

Runner создаёт отдельные `--user-data-dir`/`--extensions-dir` каждого запуска
и использует сохранённые бинарники, runtime и две собственные копии входа.

неизменённые gates из T90; пересчёт на сохранённых данных дал те же агрегаты
и результаты gates. Это локальное воспроизведение требует сохранённых
артефактов playground; пользовательский исходник `buhmfo` не используется.
