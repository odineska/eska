# T145–T148 — Глобальные библиотеки: анализ, загрузка и сборка

Задачи добавлены по запросу от **2026-10-27** и уточнены **2026-10-31**.
Они составляют первые три этапа назначенного пула:
**T145 → T147 → T148 → T149 → T150 → T151**.
T145 вводит одну библиотеку по имени, T147 — сборку с этой библиотекой,
T148 — подключение БСП командой `eska add <library>`.
Устанавливаемые ESKA библиотеки хранятся в пользовательском `~/.eska/lib`.
T146 имеет статус `DEFERRED`: несколько библиотек в одном контексте сейчас
не требуются и ждут отдельного решения.
Для незавершённых задач этот документ описывает целевой контракт.
Применяются общие [правила реализации](working-agreement.md).

## Исходное состояние

Для отдельной обработки, отчёта или расширения внешняя основная конфигурация
подключается через `[analysis.configuration].source`. В workspace та же роль
задаётся через `workspace.members.<application>.configuration = { source = ... }`.
Ссылка ведёт к Designer XML, участвует в анализе и не становится рабочим member.
[Действующий контракт контекста](../application-context.md) и
[генерация bsl-analyzer.toml](../analyzer-configuration.md) остаются исходной основой.

Глобальный конфиг содержит настройки сборки и каталог `[libraries.<name>]`.
Загрузчик и транзакционное редактирование находятся в `eska-project-core::config::global`,
общая диагностика — в `eska-presentation`. Ссылка `configuration.library`,
разрешение для CLI/Metadata API, selective fingerprints и наблюдение за глобальным
файлом в Explorer реализованы в T145. Нативная приёмка на Linux ARM64 подтвердила
смену пути и восстановление без файла/каталога с сохранением dirty-буфера.
Генератор анализатора записывает один `source.root`. В проверенном контракте
bsl-analyzer 0.4.0 нет списка самостоятельных библиотек.

Сборщик принимает готовый `.cf` через разовый CLI `--base-configuration`.
T147 добавляет автоматический выбор той же ссылки из `eska.toml` для EPF/ERF
и native-подготовку CF из XML. Без ссылки сохраняется пустая служебная ИБ.
[Выбор для каждого объекта](../../crates/eska-build/src/cli/commands/build/reference.rs)
и [подготовка служебной ИБ](../../crates/eska-build-runtime/src/build/execute.rs).

Действующий [`eska new --from`](../../crates/eska-project/src/onboarding/new/from.rs)
распаковывает локальный файл 1С; Git URL не поддерживается. Отдельный
[`eska clone`](../../crates/eska-vcs/src/project/clone.rs) использует `gix`,
но после checkout требует уже существующий проект ESKA. Для T148 нужно
переиспользовать этот transport и существующие правила инициализации:
новая команда `eska add` подключает библиотеку к существующему внешнему проекту.

## T145 — Одна глобальная библиотека

**Статус:** `DONE` — 2026-10-31.
**Зависит от:** T83, T84, T90, T92, T93 — выполнены.
**Владелец:** ESKA — глобальный конфиг, разрешение ссылки и контекст;
Explorer — отображение ошибок и обновление языковой сессии по контракту ESKA.

### Результат и формат

Путь к библиотеке задаётся один раз на машине. Проекты и приложения workspace
выбирают библиотеку по имени. В каталоге допускается несколько записей,
например `ssl_3_1` и `ssl_3_2`, но один контекст использует **ровно одну выбранную
запись**. Наличие других записей не подключает их к анализу.

Управляемая установка T148 использует `~/.eska/lib/<name>` относительно
домашнего каталога текущего пользователя; на Windows — `.eska/lib` в его профиле.
Например, репозиторий БСП 3.1 находится в `~/.eska/lib/ssl_3_1`,
Designer XML — в `~/.eska/lib/ssl_3_1/src/cf`. Путь вычисляется средствами ОС,
без фиксированного абсолютного пути. Глобальный каталог также может ссылаться
на уже существующую пользовательскую выгрузку; регистрация не переносит её.

Глобальный `config.toml` — пример расположения исходников:

```toml
[libraries.ssl_3_1]
source = "/data/libraries/ssl_3_1/src/cf"

[libraries.ssl_3_2]
source = "/data/libraries/ssl_3_2/src/cf"
```

Отдельная внешняя обработка, отчёт или расширение:

```toml
[analysis.configuration]
library = "ssl_3_1"
```

Приложение workspace с внешними объектами и расширением:

```toml
[workspace.members.tools]
configuration = { library = "ssl_3_1" }
external_objects = ["src/my-processing", "src/my-report"]
extensions = [{ path = "src/my-extension" }]
```

На другой машине то же имя регистрируется со своим путём. Проектный manifest
остаётся переносимым. Имя является точной ссылкой на запись каталога, а не
диапазоном версий; для конкретного выпуска можно использовать имя вроде
`ssl_3_1_11_466`. Автоматический выбор «последней» версии не входит в задачу.

### Границы реализации

- Сохранить прямую ссылку `configuration = { source = ... }` для явного пути.
  `source` и `library` взаимоисключающие; пустое имя, оба поля или отсутствие
  обоих полей в объявленной ссылке — структурированная ошибка.
- Загружать каталог из существующего глобального конфига с учётом
  `ESKA_CONFIG_DIR`. Относительный глобальный `source` разрешать относительно
  каталога этого конфига; прямой проектный `source` — относительно manifest.
  Существующие команды инициализации и редактирования глобального конфига
  принимают новый раздел и сохраняют настройки `[build]`.
- Разрешение имени принадлежит общему слою ESKA. `eska-project` и `eska-check`
  не получают зависимость от runtime сборки ради чтения конфига; размещение
  общего загрузчика определить по текущим потребителям без обязательного
  создания нового crate. TypeScript не читает каталог и manifest самостоятельно.
- Проверять выбранную запись, доступность Designer XML и допустимость внешней
  ссылки по действующим правилам. Неизвестное имя, отсутствующий конфиг/каталог
  или неподходящая выгрузка дают ошибку с именем библиотеки и местом настройки;
  частичный контекст не выдаётся за успешный. Отсутствие глобального файла не
  мешает проектам без ссылки `library`.
- На этапе T145 библиотека остаётся контекстом анализа только для чтения.
  Её исходники не становятся workspace member, объектом сборки, VCS-операций
  или массового fmt. Использование этих исходников сборщиком относится к T147.
  В `bsl-analyzer.toml` записывается разрешённый путь в существующий `source.root`;
  новый контракт или выпуск bsl-analyzer для T145 не требуются.
- Выбранное имя, разрешённый путь и относящиеся к ним глобальные настройки
  участвуют в проверке актуальности контекста и производного конфига. Изменение
  выбранной записи обнаруживается CLI и работающим проектным сервером; обновление
  анализатора соблюдает действующие правила владения конфигом и языковой сессией,
  сохраняет пользовательские настройки диагностик и несохранённые документы.
  Изменение посторонней библиотеки не переключает активный контекст.
- Проверить round-trip manifest и существующие `new`/`init` при добавлении
  расширения или внешнего объекта: ссылка приложения остаётся в одном месте,
  абсолютный машинный путь не дублируется в дочерних проектах.

В T145 не входят массив библиотек, объединение нескольких конфигураций,
транзитивные зависимости, скачивание исходников, менеджер версий или новые
команды управления пакетами. Автоматическая подготовка базы для EPF/ERF вынесена
в T147, загрузка библиотеки из Git — в T148; несколько библиотек остаются
отдельной T146.

### Приёмка

1. На собственных fixtures проверить отдельные EPF, ERF и расширение, а также
   workspace с общей библиотекой. Ссылка по имени и эквивалентный прямой путь
   дают одинаковые исходники и семантический контекст анализатора.
2. Две независимые глобальные настройки отображают одно имя в разные локальные
   пути без изменения проектного manifest; невыбранные записи не добавляют исходники.
3. Проверить неизвестное имя, пустую/двойную ссылку, отсутствующий файл и каталог,
   неверный XML, относительные пути, пробелы/Unicode, пересечение с рабочим member.
   Ошибки имеют ru/en-представление и стабильные machine-readable коды.
4. Изменить выбранный глобальный путь: CLI обнаруживает устаревший конфиг,
   Explorer обновляет контекст и языковую сессию без ручного изменения
   `bsl-analyzer.toml`. Настройки вроде `LineLength = false` сохраняются;
   проверяются dirty-буферы и действующее владение конфигом несколькими окнами.
5. Установленный совместимый bsl-analyzer принимает сгенерированный конфиг;
   реальная диагностика и переход в модуль выбранной библиотеки подтверждены.
   На этапе T145 проверить, что build/VCS/fmt не захватывают её исходники.
6. Выполнить обязательные проверки изменённого кода и обновить пользовательское
   руководство, схему конфигурации и контракт компонентов, если он изменится.

### Проверенные результаты T145

Обязательные Rust-проверки прошли: 1349 тестов, 18 ignored. В Explorer прошли
typecheck, compile и 405 тестов, 11 skipped. Реальная языковая приёмка:
Linux ARM64, VS Code 1.144.0, bsl-analyzer 0.4.2, собранный из upstream tag.
Проверены definition в выбранной библиотеке, диагностика dirty BSL, сохранение
`LineLength=false`, отсутствие перезапуска при посторонней записи каталога,
смена выбранного пути и восстановление при первом запуске без настроек.
Два отдельных project-сервера подтвердили запрет перезаписи до release обоих lease.
Ручные проверки fmt, VCS и build dry-run не захватывают библиотеку как рабочий проект.

Windows native здесь не запускалась. Старый native-сценарий прямой ссылки
проходит definition, но останавливается на немедленном изменении `eska.toml`;
тот же сбой воспроизведён на исходном Explorer `b4a1512`. Его нужно учесть в T148
при обновлении manifest через `eska add`. Сам глобальный файл T145 наблюдается
независимо, включая отсутствие родительского каталога.
[Итоги и ограничения](../measurements/t145-libraries.json).

## T147 — Сборка EPF/ERF с библиотекой из eska.toml

**Статус:** `DONE` — 2026-10-31.
**Зависит от:** T145; T28 и T94 — выполнены.
**Владелец:** ESKA — общий resolver контекста и native build runtime;
Explorer использует тот же план сборки без собственной логики выбора библиотеки.

### Реализация

1. Подготовлен общий снимок XML-исходников. Существующее копирование и hashing
   build manifest выделены в `eska-build-runtime::build::source_snapshot`;
   прежние snapshot ID, JSON и ошибки сохранены. Полный Rust-набор проходит.
2. Добавлена native-подготовка базового CF с проверкой актуальности по точным
   байтам исходников и платформе. Сохранены блокировки, отмена и предыдущие
   артефакты при ошибке; подготовка остаётся вне исходников библиотеки.
3. Выбор основы для каждого EPF/ERF подключён к обоим CLI, dry-run и manifest;
   реальные сборки и повторное использование проверены установленной 1С.

Runtime уже принимает типизированную основу `BaseConfiguration::DesignerXml` и
готовит CF настоящими командами `ibcmd` из собственного снимка исходников.
CF и его проверяемый checksum сохраняются под блокировкой служебной ИБ;
изменение байтов XML/BSL, выбранного пути/имени или версии платформы обновляет
подготовку. Пересоздание изменяемой ИБ сохраняет проверенный CF, `clean` удаляет
оба. Вывод внутрь исходников основы отклоняется до создания файлов.

Оба CLI выбирают ссылку из manifest через общий `resolve_project_reference`.
Resolver учитывает владельца каждого member, не читает XML других приложений
и не требует глобальных настроек при отсутствии ссылки. Явный CF обходит выбор
библиотеки; dry-run и ошибки содержат координаты выбранной настройки.
Реальная приёмка EPF/ERF прошла. Кеш принадлежит одному потребителю;
общий кеш нескольких проектов — T148.

### Результат

Основной пользовательский сценарий — запустить в каталоге проекта одну команду:

```sh
eska build
```

ESKA определяет тип артефакта, XML-исходники, версию платформы, выходной каталог
и базовый контекст по настройкам проекта/workspace. Для выходного каталога
сохраняется существующее значение по умолчанию; версия платформы задаётся в конфиге.
Путь к библиотеке, установка платформы и runner разрешаются из глобальных
настроек и штатного поиска. Ручная подготовка `bsp.cf` и обязательные параметры
`--base-configuration`, `--recreate-infobase` или `--platform-version` не нужны.
Внешняя обработка или отчёт использует одну ссылку T145 в `eska.toml`:

```toml
[analysis.configuration]
library = "ssl_3_1"
```

В workspace используется та же ссылка `configuration = { library = "ssl_3_1" }`
у приложения, которому принадлежит внешний объект. Отдельная настройка
библиотеки или пути к CF в секции сборки не требуется.

### Границы реализации

- Запуск из каталога standalone-проекта или member workspace выбирает текущий
  проект и применяет действующее наследование настроек. Полностью настроенный
  проект собирается без дополнительных CLI-параметров. Если обязательной
  настройки не хватает или она неверна, ошибка указывает файл, поле и причину;
  штатное исправление — заполнить конфиг, а не подбирать флаги команды.
- Получать библиотеку через общий resolver T145 для каждого выбранного внешнего
  объекта. В workspace с несколькими приложениями учитывать контекст каждого
  member; не подставлять одну библиотеку всем участникам сборки.
- По Designer XML выбранной библиотеки автоматически готовить базовую
  конфигурацию и служебную ИБ средствами существующего native runtime.
  Если платформе нужен промежуточный CF, создавать его в управляемом build-каталоге.
  Пользователь не экспортирует CF вручную и не добавляет библиотеке `eska.toml`.
  Способ загрузки XML подтвердить реальной платформой; анализатор для сборки
  не требуется, действующий выбор платформы и runner сохраняется.
- Явный `--base-configuration FILE.cf` имеет приоритет как разовое переопределение
  для специальных случаев и не меняет manifest или настройки анализа.
  Обычная сборка его не требует: используется выбранная библиотека;
  если ссылки нет, сохраняется существующая сборка без базового CF.
  При ошибке разрешения объявленной библиотеки не переходить молча к пустой ИБ.
- Библиотека служит входом только для чтения. Не создавать артефакты рядом с её
  XML, не менять её исходники, Git и пользовательские ИБ. Служебные файлы должны
  оставаться в управляемой области сборки, покрытой действующими ignore-правилами.
- Переиспользование подготовленной базы учитывает выбранную библиотеку,
  фактическое содержимое её исходников и версию платформы. Изменения не оставляют
  устаревший контекст: обычный `eska build` автоматически обновляет или пересоздаёт
  служебную ИБ. Ручной `--recreate-infobase` остаётся необязательным принудительным
  действием; блокировки, отмена, очистка и сохранение предыдущего артефакта
  при ошибке сохраняют действующие гарантии.
- `eska build` и `eska-build build` используют один контракт. План `--dry-run`
  показывает выбранную библиотеку/явный CF и необходимые шаги без подготовки
  базы и записи артефактов. Для `--manifest` фиксируются фактический источник
  базового контекста и его снимок/контрольные суммы.

Scope — EPF/ERF с одной библиотекой T145. Несколько библиотек, установка расширений
в базу и изменение обычной сборки CF/CFE в эту задачу не входят.
Загрузка проекта библиотеки и переиспользование её заранее собранного результата
между разными проектами относятся к T148. T147 сохраняет работу с обычной
XML-выгрузкой, которой не нужен собственный `eska.toml`.

### Приёмка

1. На реальной платформе собрать EPF и ERF, ссылающиеся на метаданные библиотеки,
   командой ровно `eska build` в чистом окружении служебной сборки, имея только
   настроенный проект и глобальный конфиг. Проверить артефакты и сопоставить
   результат с явным CF из тех же исходников.
2. Повторить запуск без параметров для standalone и из каталога member workspace.
   Дополнительно проверить выбор `-p`, сборку `--workspace`, два приложения
   с разными библиотеками и одинаковый результат обоих CLI.
3. Проверить явное переопределение CF, отсутствие ссылки, неизвестное имя,
   недоступный/неподходящий XML и несовместимую платформу. Ошибки локализованы
   в ru/en, JSON-коды стабильны; объявленная библиотека не теряется молча.
4. Проверить повторную сборку, изменение XML/BSL библиотеки, смену её пути
   и платформы командой `eska build` без дополнительных параметров; отдельно
   проверить явный `--recreate-infobase`, отмену и конфликт блокировок.
   Исходники библиотеки и пользовательские ИБ остаются неизменными.
5. Проверить `--dry-run`, `--manifest`, очистку, игнорирование служебных файлов,
   пути с пробелами/Unicode и передачу путей выбранному runner. Реальные проверки
   платформы отделять от mock-проверок; непроверенные ОС/runner явно перечислить.
6. Обновить руководство сборки и выполнить общие проверки изменённого кода.

### Проверенные результаты T147

## T148 — Подключение БСП командой eska add

**Статус:** `IN-PROGRESS` — после завершённой T147.
**Зависит от:** T145, T147; T91, T94, T95 — выполнены.
**Владелец:** ESKA — подключение зависимости, VCS transport, глобальный каталог
и общий build runtime; Explorer использует контракт ESKA.

### План реализации

1. Добавить в VCS-компонент получение снимка `refs/heads/master` через gix:
   checkout исходников без требования `eska.toml`, точный revision в ответе,
   отказ при занятом назначении и очистка только собственного staging.
2. В общем core реализовать проверку известной библиотеки, пользовательское
   расположение `~/.eska/lib`, безопасную установку/регистрацию и привязку одной
   ссылки к выбранному EPF/ERF. CLI `eska add` делегирует project-компоненту;
   тот обращается к VCS через существующий process-контракт.
3. Подключить общий проверяемый результат CF к native runtime, сохранив
   отдельную изменяемую ИБ каждого потребителя. Проверить первоначальное
   подключение в Explorer, офлайн-повтор и реальные сборки БСП.

VCS-граница реализована: `__bridge library-checkout` получает только текущую
`master` через gix (depth 1, без других веток и тегов), возвращает точный commit
и не требует manifest. Process-тест с настоящим локальным Git-сервером проверяет
выбор `master` при default `main`, сохранность байтов и отказ без `master`.
Публичная команда `add`, установка и общий результат сборки ещё не реализованы.

### Пользовательский сценарий и источники

По уточнению от 2026-10-31 основной интерфейс — аналог `cargo add`:

```sh
cd my-report
eska add ssl_3_1
eska build
```

Команда работает в существующем проекте внешнего отчёта или обработки.
Для workspace используется общий механизм явного выбора проекта; неоднозначный
выбор не изменяет сразу несколько подпроектов. Команда записывает ссылку:

```toml
[analysis.configuration]
library = "ssl_3_1"
```

Первый scope — известные публичные репозитории БСП:
`ssl_3_1` → [1c-syntax/ssl_3_1](https://github.com/1c-syntax/ssl_3_1),
`ssl_3_2` → [1c-syntax/ssl_3_2](https://github.com/1c-syntax/ssl_3_2).
Для первоначальной установки используется именно `master` выбранного
репозитория; фактический commit фиксируется. «Актуальная версия» здесь означает
снимок `master` на момент первого подключения, а не автоматический выбор тега.
Совместимость исходников с используемой версией платформы проверяется отдельно.

### Установка и повторное подключение

- Если библиотека ещё не установлена, загрузить её в
  `~/.eska/lib/<name>` текущего пользователя, например
  `~/.eska/lib/ssl_3_1`. Корень репозитория сохраняется; исходники этих БСП
  ожидаются в `src/cf` и проверяются по Designer XML. Общие правила путей
  и глобального каталога принадлежат T145.
- Переиспользовать встроенный VCS transport `gix` и существующую инфраструктуру
  инициализации. Сохранять XML/BSL, ресурсы, лицензионные файлы и исходные
  ignore-правила. Сведения об установке содержат URL, `master` и точный commit.
- Если корректная библиотека уже установлена, проверить локальную регистрацию
  и подключить существующую копию. Сеть, fetch/pull, перезапись исходников
  и автоматическое обновление в этом пути не нужны. Повторное добавление
  той же ссылки идемпотентно и работает без сети.
- Если имя зарегистрировано на существующую пользовательскую выгрузку,
  сохранить её местоположение и локальные изменения. Занятый неизвестными
  файлами каталог, повреждённая регистрация или другая библиотека в выбранном
  проекте дают понятный конфликт; чужие файлы и `source` не заменяются молча.
- Зарегистрировать установленный источник в глобальном каталоге T145 и связать
  его с проектом библиотеки. Проверенный существующий `eska.toml` сохраняется;
  при его отсутствии создать минимальный manifest конфигурации с относительным
  `source = "src/cf"` по общим правилам. Сохранить настройки `[build]`,
  другие библиотеки и посторонние поля конфигурации.
- До изменения проекта проверить его тип, текущую ссылку и библиотеку.
  Установку публиковать из собственного staging после проверки. Ошибка сети,
  XML, записи или отмена сохраняет существующий проект и исправную установку;
  в конфиге не остаётся ссылка на частично установленную библиотеку.
- `add` подключает исходники для анализа и будущей сборки. Нативная подготовка
  CF/служебной ИБ выполняется по T147 при `eska build` и использует сохранённые
  настройки платформы. Установка БСП не выполняет полученные скрипты.
- Первая версия ограничена именованной БСП. Произвольные Git URL, изменение
  `eska new --from`, отдельные команды обновления/удаления зависимостей,
  транзитивные зависимости и удалённый реестр пакетов в этот этап не входят.

### Повторное использование сборки

- `eska build` в проекте библиотеки создаёт CF и автоматически сохраняет сведения
  о его входных данных. Для использования другими проектами не нужен ручной
  `--manifest`. Сборщик отчёта находит результат через каталог T145 и общий
  resolver, без поиска случайного `.cf` по совпадению имени файла.
- Повторные сборки одного отчёта и сборка другого отчёта с той же библиотекой
  не компилируют неизменившуюся БСП заново. Проверять содержимое исходников,
  включая локальные незакоммиченные правки, параметры и версию платформы,
  целостность результата. URL, Git HEAD или время изменения каталога сами
  по себе не доказывают актуальность. Подготовленные результаты для разных
  версий платформы и параметров разделять, не переписывая настройки библиотеки
  при сборке очередного потребителя.
- Для одного отчёта сохраняется переиспользование служебной ИБ из T147.
  Для другого отчёта отдельно измерить стоимость загрузки готового CF. Если
  именно она определяет задержку, использовать проверенную подготовленную базу
  как неизменяемую основу для отдельной ИБ потребителя. Разные сборки не работают
  с одной общей изменяемой ИБ; блокировки, публикация и очистка принадлежат ESKA.
- При изменении библиотеки/платформы или отсутствии корректного результата
  автоматически подготовить его через T147 и затем собрать отчёт. Ошибка
  подготовки не разрешает использовать устаревший результат. Сборка работает
  с локальными исходниками без загрузки обновлений из сети; смена upstream-версии
  не происходит скрыто при `eska build`.
- Артефакты и служебные данные хранятся вне XML-исходников. Очистка одного отчёта
  не удаляет общую библиотеку или результат, используемый другой сборкой.
  Удаление подготовленного результата допускает его безопасное восстановление.

### Приёмка

1. В новом проекте ERF выполнить `eska add ssl_3_1`: загрузка текущей
   `master` в пользовательский `~/.eska/lib/ssl_3_1`, проверка точного commit,
   корректная глобальная регистрация и ссылка проекта.
   В работающем Explorer проверить немедленное обновление manifest-наблюдения:
   на Linux ARM64 старый `language-reference-host.cjs` пропускает запись
   `eska.toml` сразу после старта даже до изменений Explorer для T145.
2. Подключить ту же библиотеку к EPF, затем повторить `add` в обоих проектах
   при недоступной сети. Исходники, Git revision и глобальные настройки
   сохраняются; повтор той же ссылки не переписывает manifest.
3. Проверить `ssl_3_2` по тому же контракту и на совместимой платформе.
   Отдельно проверить выбранный внешний проект workspace, неподходящий тип,
   неизвестное имя, конфликт существующей ссылки и занятую установочную папку.
4. Собрать ERF и EPF через обычный `eska build`, повторить сборку и собрать
   второй независимый потребитель. Подтвердить отсутствие повторной компиляции
   неизменившейся БСП; отдельно измерить подготовку библиотеки и сборки потребителей.
5. Проверить изменение XML/BSL без commit, смену платформы, повреждённый/удалённый
   CF, параллельные сборки, отмену, очистку и отказ записи конфигурации.
   Исправная установленная библиотека подключается и собирается без сети.
6. Проверить CLI ru/en, независимый от locale JSON, границы записи и сохранность
   пользовательских файлов. Native-проверки выполняются на совместимых ОС/платформах;
   недоступные сочетания явно отмечаются непроверенными.

Несколько записей в глобальном каталоге не подключаются совместно к одному
проекту: такая композиция остаётся отложенной T146.

## T146 — Несколько библиотек в одном контексте

**Статус:** `DEFERRED` — по решению от 2026-10-31 практической необходимости
сейчас нет; задача вне назначенного пула.
**Зависит от:** T145; согласованной модели библиотек и совместимого релиза
upstream bsl-analyzer.
**Владелец:** ESKA — декларации, разрешение источников и контекст;
bsl-analyzer — видимость символов, метаданные, типы и диагностики;
Explorer — представление результата и конфликтов.

Цель — совместно использовать несколько разных библиотек в одном приложении.
Предварительная форма для обсуждения контракта:

```toml
[analysis]
libraries = ["ssl_3_1", "exchange_2_0", "company_common"]
```

В workspace список относится к `workspace.members.<application>` рядом
с `configuration`, `extensions` и `external_objects`. Общий каталог хранит
машинные пути; схема состава задаётся один раз для выбранного контекста.
Окончательный формат определить при согласовании с анализатором, сохраняя
явное различие основной конфигурации, библиотек, расширений и внешних объектов.

До реализации определить identity и версию библиотеки, её собственный состав
и зависимости, устранение повторного подключения общего источника и поведение
при циклах. Две версии одной библиотеки проверяются в разных контекстах.
Конфликтующие одноимённые модули и объекты должны сообщать оба источника;
порядок списка не выбирает определение молча. Отдельно разобрать полные XML-выгрузки,
которые уже содержат одну и ту же БСП, и пересечение с основной конфигурацией.

Поддержка требует общего контракта анализа библиотек, а не повторной записи
`source.root` или объявления библиотек расширениями. Ядро bsl-analyzer не
форкается и не встраивается; наличие upstream PR не заменяет совместимый релиз.

Приёмка: две независимые библиотеки, общая зависимость, повтор одного источника,
конфликт определений, две версии одной библиотеки и цикл; одинаковый результат
CLI/IDE, реальные диагностики/переходы/типы, обновление одного источника без потери
происхождения символов. Текущая основная конфигурация и расширения сохраняют
свои правила видимости. Начало T146 требует отдельного выбора приоритета.
