# Статическая проверка CI

`eska-check` — самостоятельный компонент для Designer XML и полного BSL-анализа
выбранного приложения. Он не запускает `eska`, `eska-project`, IDE, Git или платформу
и не связывает ядро bsl-analyzer. Нужен опубликованный `bsl-analyzer-app`
с командами `check-config` и `analyze --format jsonl`. Номер релиза не закреплён;
версия JSONL сверяется с выбранным исполняемым файлом и записывается в отчёт.
Сам компонент собирается: `cargo build -p eska-check --locked`.

Пример для CI; `PROJECT_ROOT`, `BSL_ANALYZER` и `CHECK_REPORT` задаёт среда запуска:

```sh
target/debug/eska-check --project-dir "$PROJECT_ROOT" \
  --analyzer "$BSL_ANALYZER" --format json --report "$CHECK_REPORT"
```

`--project-dir` начинает обычный поиск `eska.toml`; по умолчанию используется cwd.
`--application` выбирает объявленное приложение. Если выбор неоднозначен,
проверка останавливается. Состав, source, зависимости и платформа берутся из
[общего контекста](application-context.md), правила — из `[tools.bsl-analyzer]`,
[пороги CI](analyzer-configuration.md#пороги-ci) — из `[tools.eska-check]`.
Пути членов приложения в аргументах pipeline повторно не перечисляются.

`--analyzer` принимает путь либо имя исполняемого файла. Относительный путь
с каталогом (например, `./tools/bsl-analyzer-app`) разрешается относительно
каталога запуска ESKA, независимо от `--project-dir`. Имя без каталога ищется
в PATH. Это правило действует также для `analyzer-config prepare`. Без явного
`--analyzer` используются
`ESKA_BSL_ANALYZER` и затем `bsl-analyzer-app` из PATH. Версия и CLI-контракт
проверяются у выбранного файла. `--timeout` — положительное число секунд на
каждый внешний процесс и чтение обоих его потоков, по умолчанию 600. Сеть и
установщик не запускаются.

Необязательная оболочка предоставляет `eska check` с теми же analysis flags,
JSON и exit codes. Она ищет `eska-check` по общим правилам компонентов;
`ESKA_CHECK_BINARY` задаёт явный executable. Общий вход удаляет только слово
`check`; анализ выполняет самостоятельный процесс. Отсутствующий компонент
даёт ненулевой статус без автоматической установки. Для минимальной CI-установки
оболочка по-прежнему не нужна. [Делегирование](component-delegation.md).

## Проверка и запись

Проверка разрешает контекст, подготавливает только принадлежащий ESKA
`bsl-analyzer.toml`, обходит объявленные XML-дескрипторы общими resolver/parser
и вызывает `analyze --format jsonl` внешнего анализатора. Производный конфиг
проверяется настоящим `check-config`, повторный запуск идемпотентен. Чужой
конфиг, ручная правка managed-файла и чужой активный контекст дают ошибку.
Миграция и переключение контекста требуют отдельного явного действия через
[проектный инструмент](analyzer-configuration.md); CI не выполняет их молча.

Ход проверки выводится в stderr: проверка структуры (`check_structure`), подготовка
анализатора (`prepare_analyzer`) и анализ модулей (`analyze_modules`). Структура
проверяется при открытии контекста и повторно перед анализом. Human-режим показывает
локализованные этапы и число обработанных модулей по умолчанию;
`ESKA_OPERATION_PROGRESS=0` отключает эти сообщения. Существующий отчёт в stdout
и файл `--report` от прогресса не меняются.

В режиме `--format json` успешный stderr по умолчанию остаётся пустым. Для JSONL
прогресса задайте `ESKA_OPERATION_PROGRESS=1`; переменная также наследуется при
вызове через `eska check`. Каждая строка имеет `schema_version: 1`,
`kind: "operation_progress"`, `event: "stage"`, `phase`, `elapsed_ms` и
`stage_elapsed_ms`. Для анализа добавляются целые `processed_modules` и
`total_modules`. Счётчик увеличивается только после проверенного уникального
события `file` анализатора; повторные и ошибочные записи не учитываются.
Вывод счётчика ограничен двумя обновлениями в секунду, первый и последний
результаты сообщаются сразу. Проценты не вычисляются. Даже равенство счётчиков
не означает успешного завершения: нужны корректный `done`, успешный exit и
проверка неизменности исходников; итог определяют отчёт и exit code.

Полный набор BSL-файлов сверяется с событиями `start/file/done`, включая чистые
файлы. Начиная с bsl-analyzer 0.4.4 файлы с суффиксом `*.Queries.bsl`
считаются выгрузками запросов и пропускаются. Регистр суффикса произвольный.
В более ранних версиях эти файлы входят в проверку. Обычный файл `Queries.bsl`
и модули в каталоге `Queries` учитываются в обеих версиях.

Ошибка файла, ненулевой `failed_files`, потеря/дубликат события, неверная
версия, повреждение JSONL, обратные диапазоны, несогласованные счётчики
и ненулевой exit после `done` означают незавершённую проверку. Пустой набор
тоже не считается успехом. При тайм-ауте или отмене ESKA завершает прямой процесс
анализатора, если он ещё работает, и забирает его статус. Потомки остаются под
управлением анализатора или его обёртки. Если потомок унаследовал канал вывода,
ESKA возвращает ошибку сразу после тайм-аута или отмены, а заблокированное
чтение заканчивается, когда в канале появятся данные или он закроется.

`analysis.diff_base` и непустой `analysis.ignored_authors` отклоняются как
частичный анализ; флагов changed-only нет. Литеральные `source.exclude`
применяются в значении upstream, относительно корня конфига. Symlink,
непредставимые UTF-8 пути и выходящие за root исключения отклоняются.
При наследовании настроек через `extends` эти правила учитывают значения из
родительских TOML и локальные переопределения. Изменение родительского файла
во время анализа прерывает проверку, даже если исходный BSL остался прежним.
Если `done.baseline` присутствует, для завершения нужны `complete: true` и
состояние `disabled` или `full`. Старые потоки могут опускать это поле.
Порог применяется к эффективным диагностикам после выбранной upstream-политики.

Общий lease запрещает конкурентную замену контекста. Перед выдачей отчёта
повторно проверяются манифесты, конфиг и байты XML/BSL, а также добавление
и удаление файлов. Для модуля обычной формы учитываются содержимое
`Ext/Form/Form.json` и его актуальность. Анализатор считает описание устаревшим,
если `Ext/Form.bin` записан позже JSON. Изменение только этого соотношения также
меняет `input_fingerprint`. Изменение входов во время анализа завершает его
с ошибкой.
ESKA не создаёт дополнительный BSL-индекс.

Структурная проверка не заменяет компиляцию платформой и не проверяет
непрозрачные данные форм. Отсутствующий, повреждённый или неподдерживаемый
объявленный дескриптор останавливает её. Размер одного JSONL-события ограничен
8 MiB, всего потока — 512 MiB; превышение не выдаётся за частичный успех.
На `buhmfo` опубликованный анализатор выдаёт 380 241 135 байт для 23 162 файлов
и 1 362 653 диагностик; прежний общий предел 256 MiB отвергал этот полный поток.
Предел одного события и обязательные проверки `done`/счётчиков сохранены.

## Результат

`--format human|json` выбирает stdout; по умолчанию human. `--lang ru|en`
меняет интерфейс и справку. Код возврата отделяет диагностики от сбоя инструмента:

| Exit | Результат | `complete` |
|---|---|---|
| 0 | `passed` | true |
| 1 | `threshold_exceeded` | true |
| 2 | Ошибка аргументов clap | JSON не обещается |
| 3 | `incomplete` | false |
| 130 | `cancelled` | false |

JSON schema 1 имеет `kind: "check"`. Завершённый отчёт содержит `scope: "full"`,
фактический `context` с root/application/limited_context, версию анализатора,
вид структурной проверки, число объектов, `counts`, `policy`,
`input_fingerprint` и `files`. Каждый файл содержит обратимый `{value,encoding}`
путь и `diagnostics` с code/message/severity. В JSON строки и столбцы нумеруются
с нуля, столбцы считаются в кодовых точках Unicode, конец диапазона исключён.
Если событие `start` объявляет другую базу строк или столбцов, проверка завершается
с ошибкой `invalid_stream`. В старых потоках действует неявная нулевая база.
Human-вывод показывает строки и столбцы с единицы. Ошибка содержит
`error: {code,data}` и не содержит неполного массива диагностик.

Опубликованный JSONL 0.4.0 также выдаёт `Blocker`, `Critical` и `Major`.
Как и [LSP upstream](https://github.com/itrous/bsl-analyzer/blob/bdb221307b73f83f9401558e8013f3a1667969b9/crates/bsl-analyzer/src/lsp/to_proto.rs#L44),
отчёт нормализует их в `Error`: они увеличивают `counts.errors` и участвуют
в пороге ошибок. Публичные четыре категории и схема отчёта сохраняются;
неизвестный уровень по-прежнему означает незавершённый результат.
Реальная проверка `CommonModuleInvalidType` с уровнем `Major` теперь даёт
полный отчёт и превышение порога ошибок вместо `invalid_stream`;
[проверки CLI и полного workspace](measurements/t89-severity.json).

Времена не входят в отчёт. CLI locale не меняет JSON, выбор контекста или
правила. Язык upstream-сообщений остаётся настройкой `[tools.bsl-analyzer.output]`.
Локализованные объяснения и upstream-логи ошибок идут отдельно на stderr.

`--report` сохраняет тот же JSON независимо от формата stdout. Родительский
каталог должен существовать; файл должен быть новым и находиться вне source
выбранного контекста. Существующий файл сохраняется, отказ происходит до
подготовки конфига и анализа. Ошибка начального resolve ещё не создаёт файл
отчёта; JSON ошибки доступен на stdout. Ошибка записи даёт exit 3. При аварийном
прерывании записи файл может быть неполным; потребитель проверяет и JSON,
и exit code. XML/BSL и исходный пользовательский конфиг не перезаписываются.

JSON записывается потоково после проверки полноты анализа. CLI не создаёт
второе дерево всех диагностик и буфер всего JSON; текстовый вывод без `--report`
вообще не сериализует JSON. Сами проверенные результаты анализа остаются в памяти.
В синтетической проверке 2 000 файлов / 200 000 диагностик peak RSS снизился
с 425 до 43 MiB, JSON-вывод — с 0,84 до 0,49 с (медианы трёх запусков).
Значения JSON и байты текстового вывода совпали; это измерение сериализации,
а не реального анализа BSL: [результаты](measurements/review-report-streaming.json).

Описание диапазонов и состава модулей для актуализированного адаптера приведено
в документации upstream. [Координаты JSONL](https://github.com/itrous/bsl-analyzer/blob/v0.4.6/docs/CI_REPORTERS.md)
и [классификация файлов](https://github.com/itrous/bsl-analyzer/blob/v0.4.6/crates/project-model/src/file_role.rs).

## Проверка T93

На Linux x86_64 прошли полный workspace fmt/check/strict Clippy/test/Rustdoc:
798 Rust-тестов passed, 12 ignored. Три явных теста с настоящим опубликованным
анализатором прошли отдельно: четыре standalone-типа, приложение с базой,
пятью расширениями и EPF, CLI с пустым PATH и побайтно одинаковым JSON ru/en.

Process-тесты покрывают нулевой exit при неполном потоке, `failed_files`,
ошибки файлов, неверную версию, ненулевой exit после `done`, timeout и SIGINT,
политику порогов, сохранность пользовательского конфига и отчёта, BOM/CRLF,
локализацию human и JSON. После timeout/отмены проверено отсутствие owned PID.
Нормальный граф зависимостей `eska-check` не содержит полной ESKA,
`eska-project`, `gix`, platform runtime, HTTP/updater или BSL-движка.

Промежуточные полные прогоны получили ошибки Git preflight при параллельных
sandbox-командах: внутри sandbox у playground виден пустой `.git`, на хосте
его нет. Финальный полный прогон одним запуском вне sandbox прошёл без
параллельных файловых команд; код VCS не менялся. Windows/macOS, Remote
и большое измерение `buhmfo` ожидают приёмки T89.

## Проверка 8.5.4 на Linux ARM64

25 ноября 2026 года в отдельной копии демонстрационной выгрузки Designer XML
8.5.4.2072 проверен настоящий локально собранный `bsl-analyzer-app` 0.4.6.
`analyzer-config prepare` и `check-config` прошли. `analyze --format jsonl`
завершился с exit 0: 139 событий `file`, `failed_files=0`, 1853 диагностики.
`eska-check` вернул `complete=true`, проверил 389 объявленных XML-объектов и
139 BSL-файлов. Exit 1 с `status=threshold_exceeded` соответствует найденным
70 ошибкам при пороге `max_errors=0`; остальные результаты — 633 предупреждения,
440 информационных сообщений и 710 подсказок. Это успешное завершение анализа,
а не подтверждение отсутствия ошибок в демонстрационной конфигурации.

Повтор с явно указанной штатной HBK 8.5.4 прошёл с теми же счётчиками. Внешняя
справка доступна, однако анализатор 0.4.6 предупреждает, что его отдельный
каталог глобальных имён 8.3.27 не покрывает target 8.5.4, и подавляет диагностики
отсутствующих глобальных имён. Полнота проверки новых API 8.5.4 этим запуском
не подтверждена; требуется поддержка соответствующего каталога upstream.

На запросе из общего модуля `Пользователи` MCP-инструмент `query` с действием `validate` после готовности
метаданных вернул `backend=workspace_semantics`, `metadata_checked=true`,
`status=checked_against_metadata`, без замечаний. Контракт `query` этой сборки
содержит `validate`, `execute`, `schema`, но не публичную семантическую модель
запроса. Отдельный синтаксический `query/constructorModel` ESKA вернул одну
инструкцию и одну область без issues. Он не является моделью типов upstream.

BSL, встроенный BSL-запрос, отдельный SDBL и запрос в XML СКД прошли
форматирование с последующим идемпотентным `--check`. JSON предварительной
проверки BSL и встроенного запроса совпал для `ru` и `en`. Эти операции
не запускали код в 1С и не требовали анализатора. Evidence находится в
собственном `analyzer-854-xl3olm27/evidence` соседнего playground, включая
JSONL, отчёты CLI, ответы RPC/MCP и исходные байты до форматирования.

Локальная сборка bsl-analyzer-app 0.4.7 на том же стенде прошла `check-config`
и анализ 139 BSL-файлов с 1853 диагностиками и `failed_files=0`. LSP открыл
определение `Пользователи.ТекущийПользователь()` и показал описание и сигнатуру
новой глобальной функции из HBK. Подсказка имени этой функции по префиксу
осталась пустой. В тегах 0.4.6 и 0.4.7 используется один и тот же встроенный
каталог 8.3.27. Обе версии сообщают о подавлении диагностики отсутствующих
глобальных имён при target 8.5.4. [Выпуск 0.4.7](https://github.com/itrous/bsl-analyzer/releases/tag/v0.4.7).

В VS Code 1.144.0 Explorer открыл запрос общего модуля `Пользователи` из BSL,
показал конструктор и сохранил правку `ПЕРВЫЕ 1` → `ПЕРВЫЕ 2` в исходном
модуле. Соседний код сохранился побайтно. Оба варианта исполнены с тем же
параметром текущего пользователя в серверном общем модуле тестовой файловой
базы на 8.5.4.2072. Каждый вернул одну строку с колонками `Ссылка`, `Код` и
`Наименование`. Отчёты сохранены в отдельных каталогах соседнего playground
`analyzer-047-2gu2rckn`, `query-377-pdwkcaol` и `query-runtime-377-nh_3xsp6`.

С bsl-analyzer-app 0.4.7 явный target анализа имел приоритет над версией
сборки. Генератор принял другой полный номер `8.5.4.9999` и отдельно сохранил
`CompatibilityMode=Version8_5_1` из XML. При отсутствии версии сборки и
явного target генератор передал режим совместимости без целевой версии.
`eska check` на ru-RU и en-US завершился с кодом 1 и одинаковым JSON с
`complete=true` и прежними счётчиками диагностик.

В живом Explorer с 0.4.7 анализатор показал две ошибки синтаксиса в
несохранённом BSL демобазы. После исправления ошибки исчезли, а байты на
диске сохранились. Форматирование BSL и встроенного текста запроса
применило ожидаемые планы. Повторный `--check` завершился с кодом 0.
При форматировании запроса байты соседнего кода не изменились. Сводки
находятся в соседнем playground `acceptance-377-yhdryo73`.
