# Запуск и отладка 1С из Explorer

ESKA запускает клиент 1С и подключает отладчик прямо из VS Code / VSCodium.
Собственный `eska-debug` написан на Rust, общается с IDE по DAP, а с сервером
отладки платформы `dbgs` — по HTTP. Нативный TCP-режим
отладки 1С не поддерживается.

## Подготовить проект

1. Обновите Explorer и инструменты ESKA. Команда **Обновить все компоненты ESKA и BSL Analyzer**
   устанавливает `eska-debug` и при обновлении старого полного комплекта.
   Перед обновлением завершите активные сессии отладки. Для нестандартной
   установки задайте `eska.explorer.debugExecutable`.
2. Откройте корень проекта с `eska.toml`. В дереве ESKA нажмите правой кнопкой
   на **Настройки проекта** и выберите **Настроить проект**.
3. В разделе **Запуск и отладка** окна настроек заполните профиль `test` или `prod`. Укажите
   тип и адрес базы, среду запуска, платформу и параметры HTTP-отладки.
   **Из списка 1С…** показывает базы из списков запуска на хосте расширения и в
   Distrobox. Используется контейнер текущего черновика профиля или контейнер из
   общих настроек ESKA. Возле базы виден её источник. Если один список
   недоступен, базы из второго списка можно выбрать. Выбор заполняет реквизиты
   базы в черновике профиля. Для поиска в обоих источниках нужна версия
   `eska-debug` с [режимом `--include-distrobox`](eska-debug-standalone.md#базы-хоста-и-distrobox).
   Переключение профилей сохраняет отдельные черновики до закрытия вкладки.
   **Сохранить профиль** и **Отменить изменения** действуют на открытый профиль.
   Если снять флажок **Настроить этот профиль**, сохранение удалит его локальную запись.
4. Проверьте исключение `.eska/settings_local.toml` из Git. Этот файл принадлежит
   конкретному проекту; адреса баз не нужно переносить в общий `eska.toml`.
   В поле пароля указывается имя переменной окружения.

Команды доступны в секции **ESKA: запуск 1С** стандартной панели VS Code
**Запуск и отладка**: запуск тестовой базы, запуск с отладкой, подключение,
обновление, обновление с запуском и обновление с отладкой. Если подходящих
проектов несколько, команда предлагает выбрать проект.
По правой кнопке на **Настройки проекта** доступно только **Настроить проект**.

**Проверить настройки** использует текущие значения открытого профиля через
`eska-build probe --stdin`. Команда проверяет наличие тонкого клиента, файл
базы или доступность настроенных TCP-адресов. Проверка не сохраняет черновик
и не открывает сеанс 1С. Для запуска встроенного сервера отладки проверяется
наличие `dbgs` в выбранной среде.

Клиент может запускаться локально или через Distrobox. База может быть файловой,
автономной или кластерной; её адрес и адрес `debug.url` сервера отладки независимы.
Для удалённой базы, в том числе через VPN, укажите доступный HTTP-адрес `dbgs`.
Это подключение к уже настроенному серверу; ESKA не развёртывает удалённую 1С.

Для локальной файловой базы `debug.managed = true` запускает собственный `dbgs`
на `127.0.0.1` со свободным портом. Адаптер завершает этот сервер при отключении.
Для внешнего сервера задайте `debug.url`.

В блоке **Отладка** показаны флажки типов предметов. Стандартный набор
включает клиент и серверный контекст. Чтобы задать свой набор, включите
настройку типов и отметьте нужные предметы. Пустой собственный набор
отключает автоподключение. Сохранённые параметры `test` и `prod` независимы.

## Запустить или подключиться

| Действие Explorer | Результат |
| --- | --- |
| **Запустить тестовую базу** | Обычный запуск клиента по профилю `test` |
| **Запустить 1С с отладкой** | Выбор `test`/`prod`, подключение отладчика и запуск клиента |
| **Подключиться к серверу отладки 1С** | Выбор профиля и подключение к существующему предмету |
| **Выбрать предмет отладки 1С** | Выбор нужного предмета из доступных в текущей сессии |
| **Обновить тестовую базу** | Preview и подтверждённое применение исходников в `test` |
| **Применить и запустить** | Применение в `test`, затем обычный запуск клиента |
| **Применить и запустить с отладкой** | Применение в `test`, затем запуск с отладчиком |

Для запуска и отладки `test` должен быть настроен соответствующий профиль.
Для отладки `prod` профиль `test` не обязателен. Перед `prod` проверяются
исходники относительно основной ветки выбранного Git-flow; при расхождении
действие выбирает разработчик. Соответствие этой ветки реальному коду на сервере
остаётся на контроле разработчика.

Команды обновления конфигурации доступны только для `test`. Частичное применение
поддерживает определённые изменения существующих BSL, свойств и макетов, а также
некоторые структурные изменения. Неподдержанные изменения требуют отдельного
подтверждения полного импорта; универсальная частичная загрузка пока не заявляется.
Поддержаны файловая и автономная база; административное обновление удалённого
сервера и кластерной базы в этот сценарий не входит.
[Точные границы частичного применения](1c-http-debug.md#что-ещё-отсутствует-или-требует-доработки).

При первом обновлении основной конфигурации существующей файловой базы ESKA
может создать локальный снимок чтением базы. Для этого инструмент выгружает
применённую конфигурацию, сравнивает её с основной конфигурацией и повторно
проверяет поколение. Импорт XML и обновление базы при такой сверке не выполняются.
Поэтому проект из того же `.cf` или свежая выгрузка Конфигуратора в `src`
не требуют полного импорта только ради создания снимка. Если исходники
действительно отличаются, в предпросмотр попадают их отличия от базы.

Первичная сверка большой конфигурации может занять несколько минут.
Explorer показывает ход операции и позволяет её отменить. Последующие
обновления используют сохранённый снимок. Неприменённые изменения
Конфигуратора, недоступное чтение базы, повреждённый снимок и незавершённое
применение не обходят существующие проверки и подтверждение полного импорта.
Автоматическое создание снимка чтением пока не распространяется на расширения
и автономный сервер.

Перед подтверждением обновления Explorer открывает отдельную вкладку с полным
прокручиваемым списком изменений, без обрезания по количеству файлов. Объекты
и модули показаны в обозначениях `eska diff`. Закрытие вкладки, Escape и отмена
не применяют изменения. Если во время просмотра появились несохранённые правки,
обновление останавливается; сохранённые изменения повторно проверяет backend
по токену подтверждения.

После подтверждения полного импорта (`--initialize` и токен из плана)
ESKA вызывает `ibcmd config apply --force`. Подтверждение этого плана
охватывает обновление схемы тестовой базы, включая изменение режима
динамической реструктуризации. Частичный импорт выполняется с обычными
проверками платформы при обновлении базы.

### Как следить за реструктуризацией

[Скринкаст обновления справочника «Товары» на платформе 8.5.4.2072](https://odineska.tech/eska/docs/#demo-apply).

Во время обновления тестовой базы откройте уведомление Explorer. В нём видны
текущий компонент приложения, этап, время операции и время на этапе. Историю
смены этапов можно просмотреть в **Вывод → ESKA Operations**. Те же сведения
появляются в терминале при обычном запуске `eska-build apply`.

При переходе от импорта к применению ESKA сразу показывает новый этап. Затем
она читает сообщения работающей 1С. Например, после изменения длины
наименования справочника 1С сообщила об обработке структуры базы, затем
назвала конкретный справочник. Следом появились сообщения о принятии изменений
и создании поколения. Порядок и набор сообщений зависят от операции и версии
платформы. После завершения применения видны выполняемые проверки: чтение
поколения, расчёт контрольных сумм основной конфигурации и конфигурации базы.

При длительной тишине CLI обновляет время примерно раз в 15 секунд. В Explorer
часы идут каждую секунду. По времени с последнего сообщения видно, как давно
платформа отвечала. Для файловой базы во время работы `ibcmd` ESKA также
отслеживает размер и время изменения файла `1Cv8.1CD`.
Для этого достаточно прочитать атрибуты файла. Когда файл изменился, появляется
отдельная отметка, даже если платформа ничего нового не вывела.

Число сообщений об объектах относится к текущему этапу. Один и тот же объект
может встретиться несколько раз. При потоке сообщений ESKA обновляет последний
объект и счётчики порциями. В проверенных сценариях на 8.5.4.2072 и 8.3.27.2342
платформа не сообщила ни общего объёма работы, ни процента. Если долго нет
сообщений и наблюдаемых изменений файла, определить причину паузы по этим
сигналам невозможно. Для автономной базы доступен только вывод платформы.

При полном импорте основной конфигурации в файловую базу на 8.5.4 и новее
ESKA использует нативный `checksum`, если он доступен. Когда поколение в
журнале `apply` отличается от `generation-id`, ESKA сохраняет фактический
результат `generation-id` после сверки контрольных сумм импортированной,
основной и применённой конфигураций и повторного чтения поколения.
Если расхождение поколений не удалось подтвердить контрольными суммами
или поколение изменилось во время сверки, команда возвращает `stale_preview`.
ESKA сохраняет предыдущий снимок и помечает применение как незавершённое
для повторной проверки.

JSON-ответы `eska-build apply` дополнены необязательным полем `display`.
Для одного проекта это словарь точных путей из плана с подписями
`{"ru-RU":{"label":"…","group":"…"},"en-US":{"label":"…","group":"…"}}`.
В предпросмотре приложения внешний словарь содержит имена компонентов.
Для неизвестного формата файла `label` сохраняет путь, а `group` равен `null`.
Обе локали передаются независимо от `--lang`; поле предназначено только для
отображения и не изменяет состав плана или его подтверждение. Без `display`
клиент показывает исходные пути.

На Windows список частичного импорта передаётся платформе Unicode-аргументами:
имена объектов на кириллице не зависят от кодировки стандартного ввода.
Если список превышает безопасный размер командной строки, предпросмотр
требует отдельного подтверждения полного импорта.

## Работать на точке останова

- Поставьте точку в BSL. Поддержаны условия, счётчики срабатываний, логпоинты
  и остановка по ошибкам с фильтром текста сообщения.
- Используйте Continue, Pause, Step Into, Step Over и Step Out. Стек открывает
  исходник соответствующего модуля конфигурации или расширения.
- Смотрите локальные переменные, Watch и значения при наведении на выражение.
  В Debug Console можно вводить свои выражения BSL в выбранном кадре стека.
- Раскрывайте результат и вложенные значения. Коллекции читаются порциями;
  раскрытие результата Evaluate повторно не выполняет исходное выражение.
- **Set Value** принимает выражение BSL для доступной переменной, свойства
  или индексированного элемента; возможность присваивания определяет платформа.
- Выбирайте предметы и типы автоподключения для текущей сессии.

Evaluate и Set Value доступны и в `prod`. Выражения выполняются в настоящей
сессии 1С и могут иметь побочные эффекты. Отмена ожидания не откатывает уже
выполненный код. После продолжения выполнения прежние ссылки на значения
и кадры перестают быть действительными.

## Внешние обработки и отдельный адаптер

Для проекта типа `processing` укажите собранный EPF в локальном профиле.
Рядом нужен манифест сборки: адаптер сверяет артефакт и исходники, а при запуске
открывает приватную копию EPF через `/Execute`. Подключение к уже загруженной
обработке использует её полный `debug_url`.
[Настройка EPF и ограничения](1c-http-debug.md#epf-в-проекте-explorer).

Можно использовать отладчик через Explorer либо как самостоятельный DAP-адаптер.
Отдельный ZIP `eska-debug-<version>-<target>.zip` опубликован в
[GitHub Releases](https://github.com/odineska/eska/releases/latest);
альтернативная установка — `cargo install --locked eska-debug`.
Самостоятельный вход — `eska-debug standalone`, без проекта ESKA и Explorer.
Нужен DAP-клиент; для VS Code есть минимальный декларативный пример расширения.
[Инструкция standalone](eska-debug-standalone.md).

[HTTP-контракт, проверенные сценарии и ограничения](1c-http-debug.md) ·
[Локальные профили и CLI](cli-reference.md#command-eska-project-settings-local).

## Проверка 8.5.4 на Linux ARM64

25 ноября 2026 года в отдельном синтетическом проекте и собственной файловой
базе через Distrobox проверена платформа 8.5.4.2072. `eska-build apply`
прошёл полный импорт с `--initialize`, затем частичное изменение существующего
общего BSL-модуля. Повторы после обеих операций вернули `mode=unchanged`,
`status=up_to_date`, без confirmation и pending apply. Частичный план включал
только изменённый `CommonModules/PatchProbe/Ext/Module.bsl`. Изменение исходника
после preview отклонено с `stale_preview`. Обратная выгрузка базы подтвердила
новое тело `Return 3` и сохранение текста несвязанного модуля приложения.
В той же базе установленное расширение прошло `apply --initialize` и повтор
без изменений. UUID расширения и поколение основной конфигурации сохранились.

На чистой файловой базе с интерфейсом 8.5 подтверждённый полный импорт
прошёл с динамической реструктуризацией. Поколение в журнале `apply`
отличалось от результата `generation-id`. После сверки контрольных сумм
ESKA сохранил фактическое поколение, а следующий preview вернул `unchanged`
без ожидающего применения. Отдельный импорт изменённой конфигурации через
`ibcmd` привёл к `baseline_changed` при неизменных исходниках ESKA.

`probe` вернул `ready` с одинаковым JSON на `ru` и `en`. `apply --profile prod`
и обычный `run --profile prod` отклонены с `forbidden_action` на обоих языках.
Отдельная Git-копия подтвердила production source gate: чистые исходники —
`current`; dirty, unsaved и отставание от выбранной основной ветки — `different`;
недоступный remote — `unverified`. В негативных случаях DAP launch без явного
решения о коде не обращался к платформе и требовал выбора пользователя.

Настоящий `eska-debug` с `debug.managed=true` запустил собственный `dbgs`
8.5.4 и выполнил DAP `initialize`, `attach`, `configurationDone`, `threads`,
`disconnect` на обоих языках. После `disconnect` и отдельной проверки EOF
адаптер завершился с кодом 0, его loopback-порт закрылся.

После активации Community-лицензии на отдельной копии демонстрационного
приложения 2.0.0.21 `1cv8c` запущен через `launch`. DAP остановился на точке
в `ManagedApplicationModule.bsl`, вернул стек с путём к исходнику, вычислил
`1 + 1` со значением `2` и типом `Число`, затем остановился после `next`.
`disconnect` завершил клиент и управляемый `dbgs`. Проверка относится к
файловой базе и самостоятельному адаптеру на Linux ARM64.

В VS Code 1.144.0 на Linux ARM64 запуск через F5 в Explorer остановился
в `ManagedApplicationModule.bsl`. Call Stack показал исходный BSL-фрейм,
Debug Console вернула `2` для `1 + 1`, а Step Over привёл к новой остановке.
После отключения управляемый порт `dbgs` закрылся.

В том же выпуске VS Code штатная команда подключения Explorer увидела
уже работающий тонкий клиент в Distrobox. Сеанс остановился в BSL со
стеком, привязанным к исходнику. После `disconnect` тот же процесс клиента
продолжил выполнять прикладной код. Самостоятельный DAP подтвердил
подключение к этому типу сеанса, остановку и шаг в модуле установленного
расширения и привязку стека к локальному модулю развернутой EPF.
Для EPF изменение локального исходника разорвало привязку фрейма, а
восстановление точных байтов вернуло её в том же остановленном сеансе.

Клиент-серверная проверка использовала отдельные кластер 8.5.4.2072 и базу
PostgreSQL 15.18 с пакетом 1С из ALT p10. Конфигуратор загрузил конфигурацию
и обновил базу. `eska-debug attach` увидел серверный и клиентский контексты,
остановился в серверном `PatchProbe.Value`, вернул путь к модулю и вычислил
`1 + 1`. Стенд работал на loopback в отдельном сетевом пространстве имён.
В нём использовался хостовый `eska-debug` с его загрузчиком и libc.
После прогона процессы и порты стенда завершились.

Сводки проверок находятся в отдельных каталогах соседнего playground
`runtime-854-boiqm61p`, `demo-thin-854-4en66t9t`,
`vscode-debug-854-zsuvo4qs`, `cluster-854-native-d5oip64y`,
`composition-854.jpzzhqry/apply-fixed.Pp21YRfw` и
`debug-attach-854-18xqicgd`. На хосте запускались CLI, DAP и VS Code.
Нативные процессы 1С использовали ALT 10, установленный для этого стенда.
