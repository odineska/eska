# Проверка сборки на поддерживаемых ОС

Документ разделяет проверку переносимого process pipeline и приёмку с настоящей
платформой 1С. Тестовый `ibcmd` подтверждает передачу нативных аргументов,
stdout/stderr, exit codes и очистку ресурсов, но не совместимость Designer XML с
конкретной версией 1С.

## Переносимый процессный стенд

`tests/fixtures/ibcmd` — отдельный Rust-процесс без shell-команд. Интеграционный
набор собирает его один раз под текущую host-платформу и передаёт путь через
публичный `build --ibcmd`.

Linux и macOS:

```bash
ESKA_TEST_ROOT="$(realpath ../eska-playground)" \
  cargo test --test integration cli::build
```

Windows PowerShell:

```powershell
$env:ESKA_TEST_ROOT = (Resolve-Path ..\eska-playground).Path
cargo test --test integration cli::build
```

Набор использует пути с пробелом и кириллицей и проверяет:

| Контракт | Сценарий |
|---|---|
| `.cf`, `.cfe`, `.epf`, `.erf` и JSON | `builds_all_native_artifact_types_with_locale_independent_json` |
| контекст основной конфигурации для `.epf`/`.erf` | `external_build_uses_base_configuration_context_and_source_directory` |
| повторное использование и принудительное пересоздание служебной базы | `repeated_build_reuses_managed_infobase` |
| пересоздание при изменении базового `.cf` | `changed_base_configuration_invalidates_managed_infobase` |
| точное совпадение версии платформы | `exact_platform_version_is_required` |
| workspace, selectors и aggregate JSON | `workspace_build_uses_shared_outputs_and_distinct_json_shapes` |
| dry-run и отсутствие побочных эффектов | `dry_run_human_is_localized_and_does_not_change_the_filesystem` |
| паспорт и зафиксированный снимок исходников | `manifested_build_uses_the_captured_source_snapshot` |
| безопасная замена и сохранение служебной базы после ошибки | `failed_build_preserves_existing_artifact_and_managed_infobase` |
| прерывание, сохранение базы и очистка staging | `interrupted_build_preserves_managed_infobase` |

Сценарий прерывания пока посылает POSIX `SIGTERM`, поэтому исполняется только на
Unix. Проверка отказа и cleanup переносима, но не заменяет проверку Ctrl+C на
Windows. Проверка символических ссылок также остаётся Unix-специфичной.

## Протокол с настоящей платформой 1С

Для каждой проверенной комбинации сохранить:

- ОС, архитектуру, версию Rust и полный вывод `ibcmd --version`;
- точные команды `eska`, runner (`host` или `distrobox`) и пути проектов;
- exit code, stdout и stderr каждой команды;
- размеры и SHA-256 файлов `.cf`, `.cfe`, `.epf`, `.erf` и их паспортов;
- результат повторной сборки поверх существующего артефакта;
- результат Ctrl+C во время import: прежний артефакт и служебная ИБ сохранены,
  staging-файлы удалены;
- результат `eska clean`: служебная ИБ удалена, опубликованный артефакт сохранён;
- дату проверки и имя исполнителя.

Минимальная последовательность для каждого из четырёх типов проекта:

```text
ibcmd --version
eska build --dry-run --format json --ibcmd <полный-путь-к-ibcmd>
eska build --manifest --format json --ibcmd <полный-путь-к-ibcmd>
```

Для workspace выполнить те же две команды из корня без selector, затем с `-p`
для одного member. На Linux сценарий Distrobox записывается отдельно с
`--distrobox <container>`; он не считается проверкой host runner. Если ОС,
архитектура или версия 1С недоступны, строка результата должна оставаться
`UNVERIFIED` с причиной.

T94 проверяет самостоятельный [eska-build](build-tool.md). Повторная нативная
матрица запускается `tests/native_build.py` с явными Distrobox, путём ibcmd
и точной версией; все проекты и базы создаются в уникальном соседнем playground.
Linux-запуск не закрывает оставшуюся OS-матрицу T55 и не считается проверкой
настоящего host runner или функциональной работой клиента 1С.
Отдельная Windows host-приёмка описана в [отчёте от 2026-10-31](windows-review-2026-10-31.md).

## Автоматическая основа EPF/ERF (T147)

Новые process-сценарии находятся в `crates/eska-build/tests/build_reference`
и `runtime_base`. Они проверяют manifest-ссылки по имени/пути, отдельные приложения,
изменения содержимого/пути/платформы, checksum CF, ошибки и сохранность результатов.
Core отдельно проверяет ownership member и пересечение с рабочими исходниками.

Нативная серия: Linux ARM64, ALT/Distrobox, 1С 8.3.27.2342.
[Матрица и ограничения](measurements/t147-build-libraries.json).
EPF/ERF с типом из библиотеки собираются обычным `eska build`, имеют тот же
native XML-экспорт, что вариант с явным CF; без основы импорт отклоняется.
Проверены два приложения workspace, member/selectors, повтор, паспорт, очистка
и отмена подготовки CF. Скрипт работает только в новом соседнем playground,
исходную библиотеку копирует и проверяет её сохранность:

```sh
ESKA_TEST_ROOT="$(realpath ../eska-playground)" python3 -B tests/native_libraries.py \
  --library-source "$ESKA_LIBRARY_SOURCE" --catalog "$ESKA_LIBRARY_CATALOG" \
  --platform-version "$PLATFORM_VERSION" --distrobox "$ESKA_DISTROBOX" \
  --platform-arch "$ESKA_PLATFORM_ARCH" --ibcmd "$ESKA_IBCMD"
```

Перед запуском собрать `eska`, `eska-build`, `eska-vcs`; значения переменных
относятся к выбранной установленной платформе. `--ibcmd` используется для
контрольного native-экспорта, build ищет стандартный путь по machine config.
Другие ОС и host runner этим результатом не подтверждены.


## Общая подготовка именованной библиотеки (T148)

Process-сценарии `build_reference::shared` проверяют CF-производителя без
`--manifest`, разные потребители, отдельные изменяемые ИБ, канонические пути,
root source layout, повреждение/удаление CF и шаблона, параллельную подготовку,
отмену ожидания lease, read-only исходники и locale-independent ошибки.

`tests/native_libraries.py` теперь проверяет общий CF, неизменяемую основу ИБ
и два параллельных native-потребителя. Реальная БСП 3.1 на 8.3.27.2342 прошла
всю серию Linux ARM64/ALT Distrobox. Новый независимый отчёт — 9,59 с после
подготовки основы; первоначальная сборка без общего результата — 24,62 с.
Проверка исходных байтов остаётся обязательной. Explorer отдельно проверен
в VS Code 1.144.0: раннее изменение manifest и живой `eska add` с dirty-буфером.
[Результаты и ограничения](measurements/t148-build-libraries.json).

## Файловые операции 8.5.4

На Linux ARM64 в rootless Distrobox `onec-alt10-854` проверен настоящий
`ibcmd` 8.5.4.2072. `platform list` показал эту сборку, `doctor` принял
конфигурацию с линейкой 8.5.4. В плане сборки `required_version=8.5.4` и
`found_version=8.5.4.2072`. В отдельных каталогах соседнего playground прошли
`config import --out` и `config export --file` для CF, CFE, EPF и ERF.
CF получен из минимальной конфигурации; CFE — из копии выгрузки «ВесТоваров»;
EPF/ERF имеют собственные сгенерированные UUID. Имя и UUID CF/CFE
сохранились после прямой выгрузки. Это проверка файлового режима, а не
полная проверка приложения в клиенте.

В живом VS Code 1.144.0 в разделе Project and Build точная сборка
`8.5.4.2072` заменена на линейку `8.5.4` в манифесте. Штатный предпросмотр
сборки показал выбранную `8.5.4.2072` и runner Distrobox, после чего план
отменён. Доступный через хост `ibcmd` оказался обёрткой для старой установки.
CLI выбрал через неё `8.3.27.2342` для линейки `8.3.27` и сообщил фактический
runner Distrobox. Выбор среди нескольких сборок и точное закрепление
покрыты тестами на синтетических установках.

При конкурентном запуске файловые операции с каталогом сервера по умолчанию
конфликтуют: платформа возвращает ошибку блокировки. Одного `--lock` недостаточно
(ошибка доступа к реестру сервера). Проверенный изолированный `--data` создаёт
IPC, логи и временные данные, но не `1Cv8.1CD`. С ним CFE импортируется и
экспортируется без `infobase create`, одновременно с другой операцией.
Runtime размещает эти данные внутри принадлежащего операции staging.

Выбор режима использует линейку фактически запущенной платформы: 8.5.4
и новее. Наличие флагов в help не служит признаком поддержки. Portable-тесты
`standalone_build_preserves_publication_contract_without_infobase` и
`standalone_unpack_exports_all_artifacts_without_infobase` проверяют
8.5.4.2072 и другой номер сборки той же линии. Существующие тесты 8.3.27
проверяют резервный путь с ИБ. Входы с базовым CF/XML и сборка библиотеки
сохраняют контекст ИБ. У CF есть узкий совместимый повтор через загрузку в ИБ
после платформенного отказа прямого экспорта; отмена и ошибки запуска
не повторяются. При двух отказах сохраняются обе диагностики.

Нативная матрица `eska-build` на том же стенде прошла для четырёх форматов:
первый build, повторный build с `--recreate-infobase`, оба с `--manifest`,
и `unpack --format json`. Все 12 вызовов завершились кодом 0; `1Cv8.1CD`
не появился ни в одном проекте, SHA-256 опубликованных файлов совпал с паспортом.
Для пустых EPF/ERF экспорт пропускает объектный каталог: обратный импорт
требует пустой `<имя-descriptor>/Ext`. Runtime восстанавливает его в своём
staging без изменения выгруженных файлов. Обратный нативный импорт
с восстановленным контейнером прошёл для обоих форматов.

`eska new --from` создал проект из собранного EPF и сохранил линейку
`platform_version = "8.5.4"`. `import --dry-run` и последующий `import --force`
опознали одно и то же имя и UUID. Применение прошло на отдельной копии проекта.

На CF демонстрационного приложения (~20 МБ), собранном прямым импортом 8.5.4,
прямой экспорт вернул 255 «Ошибка формата потока». Тот же снимок успешно
загрузился в ИБ и выгрузился штатным способом. Проверка через обновлённый
`eska-build unpack --format json` завершилась кодом 0, сохранила имя
`ДемонстрационноеПриложение` и UUID `a3a9949e-f1f0-4b3a-821f-a85a9fb2fb3c`.
Поэтому поддержка линейки не считается гарантией прямого экспорта любого CF:
этот формат сохраняет изолированный совместимый повтор.

В этой матрице первый/повторный build занял соответственно: CF 43,6/42,6 с,
CFE 41,5/43,6 с, EPF 42,6/43,1 с, ERF 42,6/43,6 с. Повторный файловый режим
не переиспользует ИБ; измерение не доказывает ускорение относительно старого
пути и включает ожидание завершения нативного процесса.

### Внешние объекты с типами основной конфигурации

На 8.5.4.2072 проверен отказ EPF/ERF с атрибутом
`cfg:CatalogRef.Контрагенты` при обоих способах задания контекста: явный CF
и `analysis.configuration.source` с Designer XML той же демоконфигурации.
Каталог присутствует в контрольной выгрузке основы. Создание/загрузка ИБ
и подготовка XML-основы завершаются успешно, но прежний вызов
`infobase config import --data=... --out=...` возвращает 255
«Неизвестное имя типа - CatalogRef.Контрагенты». Дополнительные
`config apply --force` и явный `--db-path` не устраняют этот отказ.

После штатной активации Community-лицензии тот же контекст успешно проверен
через соседний Designer 8.5.4.2072:

```text
1cv8 DESIGNER /F <prepared-data>/db-data
  /LoadExternalDataProcessorOrReportFromFiles <root-descriptor.xml> <artifact.epf|erf>
  /DisableStartupDialogs /DisableStartupMessages
  /Out <owned-workspace>/designer.log /DumpResult <owned-workspace>/designer.result
```

Синтаксис подтверждён [официальным описанием параметров платформы](https://edt.1c.ru/dev/edt/2025.2/apidocs/com/_1c/g5/v8/dt/platform/services/core/runtimes/execution/impl/IRuntimeExecutionCommandOptions.html)
и [контрактом DumpResult](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.24_Administrator_Guide/Appendix_7._The_parameters_of_the_command_line_to_launch_1C_Enterprise/7.4._Running_Designer_in_batch_mode/7.4.17._Other_parameters/?language=en).
EPF и ERF дали exit 0 и `DumpResult` 0. Обратная выгрузка Designer сохранила
тип объекта, имя, UUID и `cfg:CatalogRef.Контрагенты`. Прямой экспорт ibcmd
тоже завершился успешно; тип представлен `v8:TypeId`, совпадающим с
`GeneratedType` соответствующего справочника в исходной конфигурации.

Отдельные копии только загруженной, но не применённой ИБ также собрали оба
формата: для Designer не нужны `config apply` и дополнительная materialize.
Обновлённый `eska-build build --manifest --format json` прошёл все четыре
сочетания EPF/ERF × CF/XML-основа, включая повторный запуск
с `--recreate-infobase`; SHA-256 опубликованных файлов совпал с паспортами,
а snapshot_id неизменных исходников сохранился. Обратный Designer-экспорт
всех четырёх опубликованных файлов сохранил идентичность и тип атрибута. На Linux Distrobox проверен обычный доступный DISPLAY;
отдельная проверка batch-команд под Xvfb также прошла. В runtime нет нового
графического runner: используется существующий interruptible sibling runner.

Платформенный отказ ibcmd запускает этот совместимый путь только для EPF/ERF
с явно разрешённой основой на файловой линейке 8.5.4 и новее. Успешный ibcmd
не требует Designer, поэтому исправленная сборка той же линии сохраняет
основной путь. Portable-тесты проверяют два номера сборки, CF/XML-основу,
неуспешный exit, отсутствующий/ошибочный `DumpResult`, отсутствующий/пустой
новый файл и отмену в обоих importer-процессах. При отказе или отмене
предыдущие артефакт и паспорт сохраняются; 8.3.27 и входы без основы
не переходят к Designer.

### Нативные идентификаторы (#382)

Ограниченная проверка 8.5.4.2072 над теми же CF/CFE/EPF/ERF:

| Формат | `config checksum` | `config generation-id` |
| --- | --- | --- |
| CF | код 0, 64 шестнадцатеричных символа | код 0, 40 шестнадцатеричных символов |
| CFE | код 0, 64 шестнадцатеричных символа | код 0, 40 шестнадцатеричных символов |
| EPF | код 139, без stdout/stderr | код 2, «Некорректное расширение файла» |
| ERF | код 139, без stdout/stderr | код 2, «Некорректное расширение файла» |

Обе операции принимают путь позиционно, например
`ibcmd config checksum --data=<каталог> <файл.cf>` и
`ibcmd config generation-id --data=<каталог> <файл.cfe>`. Повреждённый CF
в обоих случаях дал код 255 и «Неверный формат хранилища данных».
Поддержку на другой установке можно проверить по справке команды и повторить
вызов на годном файле нужного формата в отдельном `--data`.

Две сборки одинакового CF XML получили разные SHA-256 файла и поколения при
одинаковом нативном checksum. После изменения `Comment` нативный checksum CF
изменился. Для CFE две сборки одного XML получили разные значения всех трёх
идентификаторов. Повторный checksum одного и того же готового CFE совпал.
После загрузки и применения CF поколения файла, загруженной конфигурации
и конфигурации базы различались. У минимального CFE без заимствований
поколение совпало во всех проверенных точках.

Паспорт использует SHA-256 для целостности опубликованных байтов.
`apply` продолжает сверять поколение установленной конфигурации. Наблюдаемые
различия CF и CFE исключают общий контракт идентичности на базе новых команд.
Подробности проверок сохранены в `ibcmd-854-id-followup-98_6eser` соседнего
playground. `config update <path>` принимает файл обновления конфигурации CFU.
Текущий `apply` применяет Designer XML и использует `config apply` для
обновления конфигурации базы данных.
