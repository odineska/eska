# Создание реквизитов и табличных частей

`eska metadata add` создаёт элементы Designer XML через общее Rust-ядро.
Интерактивный мастер, команды для скриптов и IDE используют одинаковые
типы, ограничения, план изменений и проверку перед записью. Платформа 1С
для самой правки исходников не требуется.

Поддержаны реквизиты и табличные части справочников, документов, обработок
и отчётов основной конфигурации, внешних обработок EPF и отчётов ERF.
В существующие табличные части можно добавлять реквизиты. Создание в
расширениях пока не поддержано. Для конфигураций, целых объектов, копирования,
удаления и редактирования форм см. [общее руководство CLI](metadata-authoring.md).

## Интерактивная работа

В каталоге проекта выполните:

```bash
eska metadata add --interactive
```

Мастер предлагает вид элемента, владельца, имя, тип и его параметры,
синоним и комментарий. Уже переданные параметры сохраняются:

```bash
eska metadata add attribute --owner 'document:ВыдачаЗайма' --interactive
```

Перед записью показываются создаваемый элемент, его свойства и изменяемый
файл. Подтверждение принимает `y/n` и `д/н`; отмена не изменяет исходники.
Мастер также показывает эквивалентную команду с явными параметрами.
Подписи свойств и типов берутся из существующих словарей платформы; язык
CLI не меняет имена объектов, коды языков конфигурации или значения JSON.

Для проекта внутри workspace укажите `--project NAME` (`-p NAME`).
Самостоятельный компонент предоставляет те же команды:

```bash
eska-project --project-dir ./demo metadata add --interactive
```

## Явные команды

Добавить строковый реквизит:

```bash
eska metadata add attribute \
  --owner 'document:ВыдачаЗайма' \
  --name КомментарийМенеджера \
  --type string --length 200 \
  --synonym 'ru=Комментарий менеджера' \
  --no-input --format json
```

Добавить табличную часть и числовой реквизит в неё:

```bash
eska metadata add table-part \
  --owner 'document:ВыдачаЗайма' --name Расшифровка \
  --no-input --format json

eska metadata add attribute \
  --owner 'document:ВыдачаЗайма/tabular-section:Расшифровка' \
  --name Сумма --type number --digits 15 --fraction-digits 2 \
  --no-input --format json
```

Ссылочный тип выбирает существующий объект по его логическому идентификатору:

```bash
eska metadata add attribute \
  --owner 'document:ВыдачаЗайма' --name Ответственный \
  --type reference --reference 'catalog:Сотрудники' \
  --no-input --format json
```

Другие простые типы — `boolean` и `date`. Для даты доступны
`--date-fractions date|time|date-time`, для строки — `--fixed-length`,
для числа — `--nonnegative`. Полный набор параметров показывает
`eska metadata add --help`.

`--no-input` запрещает вопросы даже в терминале. Если данных недостаточно,
команда завершится ошибкой со списком необходимых параметров. Вызов с
полным набором параметров выполняет создание без интерактивного мастера.

## Discovery, предварительный просмотр и применение плана

ИИ и скрипты могут получить допустимые операции, типы, ограничения и defaults:

```bash
eska metadata create-schema
eska metadata create-schema --owner 'document:ВыдачаЗайма'
```

Для конкретного владельца ответ содержит `snapshot`, доступность записи,
виды создаваемых элементов, ссылки на объекты конфигурации и её языки.
Состав поддержанных операций проверяет ядро; клиент не должен выводить его
из внешнего вида дерева или самостоятельно конструировать XML.

Чтобы сначала рассмотреть точные изменения и затем применить их:

```bash
eska metadata add attribute \
  --owner 'document:ВыдачаЗайма' --name Проверено --type boolean \
  --dry-run --no-input --format json > create-plan.json

eska metadata add --plan create-plan.json --no-input --format json
```

`--dry-run` не записывает исходники. Ответ включает вычисленные замены
UTF-8 байтов, путь относительно каталога исходников, исходный снимок и
`prepared` с семантическим запросом и выделенными UUID. Сохранённый план
применяется с теми же UUID. `expectedOutputSnapshot` проверяет точное
совпадение получаемого XML с предварительным просмотром.
`--plan -` принимает сохранённый ответ через stdin. Повторная проверка
`--plan create-plan.json --dry-run --format json` сохраняет выделенные UUID
и заново проверяет план без записи.

`--snapshot TOKEN` у обычной команды задаёт только предусловие исходного
файла. Для применения именно рассмотренного плана используйте `--plan`.
После внешней правки старый план отклоняется; нужно получить новый preview.

## JSON-запросы

Составные типы и несколько локализаций можно передать через `--input FILE`.
`--input -` читает запрос из stdin. Пример для реквизита с двумя типами:

```json
{
  "schemaVersion": 1,
  "request": {
    "owner": "document:ВыдачаЗайма",
    "snapshot": "Значение snapshot из create-schema для этого владельца",
    "kind": "attribute",
    "name": "Основание",
    "synonyms": [{"language": "ru", "content": "Основание"}],
    "comment": "",
    "types": [
      {"kind": "string", "length": 200, "fixed": false},
      {"kind": "reference", "object": "catalog:Договоры"}
    ]
  }
}
```

```bash
eska metadata add --input request.json --dry-run --no-input --format json
```

У `number` поля `digits`, `fractionDigits`, `nonNegative`; у `date` —
`fractions` со значениями `date`, `time`, `dateTime`; у `boolean` дополнительных
полей нет. Для `table-part` список `types` пустой. Неизвестные поля и
неприменимые параметры отклоняются, а не игнорируются.

Машинный ответ сохраняет общую оболочку `{schema_version:1,result:...}`
либо `{schema_version:1,error:{kind,details}}`. JSON не зависит от `--lang`.
Успех имеет exit code `0`, ошибка операции — `1`, неверный синтаксис
параметров — `2`. У новых `add` по умолчанию человекочитаемый вывод;
прежние команды `inspect`, `check`, `apply` сохраняют JSON по умолчанию.
`add` поддерживает `--format human`; `create-schema` и прежние операции
используют JSON. Новые команды объектов и форм описаны отдельно.
Запрос и сохранённый план ограничены 1 МиБ.

## Сохранность и границы

Создание проверяет владельца, имена, типы, ссылки, UUID и ограничения записи.
Все остальные байты исходника, включая BOM, окончания строк и неизвестные
XML-элементы, сохраняются. Коллизия имени не превращается в перезапись.
У табличной части ядро создаёт также внутренние идентификаторы её типов.
`ConfigDumpInfo.xml` ради этой операции не переписывается.

Создание не включается в историю скалярного Undo/Redo: обратная операция
удаляет элемент и требует отдельной проверки появившихся ссылок. Старая
история свойств изменённого дескриптора сбрасывается, чтобы её повтор не
удалил созданный элемент. Прежнее редактирование свойств остальных объектов
продолжает работать.

При `creation_committed_refresh_required` исходник уже записан. После этой
ошибки или обрыва соединения сначала проверьте объект через `metadata inspect`;
автоматически повторять создание нельзя.

Команда меняет только исходники. Обновление тестовой базы выполняется
отдельной [операцией применения изменений](run-debug.md). Отчёт о проверке
настоящей платформой и подтверждённые ограничения находятся в
[нативной приёмке](measurements/metadata-creation-native-2026-11-16.md).
