# Самостоятельный проектный инструмент

`eska-project` работает с Designer XML без полной ESKA, Git, платформы 1С и
анализатора. Модель, правила XML и проверенные операции записи находятся в
общем ядре. Существующий `eska` сохраняет прежние команды и их поведение.

Сборка из checkout: `cargo build -p eska-project`.

Примеры внутри отдельного каталога соседнего `eska-playground`:

```sh
eska-project new demo --type configuration
eska-project new report --type report --source "Исходники XML"
eska-project init existing-export --source src
eska-project --project-dir demo validate --format json
eska-project --project-dir demo context --format json
eska-project --project-dir demo version --format json
eska-project --project-dir demo metadata inspect
```

`new` создаёт манифест и пустой source без генерации XML; требует тип.
`init` определяет тип по существующему корневому XML.
Поддерживаются configuration, extension, processing и report. `--source`
задаёт относительный каталог без `..`; `.` допустим. Существующий destination
или манифест не перезаписывается. Инициализация сохраняет исходные байты XML,
BSL и непрозрачных файлов. Git не инициализируется. В standalone создаются
обычные `.gitignore` и `.gitattributes`; существующий `.gitignore` дополняется
правилами производных файлов без удаления пользовательских правил.
Workflow не выбирается.

На Windows поля `project.source`, `build.artifacts_directory` и пути собственных
проектов в `workspace.members` также должны быть относительными: `C:\src`,
`C:src`, `\src` и UNC-пути для этих полей отклоняются. Генерируемые и обновляемые
манифесты используют `/`, например `src/base`, независимо от ОС. Это относится
к записи TOML; файловые операции и пути в JSON сохраняют нативное представление.

Необязательный `--platform-version 8.3.27.2325` сохраняет точную версию сборки
как данные, без поиска или запуска платформы. Без него standalone-манифест
содержит пустую версию. В workspace версия наследуется от корня; явное значение
записывается в member как override.

При запуске `new` внутри workspace позиционный аргумент — переносимое имя
участника, который создаётся в `src/<имя>`. `init` подключает существующий
каталог, использует его имя либо `--name`. Оба пути добавляют участника в его роль
в `workspace.members.<приложение>` с сохранением комментариев и дополняют
корневой `.gitignore`. При нескольких приложениях для расширения или внешнего
объекта требуется `--application <имя>`; ошибочный выбор не создаёт файлов.
Проверяются границы, вложенные Git/workflow-файлы не создаются.
Общий writer откатывает только принадлежащие операции файлы; конкурентно
изменённый root-манифест не перезаписывается.

`validate` и запуск без команды проверяют манифесты, выбранные корневые
дескрипторы, типы и границы исходников. Они не обходят все дочерние XML и не
проверяют BSL или возможность сборки платформой. В workspace доступны
повторяемый `--project <имя>` и `--workspace`. Пустой выбор возвращает ошибку.

`context` использует [правила контекстов приложений](application-context.md),
принимает `--application` и читает только корневые дескрипторы выбранных
источников. Standalone-расширение, EPF и ERF без подключённой базы отмечаются
`limited_context: true`. Явная `[analysis.configuration] source = "…"` подключает
XML внешней базы к анализу. Вместо `source` можно указать `library = "ssl_3_1"`:
имя разрешается через `[libraries.ssl_3_1]` пользовательского `config.toml`.
Источник остаётся только для чтения; ошибки каталога сохраняют имя и расположение
настройки. Для такого источника JSON добавляет `library: {name, configuration: Path}`.
Команда не создаёт `bsl-analyzer.toml`, кеш или индекс.

`analyzer-config` готовит [производный конфиг и миграцию](analyzer-configuration.md).
`metadata` и `version` перенесены без изменения операций, accepted-base checks,
ownership снимков и существующих JSON-схем.

`serve --stdio` запускает самостоятельный сервер [Metadata API](ide-protocol.md).
Он объявляет identity `eska-project`, API 1.21 и `selfUpdate: false`; языковой
сервер не запускается при открытии дерева. Полная ESKA, Git, платформа и analyzer
в PATH не требуются. Прежний `eska ide --stdio` сохраняет identity `eska` и прежнее
поведение CLI. Это два входа одной реализации сервера, без второго дерева или индекса.

API 1.14 добавляет общее private recovery для IDE-адаптеров: полные снимки
владельцев и черновики хранятся backend вне проекта. Формат checkpoint T101
остаётся читаемым; сохранение требует совпадения подтверждённой ревизии.
Это не запись исходника и не подтверждение блокировки BSL-владельца.

API 1.15 добавляет опциональные сессии XML-запросов: backend владеет привязкой,
черновиком, явным возобновлением и проверкой результата применения в IDE.
План не пишет исходник; адаптер применяет его через штатный редактор и передаёт
подтверждение. В режиме 1.15 незавершённый план хранится только в памяти.

API 1.16 добавляет устойчивый журнал: точный output и применяемый запрос
сохраняются до выдачи плана, отдельно от последнего черновика. Явное возобновление
после сбоя сверяет исходный или уже применённый буфер и не повторяет правку.
Рабочий Explorer использует общий жизненный цикл API 1.16: передаёт факты native
документа, выполняет проверенный план и подтверждает результат. При вводе нового
текста во время Save сохраняется отдельный черновик. Общее восстановление
с API 1.14 остаётся доступным для чтения без возможности применения источника.
API 1.19 включает BSL-сессии с полным защищённым снимком и проверкой конфликтов.
Обычные нативные вкладки могут редактироваться; их изменения не перезаписываются
при применении устаревшего черновика. Save BSL-черновика сохраняет только checkpoint,
явный Apply возвращает план без сохранения модуля на диск. ESKA владеет кодированием,
сессией, политикой, восстановлением и проверками; IDE выполняет одну отменяемую правку.
Native read-only overrides не меняются.
API 1.20 добавляет неизменяемую BSL-проекцию, карту позиций и перевод языковых
правок в SDBL-план. Эти операции не записывают исходник/черновик и не удерживают
блокировку сессии. Explorer передаёт проекцию существующему опубликованному LSP.
API 1.21 добавляет модель конструктора, операции с сохранением токенов и
исключительное владение черновиком. Только явный finish меняет private checkpoint;
исходник остаётся прежним до обычного сохранения XML или применения BSL.
Позиции переноса исходных комментариев также переводятся общим API ESKA.
Адаптер конструктора пока разрабатывается.
Активная source-сессия уже блокирует конкурирующие операции самого backend:
свойства, Undo/Redo, прежний query/plan и переименование исходника или его
дескриптора. Закрытие сессии освобождает только её ограничение, сохраняя support policy.

API 1.17 добавляет общее состояние защиты и неизменяемые снимки исходников:
точные bytes диска, переданного буфера IDE или удерживаемого владельца запроса.
Бинарный контент передаётся ограниченными base64 chunks; снимки не пишут исходники
и делят прежний бюджет 32 MiB с query-буферами и сессиями. Рабочий Explorer
использует состояние ESKA перед языковыми правками, включая временное владение
при отключённой обычной защите поддержки. Провайдер `eska-protected:` читает
через тот же backend. API 1.18 добавляет read-only просмотр без manifest
или распознанного metadata owner: только диск внутри рабочей папки serve,
без подтверждения поддержки или права записи. Такой просмотр сохраняет
восстановление вкладок и использует прежние общие лимиты памяти.

## Диагностика окружения

`eska-project doctor` сохраняет отчёт общего `eska doctor`, включая `--project`,
`--workspace`, platform flags и `--format human|json`. Для проверок платформы
и VCS вызываются их отдельные компоненты; отсутствие одного отражается
ошибкой в отчёте и не скрывает остальные проверки. Обычные команды проекта
и `serve` этих компонентов не требуют. [Композиция и проверки](component-delegation.md).

## Вывод

Все команды поддерживают глобальные `--lang ru|en` и `--project-dir`.
Справка доступна без внешних процессов. `new`, `init`, `validate` и `context`
принимают `--format human|json`; по умолчанию вывод human. Успех — exit 0,
ошибка — exit 1. Ошибка разбора аргументов clap — exit 2.

JSON новых команд содержит `schema_version: 1`, `kind` и `status`. Пути
кодируются как `{value, encoding}` по общему обратимому протоколу Metadata API.
Успех создания/инициализации содержит `project` с `root`, `source`, `project_type`
и `vcs_initialized: false` — операция не инициализировала repository.
Проверка возвращает `validation: "root_descriptors"` и `projects`.
Контекст возвращает `context` с именем, корнем, target version, limited flag,
источниками в порядке зависимостей и явными `extension_dependencies`.

Ошибка новых команд выдаёт JSON только на stdout:
`{schema_version:1,kind:"project",status:"error",error:{code,data}}`.
Локализованная причина выводится на stderr. JSON не зависит от языка.
Существующие `metadata` и `version` сохраняют собственные envelopes.

## Проверка T91

Пройден полный набор fmt/check/strict Clippy/test/Rustdoc для workspace:
769 Rust-тестов passed, 6 ignored. Новые process-тесты запускают компонент
с пустым PATH: все четыре типа, `source = "."` и вложенный source,
workspace enrollment, обе локали, отказ до записи, symlink escape и
сохранность BOM/CRLF/opaque bytes. Ручное сравнение metadata/version
полного и прямого CLI дало побайтно одинаковый JSON для ru/en.
`cargo run -- --version` сохраняет выбор прежнего binary через default-run.

Explorer: 138 Node-тестов с настоящим backend и изолированный Extension Host
properties suite (VSCodium 1.109.5) прошли. Это проверка перенесённого API через
прежний `eska ide`; переход на standalone serve выполняется в T92.
Первый промежуточный Rust-прогон получил `Shelf(Locked)` в существующем
switch-тесте; полный финальный прогон прошёл без изменения этого сценария.

Нормальный граф project package не содержит полной `eska`, repository `gix`,
platform runner, Tokio, HTTP/updater или ядра анализатора. `gix-path` и
`gix-validate` остаются переносимыми утилитами модели.
Экспериментальные Rust-типы native ошибок new/init теперь содержат
`Operation(CreationFailure/InitFailure)`; публичный CLI и JSON не изменены.

не проверены. Установщик project и языковой клиент остаются следующими этапами.

## Подключение БСП

`eska-project add ssl_3_1` и `eska add ssl_3_1` выполняют одну операцию:
первая установка из `master` известного репозитория в пользовательскую
`~/.eska/lib`, регистрация выбранного `src/cf` и одна ссылка проекта EPF/ERF.
Поддерживается также `ssl_3_2`. В workspace используются текущий member
или один `-p`; другая существующая основа не заменяется. Повтор использует
зарегистрированную локальную копию без VCS и сети.
[Настройка, квитанция и JSON](user-guide.md#add-library).

Доменные проверки, владение установкой и условная публикация TOML находятся
в `eska-project-core::libraries`. VCS остаётся отдельным process-компонентом;
project не линкует gix и не запускает системный Git. Сигнал отмены принадлежит
одной операции от checkout до записи ссылки.
