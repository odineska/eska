# Редактирование существующих свойств

Редактор VS Code и `eska metadata` используют один core API `ProjectSession`:
схема → проверенный план → запись. Источник — Designer XML. Каталог свойств входит в поставку ESKA;
для пользовательской работы не нужны EDT, Java или преобразование исходников.

Архитектурное правило для дальнейших операций изменения проекта: человек и ИИ
используют общий backend. Операция публикует машиночитаемые допустимые значения,
ограничения, preconditions и preview; эти ограничения проверяет core, независимо
от клиента. Новый UI не должен становиться единственным способом изменения.
Нынешняя поставка реализует это правило для существующих свойств.

## CLI для ИИ и скриптов

```bash
eska metadata inspect --format json
eska metadata inspect --object 'catalog:Товары/attribute:Артикул'
eska metadata types types.json
eska metadata choices reference.json
eska metadata check change.json
eska metadata apply change.json
```

В workspace укажите один member через `-p NAME`; `--project-dir` выбирает
контекст. Вместо файла запроса можно передать `-` для stdin. Лимит запроса —
1 MiB. `inspect`, `types`, `choices` и `check` не изменяют исходники и не создают disk cache.

`inspect` возвращает объект, свойства, непосредственных потомков через группы
дерева и `editing`: точный SHA-256 файла `snapshot`, источник, `writable`,
профиль справочника, `fields`, `readOnlyProperties`, возможности undo/redo.
В новом процессе CLI история пуста; последовательная история принадлежит IDE session.
`fields` — закрытый список разрешённых операций. Отсутствующее поле нельзя
изменить, даже если его значение выглядит как строка или число.

Запрос `types`:

```json
{"schemaVersion":1,"objectId":"catalog:Товары/attribute:Артикул","path":[{"key":{"namespace":"http://v8.1c.ru/8.3/MDClasses","name":"Type"},"occurrence":0},{"key":{"namespace":"http://v8.1c.ru/8.1/data/core","name":"Type"},"occurrence":0}]}
```

Для `check` и `apply` возьмите `objectId`, `snapshot` и **точный `path` из inspect**:

```json
{
  "schemaVersion": 1,
  "objectId": "catalog:Товары",
  "snapshot": "SHA-256 из editing.snapshot",
  "path": [{"key":{"namespace":"http://v8.1c.ru/8.3/MDClasses","name":"Comment"},"occurrence":0}],
  "change": {"kind":"text","value":"Новый комментарий"}
}
```

`text` передаёт также boolean (`"true"`/`"false"`), число и технический токен
перечисления. Схема содержит допустимые `values` и RU/EN `options`, ограничения
числовых параметров. Смена типа использует
`change:{kind:"dataType",key:{namespace,name}}` из ответа `types`.
Для `schema.kind:"reference"` команда `choices` принимает такие же ключи запроса,
как `types`, и возвращает `value`, `objectId`, `metadataKind` и RU/EN `caption`.
Выбранный `value` передаётся через `change:{kind:"text",value}`. Core повторно
проверяет существование объекта, класс ссылки и допустимого владельца формы.
`nullable:true` разрешает пустую строку для очистки одиночной ссылки.
Существующие строки списков ролей имеют `nullable:false`; дубли ролей отклоняются.
Для имени существующей связи параметров выбора схема имеет вид
`{kind:"text",domain:"choiceParameterName"}`. Допустимы одна или две непустые
части через точку: буквы Unicode BMP, десятичные цифры и подчёркивание.
Цифра разрешена и в начале. Имена внутри одного списка сравниваются без учёта
регистра; дубли и пары вида `Отбор` / `Отбор.Владелец` запрещены.
Режим изменения связанного значения имеет домен `LinkedValueChangeMode`
с вариантами `Clear` / `DontChange` и локализованными подписями.
Клиент не передаёт XML, byte offsets, файловые пути для записи или произвольный
patch. `check` возвращает рассчитанные core-ом замены UTF-8 байтов и признак
`changed`; эта проверка не резервирует файл. `apply` повторяет все проверки.

Поля с `linked:true` требуют также `contextSnapshot` из `editing`. Это отдельный
SHA-256 снимок зависимостей: для документа — объявленных нумераторов, для
нумератора — ссылающихся документов. `snapshot` по-прежнему относится только
к основному XML. Backend перечитывает зависимости без опоры на watcher; новый
связанный документ или изменение его байтов делает старый запрос конфликтным.
Без токена возвращается `property_context_required`, с устаревшим —
`property_conflict`. Отказ зависимого документа дополнительно сообщает
`details.objectId` и `details.objectName`, сохраняя код ошибки и `property`.
Если зависимости нельзя прочитать, связанные редакторы
скрыты с `readOnlyProperties.reason:"linked_context_unavailable"`.

`check.result.files` содержит все изменяемые файлы: `objectId`, `source` в обычном
wire path формате, исходный `snapshot`, точные byte `changes`.
Поле `changes` верхнего уровня сохраняет замены основного XML.
`linkedObjects` сообщает число связанных документов; `undoLinked` и `redoLinked`
отличают общую отмену от изменения одного файла. Один CLI-вызов не сохраняет
историю между процессами. Прерванная публикация использует существующую команду
`metadata rename-recovery`, поскольку формат журнала общий для метаданных.

Один stdout JSON: `{schema_version:1,result:...}` либо
`{schema_version:1,error:{kind,details}}`. Успех — exit 0, доменная ошибка — 1,
ошибка аргументов CLI — 2. Ответы не зависят от `--lang`; help локализован.
Основные ошибки: `property_conflict`, `property_invalid`, `property_unsupported`,
`property_read_only`, `property_write_failed`. `property_committed_refresh_required`
означает, что запись уже состоялась, но обновить представление не удалось:
нужно повторно прочитать объект, **не повторять apply**. После обрыва процесса
результат также следует выяснять чтением, а не автоматическим повтором запроса.

## Поддерживаемая область

Редактируются известные строковые, булевы и перечислимые свойства, содержимое
существующих языковых строк, проверенные вложенные поля и параметры типов.
Можно заменить существующий тип и его qualifiers, сохранив количество типов:
строка, число, дата, булево, хранилище значения, UUID и перечисленные backend-ом
ссылочные типы существующих объектов текущего проекта. Повтор одного типа
отклоняется. Разрядность числа — 1–38, дробная часть не превышает разрядность;
схема учитывает текущий соседний параметр.
Длина номера строки табличной части — 5–9; число и интервал повторов
регламентного задания — 0–1 000 000. Эти поля публикуются как `integer`
с `min`/`max`; границы проверены в редакторах EDT и загрузкой обоих крайних
значений в платформу 8.3.27.2325. Остальные числовые свойства включаются
только после проверки их собственных зависимостей.

Число уровней справочника — 2–10; поле доступно при включённых иерархии
и ограничении уровней. Причины `hierarchy_disabled` и `level_limit_disabled`
в `readOnlyProperties` объясняют недоступность соответствующих полей.
Длина порядка плана счетов — 0–628; при автопорядке минимум равен длине кода.
Уменьшение проверяет существующие значения `Order` в `Predefined.xml`, включая
вложенные счета и повторную проверку при undo/redo. Длина периода корректировки
регистра бухгалтерии — 0–3. Диапазоны сверены с редактором Конфигуратора
8.3.27.2325; крайние значения записаны через CLI, загружены из CF и проверены
обратной выгрузкой. Один успешный `CheckConfig` недостаточен для проверки границ:
импорт может принять недопустимое значение либо нормализовать его.

Срок жизни сеанса HTTP- и Web-сервисов — 0–18446744073709551615 секунд.
Для него схема `unsignedInteger` передаёт границы `min`/`max` строками, как и
само значение; преобразование в JSON number теряет точность. Интерфейс IDE
требует API 1.11. Проверены оба сервиса, ноль, число 9007199254740993 и верхняя
граница: точечная запись, undo, загрузка CF и обратная выгрузка 8.3.27.2325.
Отрицательные числа и переполнение отклоняются до записи.

Максимальное количество субконто плана счетов — 0–50. Поле доступно после
выбора плана видов характеристик; иначе `readOnlyProperties` указывает причину
`ext_dimension_types_missing`. Для очистки ссылки сначала явно установите
количество в ноль. Backend не удаляет строки предопределённых счетов:
уменьшение лимита ниже их количества и смена плана при оставшихся ссылках
отклоняются с `property_dependency`. Актуальный `Predefined.xml` проверяется
также при undo/redo. Границы проверены в форме Конфигуратора 8.3.27.2325;
его XML-импорт способен принять 51, хотя редактор такое значение отклоняет.

Длина строкового кода справочника — 0–50, плана видов расчёта — 0–40;
числового кода — 0–38. Для плана счетов, плана видов характеристик и плана
обмена длина кода — 0–50. Максимальная длина наименования — 628 у плана
счетов, 250 у плана обмена и 150 у справочника, задачи и планов видов
характеристик/расчёта. Нулевая длина отключает стандартный реквизит.
Перед записью проверяются автонумерация, контроль уникальности, ввод по строке,
автопорядок счетов, стандартное значение заполнения и актуальный `Predefined.xml`.
Отсутствующий `InputByString` сохраняет платформенные значения по умолчанию;
отключать использованное им поле нельзя. Неподходящие предопределённые коды и
наименования блокируют изменение и его отмену; данные не сокращаются автоматически.
Числовые ограничения и нулевые значения проверены загрузкой в 8.3.27.2325.

Длина номера документа, задачи и бизнес-процесса — 0–50 для строки и 0–38
для числа. Смена типа не разрешает оставить длину за пределами нового диапазона.
Перед отключением номера проверяются ввод по строке и стандартное значение
заполнения; у документа также требуется отключить автонумерацию и контроль
уникальности. При назначенном нумераторе пять параметров документа (тип,
длина, допустимая длина, периодичность и уникальность) доступны только для
чтения с `readOnlyProperties.reason:"numerator_inherited"`. Автонумерация
остаётся независимой. Это поведение блокировки подтверждено в Конфигураторе
8.3.27.2325; очистка ссылки возвращает редакторы без перезаписи остальных
параметров.

Назначение нумератора копирует все пять его параметров в существующие поля
документа. Изменение одного параметра нумератора переносит только этот параметр
во все объявленные документы, которые на него ссылаются. Для длины самого
нумератора действуют те же пределы 0–50/0–38. Некорректная длина, несовместимое
значение заполнения или запрет записи связанного документа блокируют всю
операцию. Отсутствующие поля не создаются. Все изменения и undo/redo сохраняют
исходное форматирование; связанные файлы публикуются через журнал восстановления.
Назначение и пять видов изменения проверены отдельными сборками CF, явной
загрузкой каждого CF и `CheckConfig` на платформе 8.3.27.2325.

Поддержаны одиночные ссылки на общие формы, язык, стиль, хранилище настроек,
нумератор, справочник, планы счетов/расчёта/видов характеристик, задачу и регистр
сведений; основные формы с доменом конкретного владельца выбираются среди его
форм. В списках основных ролей и ролей ограничения автономной конфигурации можно
заменить существующую строку. Пустой список остаётся для чтения.
Основная и дополнительная формы обработок/отчётов, включая внешние, выбираются
среди собственных форм. «Форма выбора» реквизита выбирается среди форм его
единственного ссылочного типа; для составного/нессылочного типа список пуст.
Правило подтверждено провайдерами EDT и загрузкой XML в платформу 8.3.27.2325.
Минимальное и максимальное значения обычных и стандартных реквизитов доступны
как `schema:{kind:"decimal",nullable:true}`. Пустая строка очищает границу;
число записывается в принятом Designer формате `xs:string`. XML-аннотация
переключается между `xsi:nil` и `xsi:type` только внутри выбранного элемента.

«Значение заполнения» реквизита использует `schema.kind:"value"`: `key` хранит
текущий тип (null — не задано), `types` содержит допустимые expanded QName,
RU/EN подписи и ограничения длины строки, точности/знака числа, частей даты.
Изменение имеет вид `change:{kind:"value",key:{namespace,name},value:"..."}`.
Для очистки передайте `key:null,value:""`; пустая строка с ключом `xs:string`
остаётся отдельным значением. Даты — календарные значения без часового пояса
`YYYY-MM-DDTHH:mm:ss`; проверяются календарь и заданные части даты.
Для ссылочного типа запрос `choices` дополнительно принимает его `key` и
возвращает пустую ссылку, существующие значения перечисления или однозначные
предопределённые элементы. Core повторно проверяет принадлежность выбранного
значения этому типу. Произвольные типы, имена и runtime-данные записать нельзя.

Значение заполнения проверенных стандартных реквизитов использует тот же редактор.
Тип кода/номера и его длина, длина наименования и доступность родителя определяются
по свойствам владельца. Поддержаны код, номер, наименование, даты и проверенные
булевы поля; родитель выбирается из ссылок собственного типа, а его форма выбора —
из форм владельца. Системные реквизиты (ссылка, предопределённость, номер строки)
остаются для чтения. Нулевая длина отключённого поля не разрешает ввод.
Изменение типа кода/номера или отключение иерархии проверяет зависимые стандартные
значения и формы, требуя ручной очистки несовместимого значения.

В существующих строках `ChoiceParameterLinks` доступны имя параметра, источник
и режим изменения связанного значения. Проверяется точная структура `xr:Link`, в том
числе у стандартных реквизитов; число и порядок строк сохраняются.
`DataPath` с `xsi:type="xs:string"` имеет схему
`{kind:"reference",domain:"ChoiceParameterField",nullable:false}`. `choices`
возвращает реквизиты, измерения и ресурсы того же владельца, а для табличной
части — ещё поля её строки. Константы выбираются из других объявленных констант.
Проверенные стандартные поля зависят от свойств владельца и режима совместимости.
У такого варианта `objectId` указывает на реального владельца, дополнительное
`standardAttribute` содержит имя поля. Текущее поле и источники других строк
исключаются. Выбор и запись повторно читают исходники; произвольный текст,
чужой владелец, другая табличная часть и повторный источник не допускаются.
Отключение стандартного поля, используемого существующей связью в этом
дескрипторе, требует сначала изменить связь вручную.

Старый UUID-путь остаётся видимым и допускает замену на известное поле; UUID-пути
не предлагаются для новой записи. В трёх реальных конфигурациях проверены
151 связь у 114 объектов: 113 именованных источников найдены, 38 UUID-путей
не разрешены в объекты. Константы, области табличных частей, устаревшие снимки
и неверные пространства имён покрыты автоматическими тестами. Замены источника
на реквизит и на стандартное поле прошли загрузку CF, `CheckConfig` и обратную
выгрузку 8.3.27.2325; native VSCodium проверил выбор, автосохранение и undo.
Динамические поля субконто, общие реквизиты, источники внешних данных и часть
специальных стандартных полей ещё требуют отдельной проверки и расширения списка.

У `LinkByType` редактируются источник и номер элемента связи. Адрес источника
заканчивается существующим `LinkByType`; схема —
`{kind:"reference",domain:"TypeLinkField",nullable:true}`. Выбор использует ту же
область полей владельца/строки и других констант, исключая самоссылку.
Источник, уже используемый в параметрах выбора, здесь допустим.
Пустое значение очищает одиночную связь; выбор источника в пустом свойстве
записывает пару `xr:DataPath`/`xr:LinkItem` с номером 0. При замене источника
существующий номер сохраняется. Это изменение одной связи, не состава списка.
Номер имеет схему `integer` с границами 0–4294967295; переполнение отклоняется.
Диапазон проверен в 8.3.27.2325: значение 4294967295 сохранилось после
сборки CF, загрузки, `CheckConfig` и обратной выгрузки. Отключение стандартного
поля, используемого связью, требует сначала изменить её вручную.
Поддержаны обычные и стандартные реквизиты; неизвестная структура XML остаётся
для чтения. Пространства имён, комментарии, BOM и окончания строк сохраняются;
изменение номера затрагивает только его текст. Native VSCodium проверил выбор,
отказ при переполнении, очистку и точный undo последовательности изменений.
Аудит трёх конфигураций проверил 2828 свойств: 2803 пустых и 25 заполненных.
Все 22 именованных источника разрешены; три старых UUID-пути доступны для замены.
На копиях двух реальных дескрипторов замена источника и номера дала по одной
текстовой правке; исходные файлы остались неизменными.

В существующих строках `ChoiceParameters` редактируются имя в `app:item/@name`
и значения `app:value`; путь имени заканчивается самим `app:item`.
Имя использует `choiceParameterName`: синтаксис тот же, дубли без учёта регистра
запрещены, но `Отбор` и `Отбор.Владелец` здесь допустимы как разные параметры.
Writer меняет только содержимое атрибута, сохраняя кавычки и соседние байты.

Значения имеют `schema:{kind:"value",domain:"choiceParameter",key,types}`.
В `types` включены строка, число, булево, дата-время и распознанный текущий
ссылочный тип. Полный список объявленных ссылочных типов загружается через
`metadata types` по тому же пути; выбранный `key` передаётся в `metadata choices`
для получения пустой ссылки, значений перечисления или предопределённых данных.
Тип и значение повторно проверяются при записи. Отсутствие `digits` и
`fractionDigits` у числовых ограничений означает отсутствие квалификаторов
разрядности: сохраняется точная десятичная строка в пределах лимита запроса.
Конфигуратор сохраняет здесь числа длиннее 38 цифр; ограничения реквизита
к параметрам выбора не применяются.

В `v8:FixedArray` доступны отдельные существующие `v8:Value`, включая вложенные
массивы. Заменить сам массив скаляром или поменять число/порядок элементов нельзя.
`key:null,value:""` задаёт неопределённое значение, сохраняя элемент.
Старые ссылки через UUID остаются читаемыми и заменяемыми; произвольный UUID
не является допустимым новым значением.
Аудит трёх реальных конфигураций: 93 имени и 119 значений у 77 объектов,
включая 15 массивов. Изменения имени, числа, строки, перечисления и даты прошли
сборку CF, загрузку, `CheckConfig` и обратную выгрузку 8.3.27.2325.

Не поддерживаются добавление/удаление элементов, прямая запись имени объекта,
UUID и других внутренних идентификаторов, языковых кодов, переключение формата
формы/макета. Для имени объекта используется отдельная операция переименования
с preview, описанная ниже. Связанные изменения файлов доступны только для
переименования и проверенных параметров нумерации.
Неизвестные writer mappings, остальные домены ссылок, TypeSet,
редактирование самих предопределённых данных и числовые свойства без проверенного диапазона остаются
для чтения. Наличие свойства в модели EDT само по себе не разрешает запись.

`fields.tsv` и `enums.tsv` в `crates/eska-project-core/src/project/metadata_edit` содержат технические
идентичности модели EDT, не переводы. Основание — те же активные bundles и
SHA-256, что в [каталоге платформы](platform-catalog.md). Профили: 8.3.27 и 8.5.1;
последний выбирается при `build.platform_version = "8.5.1.*"`, иначе используется
базовый каталог 8.3.27. Это не заявляет поддержку всех будущих версий платформы.
Для повторного извлечения `Inspect.java` сообщает changeable/derived/cardinality;
`tools/platform-catalog/editing_schema.py MODEL VALUES OUTPUT` создаёт
детерминированные TSV в выбранном каталоге playground. Специализированные XML
writers адаптируются и проверяются отдельно в `schema.rs` и `types.rs`.

Смена типа или его qualifiers отклоняется, если существующее значение
заполнения либо форма выбора перестанут соответствовать типу. Возвращается
`property_dependency` с `details.property:{namespace,name}` и
`details.reason:"incompatible_type"`. Сначала нужно явно очистить/исправить
зависимое поле. Preview и apply применяют одно правило; автоматического сброса
значений нет.

## Запись и конфликты

Адрес поля: expanded XML name + номер одноимённого ребёнка на каждом уровне.
Mapping проверяется заново в свежем исходнике. Поддерживается только однозначный
скалярный текст; комментарий, разбивающий текст на несколько частей, не имеет
однозначного места изменения. Полный XML не сериализуется. Сохраняются BOM,
CRLF/LF, атрибуты, префиксы, комментарии и все байты вне рассчитанных замен.
No-op не пишет файл и не меняет generation. Смена типа может удалить старую и
добавить новую группу qualifiers; их порядок соответствует Designer XML.

Кандидат повторно разбирается, идентичности объектов сверяются с исходными.
Правила поддержки проверяются на уровне изменяемого объекта, включая mixed XML:
запрещённый соседний объект не редактируется. Symlink-компоненты, неподдержанные
пути, readonly-файл и конфликт SHA-256 отклоняются. Во временный sibling-файл
пишется готовый результат, сохраняются permissions, выполняется sync, затем
повторно проверяются исходные байты/путь/permissions и вызывается `fs::rename`.
Нет delete-then-rename или full-serialize fallback. Очищается только свой temp.

На Linux проверена запись и сохранность байтов; нативная проверка Windows/macOS
ещё не выполнена. `fs::rename` зависит от ОС/файловой системы и возвращает ошибку,
если replacement невозможен. Проверка перед rename не является OS compare-and-swap:
остаётся короткое окно гонки с независимым внешним писателем. Нет гарантии
сохранности после потери питания (каталог отдельно не fsync-ится), сохранения
ACL/xattrs или распределённой транзакции. Эти ограничения не следует скрывать
за словом «атомарно».

История хранит прямые и обратные замены с SHA-256, поэтому undo восстанавливает
даже исходное написание entities. Изменение любого байта файла другим редактором
останавливает replay. Лимиты: 100 шагов/8 MiB на объект, 256 объектов/32 MiB на
session; старые записи вытесняются. Новый backend-процесс начинает пустую историю.

## Проверки

Регрессии покрывают четыре типа проектов, inline-реквизит, preview/no-op,
точный diff и undo, неизвестные/защищённые поля, enum/type validation, stale
snapshot, права и ошибочный путь. Нативный VSCodium 1.109.5 проверяет реальные DOM
события замочка, Enter, Esc, Ctrl+Z/Ctrl+Shift+Z и сохранение черновика при конфликте.
На изолированной копии в playground платформа **8.3.27.2325** через `eska build`
приняла шесть замен типа: string, dateTime, boolean, ValueStorage, UUID,
CatalogRef. Корень реальной бухгалтерии прочитан через CLI без изменения базы.
Для ссылок проверены замена существующей роли, назначение и замена общей формы,
очистка одиночной ссылки: все четыре XML приняты платформой 8.3.27.2325.
Установка и очистка обеих числовых границ также проверены загрузкой платформой.
Это проверка выбранных примеров; domain checks редактора не заменяют полную
проверку конфигурации платформой или выполнение её BSL.

Для значений заполнения платформа 8.3.27.2325 приняла шесть примитивных значений
и четыре ссылочных (пустые ссылки, перечисление, предопределённый элемент).
Для стандартных реквизитов проверены строковый/числовой код, наименование,
пометка удаления и ссылка на родителя. Native VSCodium также проверяет вложенное
значение заполнения наименования: выбор типа, ввод, точный XML diff и отмену.

## Предварительный просмотр переименования

`eska metadata rename-preview rename.json` читает отдельный запрос:

```json
{"schemaVersion":1,"objectId":"catalog:Товары","newName":"Номенклатура"}
```

Ответ содержит `applyAvailable` (нет блокирующих `issues`) и `plan`: исходный/новый ID, UUID, имена,
SHA-256 снимка источников, `files` с заменами и сомнительными вхождениями,
`moves` для descriptor/payload и `issues`. Координаты замен — UTF-8 байты
исходного файла; `before`/`after` содержат исходный и предлагаемый XML-текст.
Снимок учитывает содержимое всех исходных файлов и состав каталогов, включая
добавленные файлы и бинарные payload. Git internals, `.eska` и каталог
результатов сборки исключены; вывод сборки внутри дерева метаданных не скрывается.
Пути относительны source проекта.
Команда не пишет исходники, не создаёт disk cache и не меняет историю отмены.

Подтверждённые XML-ссылки определяются по namespace, типу значения и проверенной
схеме свойства; имена generated types берутся из `InternalInfo` объекта.
Учитываются также конкретные generated types в `xsi:type`, с разрешением
namespace на самом элементе; одноимённые типы чужого namespace не меняются.
Обычный текст попадает в `uncertain` без замены. Backend ESKA самостоятельно
разбирает лексические границы и области видимости BSL. В общих и прикладных
модулях конфигурации подтверждаются прямые обращения к менеджерам и метаданным,
значениям перечислений и неглобальным общим модулям. Признак «Глобальный» и
объявления общего контекста читаются из исходников; локальные параметры,
переменные и методы исключают затенённые обращения. Новое имя общего модуля
также проверяется на затенение в месте обращения.
Строки, комментарии, директивы, динамические выражения, неполные модули и пока
непроверенные контексты форм/объектов остаются в `uncertain` с причиной.
Для расширений/внешних объектов полный глобальный контекст ещё не определяется.
Защищённый глобальный модуль не позволяет подтвердить отсутствие скрытых имён.
Бинарный модуль/форма отмечается `opaque_code_or_form`; недоступная поддержка
и запрет записи видны в `issues`. XML вне ограничений текущего parser отмечен
`xml_unavailable`, XML больше 256 MiB или BSL больше 64 MiB — `text_too_large`;
эти файлы учитываются в снимке без анализа ссылок. XML больше 512 KiB без
объявления переименовываемого объекта разбирается последовательно, с проверкой
всего документа и анализом кандидатов в исходном контексте namespace. В памяти
остаётся текст одного файла; полное дерево его элементов не строится.
Коллизии имён и физических путей проверяются
без учёта регистра. Symlink и неизвестная физическая запись прерывают просмотр.
Правила идентификатора основаны на проверенном EDT `NameValidator`: до 80
UTF-16 единиц, буква/подчёркивание в начале, далее буквы/десятичные цифры/подчёркивание.

Для неглобального общего модуля дополнительно запрещены 92 имени свойств
глобального контекста и их русские варианты. Список проверен импортом в
8.3.27.2325; `GlobalContext.type` профилей EDT 8.3.27 и 8.5.1 содержит одинаковые
100 пар имён. Восемь исключений, принятых платформой отдельным импортом:
`AdvertisingPresentationTools`, `ClientApplicationAgent`, `ExternalSiteWindow`,
`LaunchURL`, `MainInterface`, `OSTaskbar`, `WorkingDate`, `WorkingDateUse`.
Глобальные модули приняты со всеми 100 именами. Поэтому проверка учитывает
`Global` и не позволяет отключить этот флаг у модуля с запрещённым именем
до его переименования. Проверка импорта не заменяет проверку BSL-вызовов.
Исходные пары извлекает `tools/platform-catalog/extract_edt.py` в
`global-properties-<profile>.tsv`; проверенный поднабор хранится в
`crates/eska-project-core/src/project/metadata_rename/reserved_common_modules.tsv`.

Вывод типов переменных, обработка запросов
и подключение поля «Имя» к этому плану пока не реализованы. Предопределённые
элементы и заимствованные объекты расширения пока отклоняются. Этот preview
служит проверке следующего этапа; он не заявляет полноту обновления ссылок.

### Применение и восстановление переименования

`eska metadata rename-apply rename-apply.json` применяет только подтверждённые
замены и перемещения, заново вычисленные backend:

```json
{"schemaVersion":1,"objectId":"catalog:Товары","newName":"Номенклатура","snapshot":"<plan.snapshot>","reviewedUncertain":true}
```

`snapshot` должен совпадать с preview. `reviewedUncertain:true` подтверждает,
что вызывающий просмотрел сомнительные места; они остаются без изменения.
Если таких мест нет, допустимо `false`. Все `issues` блокируют запись.
Клиент не может передавать собственные пути, XML или диапазоны замены.
После подготовки файлов ещё раз проверяется полный снимок источников.
Ответ содержит `applied`, новый `objectId`, исходный `uuid`, изменённые `files`
и `moves`. Поле «Имя» в Explorer ещё не подключено к этой команде.

Перед записью ESKA сохраняет исходные и новые байты в
`<project>/.eska/metadata/rename`. Файлы заменяются с проверкой текущих байтов
и разрешений, затем перемещаются descriptor и payload. BOM, переносы строк,
бинарные файлы и пустые каталоги сохраняются. Обычная ошибка записи вызывает
обратное восстановление; если оно невозможно, журнал остаётся для проверки.
Скалярные правки, undo и rename сериализуются блокировкой
`<project>/.eska/metadata/write.lock`; незавершённый журнал блокирует новые правки.

`eska metadata rename-recovery recovery.json` проверяет журнал:

```json
{"schemaVersion":1,"action":"inspect"}
```

Ответ: `pending`, `snapshot`, `committed`, `restored`, затронутые `files`
и `conflicts`. После просмотра можно восстановить прерванную операцию:

```json
{"schemaVersion":1,"action":"restore","snapshot":"<recovery.snapshot>"}
```

Восстановление проверяет каждый файл и не перезаписывает внешние правки.
Для полностью опубликованной или уже восстановленной операции удаляется
только оставшийся журнал. После `property_recovery_required` следует проверить
этот журнал; повторять исходный `rename-apply` автоматически нельзя.
`rename_committed_refresh_required` означает, что запись завершилась, но сессию
нужно перечитать. `rename_review_required` требует просмотра сомнительных мест;
`rename_blocked` возвращает препятствия в `details.issues`.

Это восстановление после прерывания процесса, а не гарантия транзакции ОС
при отключении питания. Внешние редакторы не используют блокировку ESKA;
гонка между последним сравнением и файловой операцией остаётся возможной.
Журнал и source должны находиться на одной файловой системе для атомарной
замены из staging.

В живой backend-сессии переименование сохраняется в общей последовательности
undo/redo вместе с правками свойств. Возвращаемый `PropertyReplay` содержит
актуальный `object_id` и `refresh`: после отмены/повтора имя и логический ID могут
измениться. Истории потомков переезжают вместе с объектом. Полные XML не хранятся
в памяти истории; действуют общие ограничения 100 операций/8 MiB на объект
и 32 MiB на сессию. Для отмены переименования требуется точное совпадение всего
source с сохранённым снимком. Поздняя правка другого объекта или новый файл
блокируют её до возврата исходного снимка. Одноразовые CLI-процессы историю между
запусками не сохраняют. Подключение этого поведения к полю «Имя» в IDE остаётся
следующим этапом. [IDE API 1.9](ide-protocol.md#api-19-переименование) уже
предоставляет preview/apply и передачу нового ID при undo/redo; включение записи
требует явного opt-in клиента. В Rust `EditingSnapshot.undo/redo` содержат
`Option<HistoryOperation>`: отсутствие шага, скалярная правка или переименование.
