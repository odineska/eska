# Самостоятельный нативный инструмент

`eska-build` собирает CF/CFE/EPF/ERF и распаковывает их в Designer XML.
Сборка из checkout: `cargo build -p eska-build`. В настройках сборки укажите
линейку установленной платформы 1С, например `8.5.4`, или точную версию
`8.5.4.2072`. Для работы достаточно `eska-build` и выбранной платформы.

Для линейки ESKA проверяет `--version` в стандартных каталогах нужных сборок,
начиная со старшей по числовому номеру. При поиске на хосте ESKA отдельно
проверяет `ibcmd` из `PATH`. При равном номере сборки выбирается стандартная установка.
Команда `patch` ищет парный Конфигуратор рядом с этим `ibcmd`.
Если проверка версии одной сборки завершилась с ненулевым кодом или вернула
неверный номер, ESKA пробует следующую. При отказе всех подходящих сборок
команда сообщает ошибку старшей.

Для точной версии на хосте ESKA сначала проверяет `ibcmd` из `PATH`. Если проверка
версии отклонена или номер отличается, ESKA проверяет стандартную установку
с указанным номером. Явный `--ibcmd` закрепляет исполняемый файл.
При одновременной передаче `--ibcmd` и `--distrobox` путь относится к файловой
системе указанного контейнера. Явный `--ibcmd` без `--distrobox` задаёт путь на хосте.
Отмена, таймаут и ошибки запуска прерывают поиск. Команда `platform list`
проверяет все найденные установки выбранного окружения.

```sh
eska-build --project-dir "$PROJECT_ROOT" build --manifest
eska-build --project-dir "$PROJECT_ROOT" build --dry-run --format json
eska-build --project-dir "$PROJECT_ROOT" clean
eska-build --project-dir "$PROJECT_ROOT" patch --dry-run --format json
eska-build unpack "$ARTIFACT" "$NEW_XML_DIRECTORY" --platform-version "$PLATFORM_VERSION" --format json
eska-build platform list --format json
```

Переменные в примере задаёт вызывающая среда. Запуск без подкоманды выполняет
обычный build. `--lang ru|en`, `--project-dir`, `--help`, `--version` доступны
на уровне инструмента. Справка не ищет проект и не запускает платформу.
До выборочной поставки T97 бинарник запускается из локальной сборки.

## Сборка и обслуживание

`build`, `clean`, `platform list`, `config init/edit` перенесены из общего CLI
без второго runner или реализации XML. Сохраняются workspace selectors,
aggregate JSON, `--output`, базовый CF для EPF/ERF, `--recreate-infobase`,
`--dry-run`, `--manifest`, точная версия и разовый выбор платформы.
Параметры `--ibcmd`, `--platform-arch`, `--distrobox`, переменные `ESKA_*`
и machine config имеют прежний приоритет. `config` изменяет только явно
выбранный пользовательский machine config; обычная сборка его не создаёт.

Общий `eska-build-runtime` отвечает за планы, аргументы, host/Distrobox,
изолированные infobases, снимки, публикацию пары artifact/manifest и cleanup.
Терминальные меню и оформление диагностики находятся в общем `eska-terminal`.
Core по-прежнему не зависит от TTY или runtime.

### Ход длительных операций

Во время сборки ESKA показывает подготовку исходников, создание или подготовку
служебной базы, импорт и публикацию артефакта по мере выполнения этих этапов.
У распаковки показывается этап чтения артефакта, у патча — операции подготовки
базы, применения и проверки. При обновлении базы и работе с расширениями
отдельно выводятся сообщения 1С о реструктуризации и наблюдаемой активности.
[Как читать ход обновления](run-debug.md#как-следить-за-реструктуризацией).

При `--format json` итоговый документ читается из stdout. Чтобы получать ход
операции, задайте `ESKA_OPERATION_PROGRESS=1`. Тогда в stderr наряду с
диагностикой поступают однострочные JSON-события с `schema_version: 1` и
`kind: "operation_progress"`. Для интеграций, запускающих распаковку с обычным
текстовым результатом (например, `eska new --from`), `ESKA_OPERATION_PROGRESS=1`
включает те же структурированные события в stderr.

| Поле | Значение |
| --- | --- |
| `event` | `stage` — переход между этапами, `command` — начало конкретной проверки, `native` — распознанное сообщение 1С, `activity` — другой вывод платформы, `heartbeat` — обновление часов, `database_file_changed` — изменение атрибутов файла базы |
| `phase`, `component`, `step` | Этап ESKA, имя компонента приложения и текущая проверочная команда или последний известный этап платформы. Компонент и этап платформы появляются, когда известны |
| `elapsed_ms`, `stage_elapsed_ms` | Время операции и текущего этапа в миллисекундах |
| `quiet_ms`, `native_lines` | Время с последнего наблюдавшегося сообщения и число сообщений на этапе. До первого сообщения `quiet_ms` равно `null` |
| `db_change_age_ms` | Время с последнего обнаруженного изменения файла базы на этапе или `null` |
| `object`, `objects_seen` | Последнее распознанное имя объекта и количество сообщений об объектах на этапе, если они были |

Для клиентов прежних версий при применении и операциях с расширениями также
передаются события `apply_progress` и `extension_progress` при смене их
прежних этапов. Успех операции определяется по коду выхода и итоговому документу.

Паспорт использует прежнюю schema 1 и неизменяемый снимок source.
Самостоятельный инструмент не открывает repository и записывает
`source.git.status = "unavailable"`. Общая команда передаёт путь проверенного VCS-компонента; сборщик получает
его данные через внутренний process-протокол и сохраняет прежние
available/absent/unavailable. Ошибка процесса/протокола останавливает публикацию
паспорта, а не превращается в неизвестное состояние repository.
Значение unavailable не означает доказанное отсутствие Git. Правила проверки
артефактов и source snapshot одинаковы у обоих входов.

`clean` удаляет только управляемую служебную ИБ в выбранной области,
проверяет ownership и сохраняет опубликованные артефакты и паспорта.
На платформе 8.5.4 и новее сборка без основной конфигурации использует
`config import --out` без создания служебной ИБ. Уникальный `--data`
в staging изолирует IPC и временные данные автономного сервера; файл
`1Cv8.1CD` не создаётся. `--recreate-infobase`
относится только к пути с ИБ и не создаёт её для файловой сборки.
Входы с основной конфигурацией (явный CF или XML-библиотека), сборка самой
библиотеки и более ранние платформы сохраняют путь с ИБ. Повторная
совместимая сборка по этому пути переиспользует infobase. Прерванная сборка
сохраняет прежний результат и managed infobase, удаляет свой staging.
[Контракты и OS-матрица сборки](build-validation.md).

## XML-основа для EPF/ERF (T147, T148)

Экспериментальный Rust API `BuildPlan::with_base_configuration` принимает
`Option<BaseConfiguration>`: готовый `Cf(PathBuf)` либо
`DesignerXml { source, library }`. Это заменяет прежний `Option<PathBuf>`;
CLI-параметр `--base-configuration` по-прежнему означает готовый CF.
Обычный `eska-build build` получает XML-основу из `[analysis.configuration]`
(`library` или `source`), а для member — из приложения workspace.
`eska build` использует тот же контракт. Явный CF имеет приоритет;
без ссылки выбирается самостоятельный файловый импорт на поддержанной
платформе, иначе build с пустой ИБ.
Для EPF/ERF с явно разрешённой основой на 8.5.4 и новее сначала вызывается
`ibcmd`. После платформенного отказа сборщик пробует штатную пакетную
команду `LoadExternalDataProcessorOrReportFromFiles` соседнего `1cv8`
из той же установки и через тот же runner. Используется уже подготовленная
ИБ; дополнительное применение конфигурации (`apply`) не требуется.
Отмена и ошибки запуска `ibcmd` не повторяются, 8.3.27 сохраняет прежний путь.
Требуются доступный Designer и штатная клиентская лицензия. На Linux Designer
получает существующие `DISPLAY`/`XAUTHORITY` окружения; в среде без графической
сессии доступный X11 display подготавливает вызывающая сторона.
Сборщик не устанавливает и не запускает Xvfb автоматически.
Проверяются exit status, отдельный `DumpResult` со значением 0 и новый
непустой файл. Ошибка сохраняет предыдущую пару артефакт/паспорт.
[Нативная проверка](build-validation.md#внешние-объекты-с-типами-основной-конфигурации).
[Настройка и выбор приложения](user-guide.md#build).

Runtime копирует исходники XML-основы в собственный staging и подготавливает CF
через `ibcmd`. Исходной выгрузке не нужен `eska.toml`. При прямой ссылке `source`
подготовленные `base.cf` и `base.json` находятся в управляемом каталоге ИБ
конкретного потребителя; одна блокировка защищает весь build. При именованной
ссылке общий результат хранится отдельно: системный пользовательский cache
`eska/libraries`, а для нестандартного глобального `config.toml` — соседний
`cache/libraries`. Исходники установленной БСП остаются в `~/.eska/lib`.

Namespace определяется путём библиотеки, фактической версией платформы, runner,
путём исполняемого файла и контейнером. Общая блокировка сериализует подготовку
и проверку CF, а затем копирование закрытой подготовленной ИБ. Каждый потребитель
открывает только свою изменяемую ИБ; перед импортом EPF/ERF общая блокировка
освобождается. CF и скопированная ИБ проверяются по содержимому. Отсутствующие
или повреждённые производные файлы восстанавливаются; неизвестные каталоги
без маркера ownership не перезаписываются.

Обычный build проекта конфигурации, source которого зарегистрирован в каталоге,
создаёт CF через этот же механизм. Приватные сведения о входных данных сохраняются
автоматически, без `--manifest`. Экспериментальный Rust API добавляет
`BuildPlan::with_library_build(LibrarySelection)` для такого CF-производителя.
Повторный запуск сверяет байты всех исходников и checksum CF; одинаковые размер
и время изменения файла не скрывают изменение. Пересоздание ИБ сохраняет
проверенный общий результат. `clean` удаляет только каталог ИБ потребителя;
при прямой ссылке вместе с ним удаляется его частный CF. Источники основы
остаются только для чтения: размещать выходной файл или staging внутри них нельзя.

Для XML-основы паспорт schema 1 дополнительно содержит
`source.base_context = { kind: "designer-xml", library?, snapshot_id }`.
`source.base_configuration` сохраняет checksum фактически использованного CF.
Машинные пути в паспорт не добавляются. Старые паспорта сборки без XML-основы
и JSON-представление готового CF сохраняют прежнюю форму.

В dry-run XML-основа представлена как `base_configuration` с полями
`kind: "designer-xml"`, `source: {path,path_encoding}`, необязательными
`library` и `configuration: {path,path_encoding}` (глобальный файл),
`steps: ["prepare-base-configuration", "load-base-cf"]`.
Ошибка разрешения имеет `code: "base-reference"`, `stage: "configuration"`
и `data: {file,field,application,cause}`. `file` использует `{value,encoding}`,
`cause` сохраняет структурированные координаты библиотеки. Отсутствующая версия
платформы сохраняет `platform-version-missing`/`plan` и добавляет `data` с файлом,
`field: "build.platform_version"` и `reason: "missing"`. JSON не зависит от locale.
Ошибки общей основы `base-configuration-cache`, `library-cache-unowned`
и `library-configuration` имеют stage `prepare-base-configuration`.

## Patch-extension

`eska-build patch` сохраняет аргументы, ограничения и JSON schema 1 общего
`eska patch`. Для плана нужен `eska-vcs`; build не линкует Git. При реальной
сборке VCS повторно проверяет исходный fingerprint и заполняет новый workspace,
а build выполняет прежние metadata/BSL/applicability проверки и публикацию.
Оболочка, project-сервер и анализатор не требуются. Версия платформы и наличие
`1cv8` остаются ограничениями [patch-контракта](roadmap/t42-patch-extension.md).
`runtime_verified` остаётся false. [Внутренние лимиты и проверки](component-delegation.md).

## Распаковка

На 8.5.4 и новее CF/CFE/EPF/ERF экспортируются через
`config export --file` без временной ИБ, с изолированным `--data` в staging.
Этот общий путь используется также
при `import` и создании проекта из файла. На ранних платформах сохраняется
изолированная ИБ и предварительная загрузка CF. Если прямой экспорт CF
отклонён платформой, runtime пробует прежний путь на том же изолированном
снимке: некоторые корректные CF требуют предварительной загрузки.
При отмене или ошибке запуска повторения нет; если оба способа отклонены,
ошибка содержит обе диагностики платформы. Для CFE/EPF/ERF такого повторения нет.
Снимок входа, staging, проверка идентичности и публикация остаются общими.
Для пустых EPF/ERF восстанавливается пропущенный платформой пустой каталог
`<имя-descriptor>/Ext`, необходимый обратному импорту.

`unpack INPUT DESTINATION` не требует проекта. Относительные пути вычисляются
от `--project-dir` (по умолчанию cwd). DESTINATION должен быть новым каталогом
с существующим родителем. Проверка этого условия выполняется до запуска
платформы; существующий файл или даже пустой каталог не заменяется.
Подтверждение или `--force` здесь не отключают границу нового каталога.

Вход копируется в принадлежащий операции staging. В совместимом пути CF
сначала загружается в отдельную временную ИБ, CFE/EPF/ERF экспортируются
платформой через `--file`.
ESKA проверяет фактические XML identity/type, symlink и состав экспорта.
Перед публикацией `unpack` и `import` повторно сверяют пути и содержимое
файлов со снимком подготовленной выгрузки. При расхождении операция
завершается до создания каталога назначения или замены исходников проекта.
Публикация использует общий core writer с эксклюзивным созданием каталога.
Отмена или ошибка убирают только созданный этой операцией output; ошибка
cleanup сообщает путь сохранённого частичного каталога. Нативный вход
сохраняется. Переименование XML и payload по предположению не выполняется.

В DESTINATION находятся только экспортированные исходники: `eska.toml`
и Git не создаются. Родительский `.eska/import/.gitignore` и управляемое
служебное хранилище переиспользуются. Для подключения экспорта далее
используется `eska-project init`. Для замены существующего source есть
`eska-build import FILE` (общий вход — `eska import FILE`) с VCS preflight и подтверждением.
Обратимая транзакция повторно проверяет исходники и changed paths перед записью.
Для `import` требуется `eska-vcs`; выбор следует общим правилам
[поиска компонентов](component-delegation.md). Флаги `--dry-run`, `--force`,
`-p/--project`, `--format human|json` и platform flags сохранены. JSON schema 1,
exit codes и порядок preview/подтверждения совпадают с общим входом.

JSON schema 1 успеха: `kind: "unpack"`, `status: "unpacked"`,
`destination: {value,encoding}`, `identity: {project_type,name,uuid}` и
`platform_version`. Identity берётся из содержимого, а не имени бинарного файла.
Ошибка: `kind: "unpack"`, `status: "error"`, `error: {code,data}`.
JSON не зависит от locale, объяснения и native stdout/stderr идут на stderr.
Exit 0 — успех, 1 — отказ, 2 — ошибка аргументов, 130 — отмена unpack.
`build` сохраняет прежний exit 1 и код `interrupted` при отмене.

## Нативный стенд

Полный повтор на Linux/POSIX Distrobox, только в новом соседнем playground:

```sh
cargo build -p eska-build --locked
ESKA_TEST_ROOT="$(realpath ../eska-playground)" python3 tests/native_build.py \
  --distrobox "$ESKA_DISTROBOX" --ibcmd "$ESKA_IBCMD" \
  --platform-version "$PLATFORM_VERSION"
```

Путь `--ibcmd` здесь относится к выбранному контейнеру. Значения задаёт
оператор для установленной платформы. Скрипт создаёт собственную маленькую ИБ,
получает XML конфигурации и расширения настоящей платформой, создаёт внешние
контейнеры с новыми UUID и проверяет их той же платформой. Каталог каждого
запуска сохраняется с owner marker, raw stdout/stderr и `result.json`.
Существующие demo и рабочие базы не меняются. Ошибка оставляет complete=false.
Скрипт сейчас требует POSIX/Distrobox; это не проверка Windows/macOS/host runner.

Структура InternalInfo внешних fixtures сопоставлена с
[XML обработки](https://github.com/lintest/TesseractOCR1C/blob/master/Example.xml)
и [описанием генератора отчёта](https://github.com/Nikolay-Shirokov/cc-1c-skills/blob/main/docs/1c-erf-spec.md).
Совместимость конкретных fixtures подтверждается фактическим build/export 1С,
а не только этими описаниями. В product нет генератора XML внешних объектов.

## Проверка T94

Полный workspace fmt/check/strict Clippy/test/Rustdoc прошёл: 805 Rust-тестов
passed, 12 ignored. Прежние CLI-сценарии сохранены; новые process-тесты
проверяют standalone без других ESKA-компонентов в PATH, все типы, обе локали,
help, паспорта, clean и отказ до запуска платформы при существующем output.
Writer отдельно проверен на отмене после первого перемещения файла.

[Нативный отчёт](measurements/t94-native.json): Linux x86_64, Distrobox
`1c-ubuntu-env`, настоящая 8.3.27.2325. Для всех четырёх типов прошли
build с паспортом, повторное использование ИБ, unpack, совпадение исходных
имени/UUID, checksum, стабильность snapshot и clean с сохранением результатов
и исходных байтов. Реальная отмена unpack завершила owned PID и удалила
свой output/staging. Отмена build во время import сохранила прежние CF,
паспорт, source и managed infobase, освободив PID и временный workspace.

Нормальные зависимости build не содержат полной ESKA, project-сервера,
анализатора или `gix`. Project/check проверены без build runtime; TTY project
использует только для интерактивного compatibility-onboarding, check обходится без него.
Windows/macOS, настоящий host runner, runtime/client-функции 1С и нативная
сборка большого `buhmfo` этим результатом не покрываются.

[Делегирование T96 и нативное сравнение](component-delegation.md) проверены
отдельно; T94-отчёт выше сохраняет исходный результат своего этапа.
