# Самостоятельный VCS

`eska-vcs` выполняет существующие Git/workflow-операции над проектом Designer
XML. Сборка из checkout: `cargo build -p eska-vcs`. Полная `eska`, project-сервер,
платформа 1С и bsl-analyzer не нужны. До выборочной поставки T97 используется
локальная сборка.

```sh
eska-vcs --project-dir "$PROJECT_ROOT" status --format json
eska-vcs --project-dir "$PROJECT_ROOT" monitor --format json
eska-vcs --project-dir "$PROJECT_ROOT" diff --semantic --format json
eska-vcs --project-dir "$PROJECT_ROOT" history --limit 10 --format json
eska-vcs --project-dir "$PROJECT_ROOT" start TASK-123
eska-vcs --project-dir "$PROJECT_ROOT" save --dry-run
eska-vcs --project-dir "$PROJECT_ROOT" save -m "Изменено поведение"
eska-vcs --project-dir "$PROJECT_ROOT" switch --base --dry-run --format json
eska-vcs --project-dir "$PROJECT_ROOT" shelves --format json
```

`PROJECT_ROOT` задаёт вызывающая среда. Доступны `clone`, `status`, `diff`,
`history`, `monitor`, `start`, `switch`, `save`, `finish`, `shelve`, `unshelve`, `shelves`.
Без подкоманды выводится ошибка аргументов. Глобальные `--lang ru|en`,
`--project-dir`, `--help`, `--version` не запускают другие ESKA-компоненты.
Аргументы, проектные/workspace selectors, revision/semantic diff и ограничения
операций сохранены из общего CLI. Создание манифеста относится к `eska-project`.

## Общая реализация

Общий CLI и самостоятельный процесс используют те же обработчики, repository,
workflow и XML-модель. `eska-vcs` не содержит runner, native infobase, установщик,
LSP или движок BSL-анализа. Существующий консервативный semantic diff читает
точные HEAD/index/worktree-снимки изменённых путей и сообщает fallbacks;
это не статический анализ проекта. Полный обход BSL для status/diff/save
не добавлен.

Repository discovery, refs, history, ancestry, status и committed snapshots
используют закреплённый `gix`. System Git остаётся capability fallback в одном
infrastructure layer: orchestration index/worktree/switch, hooks/editor/signing,
очистка отслеживаемых путей при сохранении полки и явно неподдержанный
transport. При остальных ошибках `gix` возвращает диагностику. Для разбора
результатов команд используются коды завершения и машинный вывод Git.
Clone/fetch могут требовать транспортные helpers Git. Для read-only
status/diff/history/shelves Git в PATH не нужен.

`eska clone` использует параллельную распаковку pack и checkout из gix. Число
потоков выбирает gix по доступным логическим процессорам и объёму работы.
Для этих стадий действуют настройки Git `pack.threads` и `checkout.workers`.
По умолчанию gix ограничивает checkout на macOS четырьмя рабочими потоками.

`eska clone` и `eska-vcs clone` сохраняют рабочую копию после полного checkout
и возвращают 0. Команда проверяет манифест в корне клона. Для `[workspace]`
она также проверяет перечисленные проекты. При отсутствии манифеста или ошибке
проверки в `stderr` появляется сообщение с префиксом `WARN`.

`status` параллельно обходит рабочее дерево и проверяет отслеживаемые файлы,
а gix читает большие индексы параллельно при наличии их таблицы смещений.

В терминале `clone`, а также сетевые стадии `start` и `finish` показывают
счётчики, объём и скорость через строчный рендерер Gitoxide в `stderr`.
Названия этапов локализованы. При перенаправлении `stderr` команды выводят
обычные диагностики и результат в прежнем формате.

## Сохранность и контракты

Workflow сохраняет существующие preflight и policy. Start отклоняет dirty
repository; finish проверяет интеграцию/публикацию согласно policy, ancestry,
состояние всего worktree и только затем завершает локальную задачу. Команда
не публикует изменения. Switch и полки работают со всем repository, включая
соседние workspace members и файлы вне вложенного проекта.

`start`, `save`, `switch` и `finish` ищут `eska.toml` только в текущем рабочем
дереве Git. Если внутри независимого вложенного репозитория манифест отсутствует,
команды завершаются до изменения файлов, индекса или веток.

Полка сохраняет raw index, отдельные staged/unstaged байты, non-ignored
untracked, удаления и mode. Дерево для защиты staged-объектов строится через
`gix` из сохранённого индекса. Если полка содержит только untracked-файлы,
для сохранения и восстановления Git в PATH не нужен. Dry-run не создаёт полку
и не меняет worktree.
Restore требует совпадения branch/base и отсутствия конфликтов; ошибка
сохраняет единственную копию состояния. BOM/CRLF и произвольные Git path bytes
проходят через прежний контракт. [Подробности workflow и полок](roadmap/05-safe-vcs.md).

В обычном Git-репозитории без манифеста `status --format json` возвращает схему 4
с полями `schema_version`, `repository` и `changes`. Объект `repository` содержит
`root`, `root_encoding`, состояние `head` (`attached`, `detached` или `unborn`),
`branch` и `branch_encoding`. При detached HEAD оба поля ветки равны `null`.
`changes` содержит счётчики для всего рабочего дерева.

Для проекта и workspace `status` использует схему 3. У текущего файлового diff
схема 1, у сравнения ревизий 2, у semantic diff 4, у истории и полок 1.
JSON независим от локали и сохраняет обратимые кодировки путей и Git-строк. Human-вывод и ошибки доступны
на русском и английском; redirect/NO_COLOR подавляет оформление.
Exit 0 — успех, 1 — отказ операции, 2 — ошибка аргументов.

## Время жизни блокировки полок

`Session` явно освобождает OS-lock при завершении операции. Одного закрытия
своего `File` недостаточно: другой descriptor того же open file, в том числе
унаследованный конкурентным fork до exec, может продлить блокировку.
[Контракт std::fs::File](https://doc.rust-lang.org/std/fs/struct.File.html#method.unlock)
предусматривает явный `unlock` для этой границы владельца.
Детерминированная регрессия удерживает дублированный descriptor: до исправления
следующая Session получала `Locked`, после — захватывает lock сразу.
Это исправляет подтверждённый механизм удержания, но без syscall trace не
приписывает ему каждый прежний случай `Shelf(Locked)`.

## Непрерывное наблюдение

`eska-vcs [--project-dir <root>] monitor --format json` и
`eska [--project-dir <root>] monitor --format json` выводят по одному JSON-объекту
на строку (NDJSON). Команда охватывает всё ближайшее рабочее дерево Git, включая
linked worktree и репозитории без `eska.toml`. По умолчанию выводятся корень и
количество изменённых путей.

При сравнении рабочего файла с индексом монитор и `scm-status` учитывают
`core.autocrlf` из конфигурации установки Git, системных и пользовательских
файлов, репозитория и рабочего дерева в порядке приоритета Git. При
`core.autocrlf=input` текстовый файл с CRLF и тем же содержимым в индексе
с LF считается чистым. Атрибут `-text` сохраняет побайтовое сравнение файла.

Команда открывает репозиторий и выводит начальный снимок.
Дальше она публикует снимки при изменении HEAD или набора статусов. Быстрые
промежуточные состояния могут объединяться. Получатель заменяет предыдущий
снимок целиком.

```json
{"schema_version":1,"kind":"snapshot","repository":{"root":"/work/example","root_encoding":"utf-8","head":"attached","branch":"main","branch_encoding":"utf-8","commit":"0123456789012345678901234567890123456789"},"changes":[{"path":"src/Module.bsl","path_encoding":"utf-8","index":null,"worktree":"modified"}]}
```

У `head` три значения `attached`, `detached` и `unborn`. При `unborn` поле
`commit` равно `null`. При `detached` поля `branch` и `branch_encoding` равны
`null`. Строки `changes` отсортированы по исходным байтам пути. `index` описывает
разницу между HEAD и индексом, а `worktree` — между индексом и рабочим деревом.
Допустимые значения полей `null`, `added`, `modified`, `deleted`, `type_changed`,
`untracked`, `intent_to_add` и `conflict`.
Переименования представлены удалением и добавлением. Пути относительны корню
Git. Кодировка `utf-8` сохраняет допустимый текст. Для остальных Git-путей
и строк `percent` кодирует каждый байт как `%XX`. Для корня Windows
`utf-16-percent` кодирует каждую единицу UTF-16 как `%XXXX`.

`gix::Repository::monitor` использует режим `IgnoreAware`. Команда проверяет
наличие файловых событий с интервалом до 40 мс и объединяет события Git
за 45 мс. Для обычных правок status пересчитывается по затронутым путям,
а устаревшие записи внутри этих путей удаляются. При изменениях HEAD, индекса,
конфигурации, правил игнорирования, атрибутов или структуры репозитория выполняется
полный пересчёт. Он также используется при потере файловых событий, сравнении
без учёта регистра и нормализации Unicode. Для пути внутри submodule проверяется
его gitlink. Наблюдение за конфигурацией и атрибутами ограничено файлами,
доступными наблюдателю репозитория.

Если ОС отказывает в подписке при запуске или наблюдатель не восстанавливается
за две секунды, ESKA освобождает его ресурсы и продолжает выдавать изменения
по результатам полного статуса. Пауза между проверками составляет пять секунд
с момента завершения предыдущей проверки. При первом снимке в этом режиме
диагностика о переходе выводится в `stderr`. При кратковременном сбое наблюдатель
повторяет регистрацию с интервалом 100 мс и сверяет статус после восстановления.

Ошибка чтения самого репозитория завершает поток с ненулевым кодом.
В JSON-режиме команда отправляет объект с `kind: "error"`,
`schema_version: 1` и кодом `monitor_failed`, `repository_not_found` или
`invalid_index`. Диагностика выводится на выбранном языке в `stderr`.
В терминале наблюдение завершает Ctrl+C. Индекс и рабочие файлы используются
только для чтения.
На Unix монитор завершается с кодом `0`, когда потребитель закрывает канал или
сокет stdout, даже если состояние репозитория с последнего снимка сохранилось.
Это работает и для дочерних процессов Node.js. На Windows монитор обнаруживает
закрытие stdout при следующей записи снимка. Монитор поддерживает закрытый stdin.

### События от редактора

Параметр `--events-stdin` позволяет использовать файловые события редактора.
Обе команды, `eska monitor` и `eska-vcs monitor`, читают из stdin по одной
записи NDJSON на строку. В этом режиме монитор использует подписки редактора.
Первый снимок охватывает весь репозиторий. После него команда выводит снимок
при изменении HEAD или статуса путей. Состояние репозитория всегда читает gix.

```json
{"schema_version":1,"paths":["Documents/Счёт/Ext/ObjectModule.bsl"]}
{"schema_version":1,"refresh":true}
```

В `paths` передаются пути в UTF-8 относительно корня Git с разделителем `/`.
При переименовании передаются старый и новый пути. Для каталога проверяются
также его потомки. Запись `refresh` запрашивает полную сверку. Такой же пересчёт
вызывают изменения `.git`, `.gitignore`, `.gitattributes` и `.gitmodules`,
неоднозначный путь, неизвестная версия протокола или повреждённая строка.

Предел строки составляет 64 КиБ с учётом перевода строки. Если строка длиннее,
монитор дочитывает её до конца и запускает полную сверку. Очередь вмещает
восемь записей. При заполнении чтение stdin приостанавливается до обработки
следующей записи. Отправитель с переполненной очередью передаёт `refresh`.
При EOF процесс обрабатывает принятые записи и завершается. При ошибке чтения
он выводит диагностику и возвращает ненулевой код.

Примерно раз в секунду монитор проверяет HEAD, время изменения и размер
действующего индекса Git, в том числе во время непрерывного потока событий.
Изменение этих данных запускает полную сверку. Это позволяет увидеть внешние
`git add` и смену ветки, в том числе когда служебный каталог связанного
рабочего дерева находится за пределами открытой папки.

Периодическую полную сверку запрашивает отправитель. Explorer посылает
`refresh` каждые 30 секунд, пока открыта панель изменений. Так в список
попадают и внешние правки, для которых редактор пропустил файловое событие.

### Внутренний адаптер SCM Explorer

Скрытые команды `__bridge scm-*` предназначены для согласованного клиента
Explorer. Они возвращают один JSON-документ
`{schema_version:1, operation, data, error}` и не зависят от языка CLI.
`operation` использует имена `scm_root`, `scm_status`, `scm_blob`, `scm_files`,
`scm_branches`, `scm_checkout`.
При ошибке `data` равен `null`, `error` содержит машинный код, exit code — 1.

- `scm-root` находит ближайший рабочий репозиторий от `--project-dir` и возвращает
  `root`, `root_encoding`, `mutations_available` и `branches_available`. Два
  флага показывают доступность системного Git и вычисляются одной проверкой.
  При `branches_available: true` Explorer может запросить список веток для выбора.
- `scm-branches` возвращает список локальных веток в формате
  `{branches:[{name,name_encoding}]}`. Короткие имена из `refs/heads/`
  отсортированы по исходным байтам. Кодировки `utf-8` и `percent` совпадают
  с кодировками строк монитора. До первого коммита список может быть пустым.
- `scm-checkout -- BRANCH` переключает только существующую локальную ветку
  с коротким именем UTF-8 и возвращает `{}`. Команда работает в обычном
  Git-репозитории, в том числе без `eska.toml`. Git сохраняет совместимые
  локальные изменения и отказывает, если переключение перезаписало бы
  подготовленный, изменённый, неотслеживаемый или игнорируемый файл либо
  если выбранная ветка занята в другом рабочем дереве. Возможные коды ошибки
  включают `branch_invalid`, `branch_not_found`, `git_unavailable`,
  `references` и `checkout_failed`. При отказе Git возвращается `checkout_failed`.
  После переключения клиент запрашивает `scm-status`. Дальнейшие изменения
  HEAD ему передаёт уже работающий монитор.
- `scm-status` возвращает полный снимок schema 1 команды `monitor`. Дополнительный
  массив `conflicts` содержит `path`, `path_encoding` и booleans `base`, `ours`,
  `theirs`: наличие соответствующих стадий индекса. Массив `renames` содержит
  `{stage:"index",from,from_encoding,to,to_encoding}` только для однозначных пар
  удаления/добавления с одинаковым Git object ID. Изменённые и неоднозначные
  перемещения остаются отдельными строками удаления/добавления.
- `scm-blob --revision head|index|base|ours|theirs -- FILE` читает только Git blob
  по пути относительно корня репозитория. `index` — stage 0; остальные стадии
  конфликта выбираются явно. `content` содержит base64 исходных байтов или `null`,
  если версии нет. Ограничение blob — 32 MiB; worktree для чтения версии не нужен.
- `scm-files stage|unstage|discard -- FILE...` изменяет только перечисленные файлы.
  Для больших списков `scm-files ACTION --paths-stdin` читает JSON-массив строк
  из stdin; одновременно передавать пути в argv нельзя. Лимиты — 2048 путей и
  256 KiB входа. `unstage` поддерживает unborn HEAD; для точного staged rename
  оба конца снимаются вместе. `discard` восстанавливает tracked-файл из индекса,
  не меняя индекс; untracked-файл удаляется. Подтверждение удаления и проверка
  несохранённых документов принадлежат UI. Конфликтный `discard` запрещён.

Чтение выполняет `gix`; для точечных изменений индекса и tracked worktree
используется изолированный compatibility fallback системного Git с literal
pathspecs. Каталоги, traversal, `.git`, вложенные репозитории и пути через
symlink-каталоги отвергаются до изменения. Игнорируемые файлы не выбираются
через этот контракт. Внешняя конкурентная правка после проверки не блокируется;
ответ не обещает транзакцию между несколькими файловыми операциями.

Поля `renames` и `conflicts` присутствуют также в каждом JSON-снимке resident
`monitor` и `monitor --events-stdin`, начиная с первого снимка. При отсутствии
таких изменений это пустые массивы. Детали вычисляются по уже полученным
changed paths и требуемым стадиям индекса/HEAD, без второго обхода статуса.
Например, точный staged rename и конфликт представлены так:

```json
{"renames":[{"stage":"index","from":"old.bsl","from_encoding":"utf-8","to":"new.bsl","to_encoding":"utf-8"}],"conflicts":[{"path":"conflict.bsl","path_encoding":"utf-8","base":true,"ours":true,"theirs":true}]}
```

Лимит blob проверяется по заголовку Git-объекта до загрузки содержимого;
каталоги и submodule commit-объекты не читаются как blob. Base64 использует
стандартный алфавит RFC 4648 с padding.

Повторные запросы чтения при неизменном репозитории возвращают тот же снимок.
Повторная мутация не считается безусловно идемпотентной: если выбранный файл
уже не имеет изменений, запрос завершается `stale_status` без записи. UI после
мутации запрашивает новый снимок. Список путей передаётся compatibility fallback
Git также через NUL-delimited stdin, чтобы не зависеть от лимита argv Windows.
