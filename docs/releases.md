# Выпуск ESKA

Версия Rust и компоненты Clippy/rustfmt закреплены в `rust-toolchain.toml`.
Локальная разработка, CI и все задания выпуска используют этот файл через
rustup. При обновлении версии нужно повторить полный набор проверок CI.

Версии всех Cargo packages наследуются из `workspace.package.version`.
Release-plz обновляет их вместе с точными версиями внутренних зависимостей;
номер вручную не повышается. В crates.io публикуются инструменты и библиотеки,
необходимые для сборки этих инструментов. Общие тег `v<version>` и CHANGELOG
принадлежат `eska`; изменения остальных packages включаются в этот CHANGELOG.

После слияния release PR в `main` Release-plz публикует crates и создаёт тег.
Выпуск бинарников запускается через `workflow_dispatch` на этом теге. Перед
публикацией Cargo обязательны fmt, check, strict clippy, тесты workspace,
Python-тесты компонентов и сборка распакованных `.crate` через `cargo package`.
Дополнительно `tools/release_bundle.py verify-crates` проверяет манифесты внутри
архивов: внутренние тестовые зависимости не должны попадать в crates.io.
Для них используется только `path`, без `version` и наследования workspace.
Обычные зависимости сохраняют точную версию из workspace. Одна проверка
`cargo package --workspace` недостаточна: она подставляет ещё не опубликованные
packages из временного локального registry и скрывает ошибки порядка публикации.
Обычный PR проверяет синтетический merge-коммит GitHub полным набором из
`ci-full.yml`. Для PR от Release-plz бот явно запускает CI через
`workflow_dispatch` на ветке PR, поскольку запуск по событию PR от
`GITHUB_TOKEN` может требовать ручного подтверждения. Если запускаются обе
проверки релизного PR, они выполняются последовательно для одного head SHA.

Для автоматического релизного PR, его слияния в `main` и публикации с тега
полный CI базового дерева можно дополнить проверкой финальных метаданных.
Переход от первого родителя допускает только новую версию workspace, точные
внутренние pins и соответствующие записи `Cargo.lock`, а также добавление
раздела в начало CHANGELOG. Остальные файлы и внешние зависимости должны
совпадать. Если для базового дерева есть подтверждённый полный CI, для
финального дерева достаточно `cargo metadata --locked`, упаковки Cargo и
проверки манифестов архивов. Полный CI выполняется при любом другом изменении
или отсутствии подтверждения базового дерева.

Релизный PR, Release-plz и выпуск бинарников сначала ищут успешную полную
проверку или проверку упаковки того же дерева через GitHub Actions API.
Сравнение Git tree позволяет переиспользовать результат после squash merge
и при совпадении деревьев тега и
`main`. Учитываются только запуски из репозитория ESKA с точным путём и
идентификатором workflow, подтверждённым SHA локального `ci-full.yml` либо
`release-package.yml` и успешным заданием последней попытки. Для PR отдельно
подтверждаются merge ref и родители проверенного коммита. Проверка из Release-plz
доступна сборке тега, пока ещё работает публикация Cargo. При отсутствии
подтверждения, недоступности API или истечении бюджета поиска выполняется
полный CI. Матрица сборки и проверка установки бинарников выполняются при
каждом запуске Release.

Если `Publish crate` остановился после публикации части packages, сначала
исправьте причину и слейте исправление в `main`. Затем запустите `Release-plz`
вручную на `main`, указав текущую `workspace.package.version` в поле `version`:

```sh
gh workflow run release-plz.yml --ref main -f version=0.15.0
```

Ручной запуск проверяет совпадение версии, подтверждает или выполняет CI для
текущего дерева и разрешает выпуск без нового release PR только для этого запуска.
Уже опубликованные версии пропускаются. После успеха запускается сборка бинарников по общему тегу,
даже если `eska` был опубликован до сбоя. Версию вручную менять не нужно.
Повтор старого задания не подхватывает исправления из нового коммита.

После сбоя публикации **бинарных файлов** повторите упавшее задание: оно использует
уже собранный `release-assets`. Полный повтор сборки допускается только при совпадении байтов
с файлами, которые уже загружены в GitHub.
Существующий черновик ищется в списке releases с учётом пагинации. При создании
нового черновика используется ID из ответа GitHub: повторного поиска в списке
нет, поскольку новый релиз может появиться там с задержкой. Загрузка файлов
и публикация обращаются к этому ID. До создания проверяется существование тега.

## Файлы поставки

Матрица содержит Linux GNU/musl и macOS на x86-64/ARM64, Windows x86-64.
Перед сборкой runner выполняет `cargo fetch --locked` без ограничения target
и проверяет `cargo metadata --locked --offline`. Упаковщик лицензий читает
метаданные всего workspace; одной загрузки зависимостей текущей платформы
для этого недостаточно. Сама упаковка остаётся полностью offline, а ошибка
Cargo сохраняет исходный stderr в поле `detail`.
Upstream-файлы в `tools/license-overrides` сохраняются побайтно: `.gitattributes`
отключает преобразование концов строк, чтобы checkout Windows не менял SHA-256
из `provenance.json`.
Для x86-64 musl используется стандартный linker Rust: принудительный `musl-gcc`
создаёт неработающий static PIE. `CC_x86_64_unknown_linux_musl=musl-gcc`
сохраняется для C-зависимостей. При отказе запуска контракта упаковщик возвращает
код `probe`, а в `detail` — путь, код завершения и stderr процесса.
Каждый runner исполняет собственные бинарники: проверяет контракты, устанавливает
и повторно устанавливает все семь компонентных ZIP в пустой каталог, проверяет
help на двух языках и initialize/shutdown Metadata API. Это проверка поставки,
не запуск платформы 1С или полной конфигурации `buhmfo`.

`tools/release_bundle.py prepare` создаёт игнорируемый
`target/release-bundle/dist.toml` из текущей версии Cargo. Cargo-dist 0.32.0
собирает полный архив с семью исполняемыми файлами и лицензиями из тех же
бинарников, что вошли в выборочные ZIP. Прежние имена установщиков и receipt
cargo-dist сохраняются. Отдельные архивы имеют имя
`<tool>-<version>-<target>.zip`, индексы — `release-<target>.json`.
Общий `SHA256SUMS` вычисляется после сборки всех установщиков.
В поставку входит также `sha256.sum` от cargo-dist с хешами полных архивов.
Перед запуском установщиков каждый runner проверяет, что скачаны все файлы
из `SHA256SUMS` и их байты совпадают с контрольными суммами.
Манифесты всех runner объединяются до генерации установщиков, чтобы в них вошли
контрольные суммы полных архивов. После сборки выполняются отдельные задания
Linux, Windows и macOS (x86-64/ARM64): чистая и повторная установка семи команд
через shell/PowerShell, отдельная квитанция, запуск Metadata API и переход
от компонентной установки Explorer, включая отдельно установленный `eska-fmt`,
к полному комплекту одной версии.
Каталоги установки и XDG-конфигурации изолированы.

Сборка общего выпуска отклоняет неполную матрицу, несовпадающие версии, SHA-256
или одинаковые имена bootstrap-файлов с разным содержимым. Релиз сначала
создаётся как draft; публичным он становится после загрузки и проверки всех
assets. Повторный запуск сохраняет совпадающие assets, а конфликтующие байты
или неполный уже опубликованный релиз приводят к ошибке без перезаписи.

Полная и выборочная установка остаются разными способами владения файлами.
Установщик компонента не заменяет стороннюю или изменённую установку молча.
Полный shell/PowerShell установщик при каждом запуске заменяет все семь команд
версиями выбранного релиза, в том числе ранее установленные Explorer или
`components.py`. При переходе с компонентов он удерживает общий с Explorer
claim, сохраняет копии прежних бинарников и квитанций, устанавливает полный
комплект и квитанцию cargo-dist. Только после успеха удаляются компонентные
квитанции этих семи команд. Explorer затем распознаёт полную установку;
`eska update` обновляет весь комплект. Внешний анализатор, пользовательские
файлы и прежние лицензии компонентов сохраняются.

Обработанная ошибка замены возвращает прежние бинарники и квитанции. Если
восстановление не удалось, резервные копии и claim остаются, а сообщение
содержит путь `.eska-full-install.*` для ручной проверки. Автоматическое
восстановление после потери питания не предусмотрено. Незавершённая компонентная
транзакция или занятый claim останавливают переход до замены файлов.
Для перехода нужна общая квитанция: режимы `ESKA_DISABLE_UPDATE` и
`ESKA_UNMANAGED_INSTALL` несовместимы с заменой компонентной установки.
Шаблоны cargo-dist закреплены версией; изменение точек подготовки и завершения
перехода останавливает сборку выпуска до изменения установщиков.
Для перехода с монолитной установки через Cargo один раз выполните команду
установки packages из README. Cargo-updater этой версии устанавливает все семь инструментов
с сохранением root/target/profile. Старый Cargo-updater знает только прежний
набор: при переходе с него один раз выполните команду установки полного
комплекта из README или `cargo install --locked eska-debug`. Shell/PowerShell
установщики и «Обновить инструменты ESKA» в Explorer добавляют отладчик
при обновлении прежнего комплекта автоматически.

## Русские описания

`release-plz.toml` задаёт русские заголовки и вводный текст CHANGELOG.
Scope и текст коммита сохраняются: например,
`*(ide)* Добавлено читаемое представление ссылок и типов свойств`.
Описание GitHub Release берёт записи конкретной версии из CHANGELOG и добавляет
русские инструкции установки. Английское автоматически созданное cargo-dist
описание не используется для GitHub Release.

## Штатный выпуск

1. При совместном выпуске готовьте PR ESKA и Explorer параллельно. Сливайте
   обычный PR после успешного CI. Для release PR дождитесь CI, запущенного
   ботом через `workflow_dispatch`. Для отслеживания конкретного запуска
   используйте `gh run watch <run-id> --exit-status`.
2. Слейте проверенный release PR ESKA. Release-plz и Release последовательно
   опубликуют crates и бинарники. Как только ожидаемый тег появится в
   `gh api repos/odineska/eska/releases/latest --jq .tag_name`, сливайте уже
   проверенный release PR Explorer. Его Release берёт backend из этого ответа
   и проверяет установку ESKA и финальный VSIX с настоящим LSP.
3. После успешных заданий публикации подтвердите доступность версий в
   GitHub Releases и новой версии Explorer в Open VSX. Ручное скачивание
   архивов, пересчёт хешей и повторный прогон в VS Code нужны для диагностики
   конкретного сбоя или отдельной приёмки. Штатные задания уже проверяют
   установщики, контрольные суммы и установленный VSIX.

## Диагностика сборки без публикации

Для проверки изменений сборки или упаковки запустите `Release` с `tag=dry-run`
на выбранной ветке. Этот режим выполняет матрицу и сохраняет проверенный
артефакт `release-assets` в GitHub Actions. Тег и публичные пакеты создаются
при штатном выпуске. Локальные проверки используют соседний `eska-playground`.
