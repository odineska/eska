# Контекст приложения Designer XML

Корневой `eska.toml` задаёт состав и настройки анализа один раз. В workspace
участники перечисляются по ролям в `workspace.members.<приложение>`.
Отдельного списка путей `workspace.members = [...]` и секции `applications` нет.
Это схема `designer-xml-4`; старый формат не принимается. Все компоненты ESKA
и Explorer должны поддерживать эту схему.

## Состав workspace

```toml
[workspace.members.accounting]
configuration = "src/main"
extensions = [
    { path = "src/integration" },
    { path = "src/reports", depends_on = ["integration"], scope = "DataSeparation" },
]
external_objects = ["src/data-import", "src/external-report"]

[build]
platform_version = "8.3.27.2325"

[tools.bsl-analyzer.diagnostics.parameters]
LineLength = false
```

`configuration`, `extensions[].path` и `external_objects` содержат **пути к проектам**
от корневого манифеста. Каждый такой каталог содержит собственный `eska.toml`
с уникальным `project.name`, соответствующим `project.type` и своим `source`.
Каталог XML берётся из этого `source`; `/src` автоматически не дописывается.
Локальные участники не могут выходить за корень workspace, включая symlink.

| Поле | Содержимое |
|---|---|
| `configuration` | Один проект типа `configuration` либо ссылка на XML базы для анализа |
| `extensions` | Записи расширений: обязательный `path`, необязательные `scope` и `depends_on` |
| `external_objects` | Пути к проектам типа `processing` или `report` |
| `extensions[].depends_on` | Имена `project.name` расширений, API которых использует это расширение; по умолчанию `[]` |
| `extensions[].scope` | `InfoBase` по умолчанию; `DataSeparation` для установки в области данных |
| `target_platform_version` | Необязательное переопределение версии анализа из трёх или четырёх числовых компонентов |

Основная конфигурация необязательна: workspace может содержать только расширение
или внешние обработки. Без базы контекст имеет `limited_context = true`.
Повторение одного участника внутри приложения, неверная роль, зависимость за
пределами приложения и циклы — ошибки. Разные приложения могут использовать
общий проект; физический участник workspace учитывается один раз.

Источники анализа идут в порядке: основная конфигурация, расширения после их
зависимостей, внешние объекты. Состав независимых приложений не объединяется.

## Область установки расширений

`InfoBase` означает установку для всей информационной базы, `DataSeparation` —
для области данных. ESKA принимает `InfoBase` как значение по умолчанию для
расширений workspace и отдельных проектов. Это правило конфигурации ESKA;
XML и расположение каталогов не определяют фактическую установку.

Путь, область и зависимости задаются **в одной записи расширения**:

```toml
[workspace.members.accounting]
configuration = "src/main"
extensions = [
    { path = "src/integration" },
    { path = "src/client-fixes", scope = "DataSeparation", depends_on = ["integration"] },
]
```

Один проект может иметь разные параметры в разных приложениях. `depends_on`
содержит имена `project.name`, а не пути или имена XML. Дубли зависимостей,
ссылки за пределы выбранного приложения и циклы отклоняются. Внешним отчётам
и обработкам область установки расширения не назначается.
Строковые элементы `extensions` и отдельные таблицы `extension_scopes` /
`extension_dependencies` больше не принимаются; совместимого второго формата нет.

Для отдельного проекта расширения переопределение задаётся так:

```toml
[project]
type = "extension"
source = "src"

[analysis]
extension_scope = "DataSeparation"
```

`analysis.extension_scope` недопустим в корневом workspace и у проектов других
типов. `new/init` добавляют `{ path = "…" }` в выбранное приложение и сохраняют
настройки, зависимости и комментарии существующих расширений. При отсутствии
`scope` новое расширение сразу использует `InfoBase`.

ESKA всегда записывает эффективный `scope` в соответствующее расширение
производного `bsl-analyzer.toml`. Изменение `scope`, пути или зависимостей
меняет fingerprint контекста и пересоздаёт конфиг при следующей подготовке.

## База с БСП в другом каталоге

Для разработки внешней обработки можно подключить существующую XML-выгрузку
базы только для диагностики и навигации:

```toml
[workspace.members.tools]
configuration = { source = "/data/bases/bsp/src" }
external_objects = ["src/my-processing"]

[tools.bsl-analyzer.diagnostics.parameters]
LineLength = false
```

`configuration.source` указывает **непосредственно на Designer XML**, где лежит
`Configuration.xml`. Допустим абсолютный путь или относительный путь от корневого
`eska.toml`, в том числе `../bsp/src`. Манифест ESKA в базе не нужен.
Эта ссылка не становится workspace member, не наследует настройки рабочего
проекта и не становится отдельной целью build или участником VCS. Генерация ничего
не записывает в подключённую базу. Отсутствующая или некорректная выгрузка даёт
ошибку; не происходит перехода к анализу без базы. Ссылка не должна пересекаться
с каталогами рабочих участников.

Для обычного проекта EPF/ERF или расширения:

```toml
[project]
type = "processing"
source = "src"

[analysis.configuration]
source = "../bsp/src"

[build]
platform_version = "8.3.27.2325"
```

Собственная основная конфигурация не может дополнительно подключать другую
основную конфигурацию через `analysis.configuration`.

## Библиотека по имени из глобального каталога

Один и тот же локальный источник можно зарегистрировать один раз в пользовательском
`config.toml` и выбирать в проектах по имени. Каталог находится в стандартной
директории конфигурации ESKA или в `ESKA_CONFIG_DIR`:

```toml
[libraries.ssl_3_1]
source = "/data/bases/bsp/src"
```

Для отдельного отчёта, обработки или расширения:

```toml
[analysis.configuration]
library = "ssl_3_1"
```

Для приложения workspace:

```toml
[workspace.members.tools]
configuration = { library = "ssl_3_1" }
external_objects = ["src/my-processing", "src/my-report"]
```

В одной ссылке допускается ровно один ключ: `source` или `library`.
Пустое имя, пустой путь, оба ключа и пустая таблица отклоняются.
Глобальный относительный `source` разрешается относительно каталога
пользовательского `config.toml`; проектный прямой `source` — относительно
корневого `eska.toml`. Имя выбирает точную запись, без автоматического выбора версии.

Разрешённая библиотека имеет те же ограничения, что прямая XML-ссылка:
она доступна анализу только для чтения, не становится рабочим участником
workspace и не включается в выбор проектов для VCS, fmt или build.
Для EPF/ERF обе формы ссылки также задают вход сборки: обычный `eska build`
подготавливает CF из собственного снимка XML-основы. Библиотека остаётся только
для чтения. При сборке member resolver использует его приложение, а для shared
member требует `analysis.default_application` среди его владельцев.
[Сборка, повторное использование и разовый CF](user-guide.md#build).
Неизвестная библиотека, отсутствующий или некорректный XML и пересечение
с рабочим участником дают ошибку с именем и путём глобального конфига.
Проект без `library` не требует наличия глобального каталога.

CLI и `analyzer/context` возвращают для выбранного источника дополнительный
объект `library = { name, configuration: Path }`. Он содержит имя и путь
к глобальному файлу; машинный путь XML остаётся в обычном поле `source`.
Fingerprint учитывает только выбранную запись, а не весь каталог.
Смена её пути или глобального файла обнаруживается следующей проверкой
`analyzer-config status`; изменение другой корректной записи не меняет fingerprint.
Пользовательская политика анализатора остаётся в проектном `eska.toml`.

Подключение по имени использует уже существующие локальные исходники.
Установка БСП командой `eska add` в `~/.eska/lib/<name>` назначена отдельной
[T148](roadmap/26-analysis-libraries.md#t148--подключение-бсп-командой-eska-add).

## Создание и добавление проектов

Пустой workspace задаётся секцией `[workspace]`. `new` создаёт участника
в `src/<имя>`, `init` подключает существующую выгрузку и сохраняет её исходники.
Обе команды записывают путь в соответствующую роль, не требуя второй настройки
состава для анализатора:

```sh
eska-project new main --type configuration
eska-project new fixes --type extension
eska-project init src/report --name report
```

Первый участник создаёт приложение со своим именем. Расширение или внешний
объект добавляется к единственному приложению. Новая конфигурация занимает
свободное место основной конфигурации единственного приложения; если база уже
задана, создаётся отдельное приложение. При нескольких приложениях расширению
или внешнему объекту требуется `--application`:

```sh
eska-project new integration --type extension --application accounting
eska-project init src/report --name report --application accounting
```

Эти параметры поддерживает и общая команда `eska new/init`.
Ошибочный или неоднозначный выбор не создаёт файлов участника. Существующая
основная конфигурация не заменяется. Команды обновляют `.gitignore` в корне
workspace; отдельные Git-файлы участников не создаются.

## Выбор и настройки анализа

`--application` имеет приоритет над `analysis.default_application`.
Единственное приложение выбирается автоматически; при нескольких задайте
имя явно или default в корневом манифесте. Текущий каталог участника сам по себе
не выбирает приложение. Пустой workspace не даёт успешный пустой анализ.

По умолчанию target равен эффективному `build.platform_version` основной
конфигурации. При ссылочной базе или без базы используется корневой `[build]`.
`workspace.members.<имя>.target_platform_version` изменяет только target
анализа. Для обычного проекта override — `analysis.target_platform_version`.
Режим совместимости берётся из реального XML и не вычисляется из версии сборки.

Политика анализатора хранится только в корневом `tools.bsl-analyzer`.
`eska-project context --format json` показывает разрешённый состав;
`eska-project analyzer-config prepare` проверяет его внешним анализатором и
создаёт [производный конфиг](analyzer-configuration.md). Explorer использует
тот же resolver и обновляет конфиг при изменении входов работающего языкового
сервиса. Вне редактора подготовка запускается командой, отдельного daemon нет.
