# Чтение правил поддержки Designer XML

Rust-модель читает `Ext/ParentConfigurations.bin`, не меняя правила поддержки,
UUID, XML или BSL. Расширение VS Code использует отдельную capability
`supportPolicy`; существующее `capabilities.readOnly` по-прежнему описывает
отсутствие операций записи в IDE API.

## Состояния и принадлежность файлов

Объект сопоставляется с правилами по UUID внутри своего проекта. Состояния:
`locked`, `editableWithSupport`, `unrestricted`, `unknown`. Для unrestricted
сохраняется причина `ownObject` либо `supportRemoved`. Разрешение редактирования
не означает разрешения удаления объекта или изменения правил поддержки.
Для fmt действует дополнительное ограничение: `locked` не форматируется,
`editableWithSupport` допускает только явно выбранный участок без правок снаружи.
Массовый CLI пропускает такие файлы с указанием причины, включая CI/check/diff.
Методы `ИзменениеИКонтроль` сохраняются целиком даже в разрешённых модулях.
Подробный контракт — [форматирование](formatting.md#защита-поддержки-и-методов-изменения-с-контролем).

Парсер поддерживает наблюдавшийся формат 6: UTF-8/BOM, CRLF, кавычки и запятые
в названиях, несколько поставщиков. Проверяются счётчики, UUID, значения правил,
повторы UUID внутри поставщика и завершённость файла. Неизвестные версии и
неподдержанные служебные секции дают диагностику. При нескольких поставщиках
запрет имеет приоритет над редактированием с поддержкой и снятием поддержки.
Общий запрет единственного поставщика учитывается отдельно от объектных правил.
Сочетание нескольких поставщиков с общим запретом хотя бы одного пока
диагностируется как `unsupported_multi_supplier_lock`, без выбора первой записи.

Принадлежность исходников берётся из существующего Designer resolver и XML parser.
Это XML-описания, отдельные модули и поддерживаемые payload-файлы. Расширение
не разбирает `ParentConfigurations.bin` и не блокирует произвольные BSL/OS по расширению.
Если один XML содержит разрешённые и запрещённые объекты, весь файл получает
read-only с причиной совместного хранения. Отдельный разрешённый модуль
этот запрет не наследует.

Отсутствующий UUID в успешно прочитанном файле означает собственный объект.
Для внешних обработок и отчётов (`processing`/`report`, EPF/ERF) правила поддержки
конфигурации не применяются: распознанные исходники получают `unrestricted` /
`ownObject` без `ParentConfigurations.bin`. Принадлежность файла и целостность
дескрипторов всё равно проверяются; повреждение или символьная ссылка не разрешают
редактирование.

Когда проверка подтверждает отсутствие `Ext/ParentConfigurations.bin`,
правила поддержки считаются пустыми. Распознанные исходники конфигураций
и расширений получают `unrestricted` / `ownObject`, в том числе после
смены ветки. Нечитаемый или повреждённый файл правил даёт `unknown` и
ограничение записи. До получения результата Explorer защищает исходник.

## Адресная проверка: IDE API 1.3

С API 1.25 клиент получает статусы видимых объектов через
`metadata/supportObjects`: до 128 ID за запрос, без предварительного получения
путей исходников. Статус вычисляет ESKA по текущим правилам и дескрипторам;
расширение отображает каждый готовый пакет, не ожидая всей раскрытой группы.
Этот ответ не содержит разрешений на файлы и не обновляет настройки защиты IDE.

Клиент с capability `supportFiles` вызывает `metadata/supportFiles` только для
открываемых файлов и дескрипторов видимых объектов. Защита больше не зависит от
построения полного инвентаря. Запрос из 1–128 путей читает правила и цепочки
дескрипторов владельцев; результат не содержит остальные файлы проекта.
XML с запрещённым вложенным объектом закрывается целиком; отдельный разрешённый
модуль не наследует запрет вложенного реквизита. Для `Predefined.xml` учитываются
UUID предопределённых элементов.

В этом методе неизвестное состояние даёт read-only. Подтверждённое отсутствие
файла правил даёт ту же политику, что пустой список поставщиков. Нераспознанные
XML-фрагменты и символьные ссылки остаются защищёнными. Ошибка одного
дескриптора не требует анализа остальных веток.

Разбор зависимостей кешируется по SHA-256 текущего содержимого. В памяти
удерживается до 128 дескрипторов и 8 MiB исходных XML; большие записи не сохраняются.
Дисковый ключ включает содержимое и владельца, поэтому варианты A → B → A
не заменяют единственный общий снимок. Перед использованием кеша читаются
актуальные байты зависимостей. Пропущенное событие Git checkout не позволяет
адресному запросу вернуть старое разрешение только на основании поколения дерева.
Файловый снимок во время внешней одновременной записи не является транзакцией.

Проверено на `big_configuration_temp/src/buhmfo`, release, три новых процесса,
`diskCache:false`: готовность backend и корня — 444–544 мс, первый запрос корня
и одного модуля — 330–336 мс, повторные запросы — 20–36 мс. Ответ — 1 163 байта.
Это запуск без производного кеша, с прогретым файловым кешем ОС. SHA-256 четырёх
использованных исходных файлов до и после совпадают; сборка 1С не выполнялась.
VSCodium 1.109.5 на той же конфигурации: дерево — 435 мс, проверка одного модуля —
672 мс, защищённая вкладка — 954 мс после начала открытия. Получен один файл,
применено одно правило редактора, запросов полного инвентаря нет.
Замеры относятся к Linux; реализация использует общий Rust/VS Code API без
отдельного механизма для ОС. Нативные проверки Windows и macOS ещё не выполнены.

## Постраничная проверка: IDE API 1.2

`initialize` объявляет `capabilities.supportPolicy: true`. Клиенты API 1.0/1.1
продолжают работать; новый клиент проверяет capability перед запросом.

`metadata/support` принимает обычный контекст `sessionId`, `projectId`,
`generation` и необязательный числовой `offset` (изначально 0). Ответ содержит
контекст и eventSequence, а также:

- `objects`: `objectId`, `uuid`, `state`, `reason`;
- `files`: source-relative reversible `path`, связанные `objects`, `readOnly`,
  `reason` (`mixedObjects`, `supportRule`, `unavailable`,
  `noSupportRestriction`), `mixed` и `unknown`;
- `suppliers`: идентификаторы, имя, поставщик, версия и общий запрет;
- `diagnostics`: коды чтения/формата и недоступные logical object IDs;
- `freshness: "current"` — ответ относится к проверенному поколению;
- `nextOffset`: следующий offset или `null`.

Ответ — страница, а не весь проект. Клиент собирает страницы одного поколения;
смена поколения отменяет старую сборку. Первое обращение читает правила поддержки,
затем один запрос обрабатывает не более 32 дескрипторов. Это позволяет другим
запросам IDE выполняться между страницами. Дерево представления остаётся ленивым.

Кеш принадлежит сессии и проекту и разделён на два уровня. Разобранные правила
поставщиков переиспользуются по SHA-256 содержимого `ParentConfigurations.bin`.
Ручной refresh проверяет байты, но не разбирает неизменившийся файл повторно.
Чтение ограничено 64 MiB, включая случай роста файла во время чтения.

Страницы соответствия UUID и физических файлов зависят от поколения XML.
XML, изменения принадлежности исходников и ручной refresh инвалидируют страницы;
уже загруженные для дерева дескрипторы используются повторно. Вложенные объекты
переиспользуют проверенный путь общего XML вместо повторных файловых проверок.

Событие только для побайтно неизменившегося файла правил не меняет поколение
и не отправляет `metadata/changed`. Удаление/восстановление файла обрабатывается
как изменение, даже если восстановились прежние байты. Изменения XML при выгрузке
проверяются независимо: неизменившиеся правила не доказывают неизменность UUID.
Сохранение содержимого существующего BSL сохраняет страницы поддержки;
`metadata/changed.supportUnchanged: true` позволяет клиенту обновить токены
без повторного сканирования. При пропуске событий клиент не доверяет этому флагу.
При `workspace/open.diskCache=true` полный успешный результат сохраняется в
проектном `.eska/cache/metadata` и используется следующими процессами. Explorer
включает этот режим и при обычном запуске, и с `--extensionDevelopmentPath`.
Перед повторным использованием проверяются SHA-256 дескрипторов, предопределённых
данных и правил, а также полный состав файлов/каталогов. Содержимое BSL и XML
форм/макетов в `Ext` не определяет принадлежность UUID и не хешируется; наличие
этих файлов входит в проверку. Изменения только времени записи не сбрасывают кеш.

Части кеша записываются атомарно, манифест публикуется последним, после полного
обхода и повторной сверки исходников. Готовые страницы выдаются укрупнёнными
порциями (целевой размер 4 MiB), без повторного разбора XML и тысяч мелких запросов
из Extension Host. Клиент следует `nextOffset`, как и при обычном анализе.
Незавершённый обход, ошибки чтения/анализа, символьные ссылки и превышение лимитов
(1 млн записей, 1 GiB проверяемого содержимого, 64 MiB одной части кеша) не публикуют результат.
Повреждённый, устаревший или недоступный кеш приводит к обычному анализу.
Формат кеша приватный и версионированный; JSON-протокол не изменён. При отключённом
`diskCache` сохраняется прежняя работа только в памяти. Быстрая проверка актуальности
при запуске остаётся обязательной: неизменность одного файла правил недостаточна.

## Проверка и ограничения приёмки

Небольшие синтетические fixtures проверяют правила, повреждение, смешанный XML,
отдельные модули, разделение проектов и сохранность исходных байтов. Для чтения
реальных выгрузок использованы `temp_configuration` и
`temp_accounting_configuration` из соседнего `eska-playground`.

В отладочной сборке самописная конфигурация: 8 330 объектов, 6 432 файла,
4 998 ограниченных файлов; около 5 секунд, максимальный пакет 356 мс.
Бухгалтерия: 103 417 объектов, 81 350 файлов, 71 180 ограниченных файлов;
89,3 секунды, максимальный пакет 2,77 секунды. Ошибок чтения не получено.
Это исходные измерения backend до добавления разбора предопределённых элементов.
Итоговая проверка большой бухгалтерии в VSCodium 1.109.5: 81 464 файла,
557 групп точных путей в настройках read-only, 76,6 секунды до применения защиты
(отладочный backend), 35 мс на запрос корневых узлов после этого.
Нативный ввод в запрещённый BSL заблокирован. Корневой XML и файл правил
до и после проверки имеют одинаковые SHA-256; несохранённых правок нет.

После добавления прелоадера и повторного использования данных нативный тест с
оптимизированным backend завершился за 22,2 секунды: 81 464 файла, 557 правил;
первые подтверждённые ограничения применены через 0,75 секунды. Дерево показывается
только после полного обхода и применения ограничений. Это время всего тестового
сценария, включая открытие и проверку защищённого модуля, не отдельный замер парсера.

После добавления дискового кеша повторное получение всех статусов в release-сборке
для `big_configuration_temp` занимает 2,54 секунды вместо 11,17 секунды полного
анализа: 138 520 объектов, 94 661 файл, 22 страницы. Это замер протокола без
применения настроек редактора. В нативном тесте отдельной основной конфигурации
дерево готово через 13,83 секунды, из них 10,11 секунды занимает финальное применение
ограничений VSCodium. Автоматическая очистка ограничений при отключении сохранена.

Состояния найденных реальных выгрузок не сверены заново с окном настроек поддержки
Конфигуратора. Синтетические образцы не заменяют такую проверку. Общая приёмка
первого этапа остаётся открытой до этой сверки, включая штатную выгрузку без поддержки.
