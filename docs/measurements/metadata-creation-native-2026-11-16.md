# Нативная проверка создания реквизитов и табличных частей

Дата: 16 ноября 2026 года. Платформа: 1С 8.3.27.2342, Linux ARM64,
ALT 10 в Distrobox, файловые тестовые базы. Проверялись только собственные
синтетические исходники и новые базы в соседнем `eska-playground`.

Проверены минимальный XML-контракт платформы и сквозное создание через CLI
с последующей нативной загрузкой и обратной выгрузкой. Проверка Explorer
в этот отчёт не входит.

## Принятый минимальный XML

Для реквизита достаточно UUID и `Properties` с `Name` и `Type`. Это проверено
у документа, справочника и в их табличных частях: строка 200 символов, число
15/2, дата и время, булево, ссылка на справочник и составной тип
«строка + ссылка». Импорт, применение конфигурации БД и обратная выгрузка
сохранили все UUID и параметры типов.

У табличной части обязательна `InternalInfo` с двумя `xr:GeneratedType`:

```xml
<xr:GeneratedType name="DocumentTabularSection.PostingProbe.Lines" category="TabularSection">
  <xr:TypeId>UUID</xr:TypeId>
  <xr:ValueId>UUID</xr:ValueId>
</xr:GeneratedType>
<xr:GeneratedType name="DocumentTabularSectionRow.PostingProbe.Lines" category="TabularSectionRow">
  <xr:TypeId>UUID</xr:TypeId>
  <xr:ValueId>UUID</xr:ValueId>
</xr:GeneratedType>
```

Пространство имён `xr` — `http://v8.1c.ru/8.3/xcf/readable`.
Для справочника префикс имён типов — `Catalog`; четыре внутренних UUID
сохраняются при обратной выгрузке. Без `InternalInfo` импорт завершился
ошибкой. Для `Properties` достаточно `Name`; стандартный номер строки
не требует создания отдельного дочернего реквизита.

У двух внешних объектов EPF/ERF также прошли сборка и обратная выгрузка
пяти скалярных/составных реквизитов объекта и пяти реквизитов табличной части.
У корневых объектов префиксы типов — `ExternalDataProcessorObject` и
`ExternalReportObject`, а у табличных частей — `DataProcessorTabularSection`,
`DataProcessorTabularSectionRow`, `ReportTabularSection`, `ReportTabularSectionRow`.
При неверном внешнем префиксе табличной части платформа принимает файл, но
переписывает имя типа при выгрузке. Это обнаружено полным сравнением
`GeneratedType` и исправлено в общем генераторе XML. Ссылки на объекты
конфигурации в EPF/ERF в этой проверке не проверялись.

## Значения отсутствующих свойств

| Свойство | Наблюдаемое значение после загрузки и выгрузки |
| --- | --- |
| `TabularSection.FillChecking` | `DontCheck` |
| `TabularSection.LineNumberLength` | `9` |
| `Catalog.TabularSection.Use` | `ForItem` |
| `Attribute.FillChecking` | `DontCheck` |
| `Attribute.Indexing` | `DontIndex` |
| `Attribute.FullTextSearch`, `DataHistory` | `Use` |
| `PasswordMode`, `MarkNegatives`, `MultiLine`, `ExtendedEdit` | `false` |
| `ChoiceFoldersAndItems` | `Items` |
| `QuickChoice`, `CreateOnInput`, `ChoiceHistoryOnInput` | `Auto` |

У реквизита самого справочника дополнительно появляется `Use=ForItem`.
У реквизитов табличной части этого свойства нет. Реквизиты объекта документа
и справочника получают `FillFromFillingValue=false` и `FillValue`;
реквизиты табличной части — нет.

## Ограничения, которые нельзя проверять одним импортом

| Вход | Фактический результат |
| --- | --- |
| Строка переменной длины `0` | Неограниченная строка; import/apply/export успешны |
| Строка переменной длины `1024` | Успешно, длина сохранена |
| Строка переменной длины `1025`, `100000`, `2147483647` | Import успешен, apply завершается ошибкой SDBL о слишком большом описателе длины |
| Строка фиксированной длины `100` | Успешно, длина сохранена |
| Строка фиксированной длины `101`, `1025`, `2147483647` | Import отвергает длину более 100 |
| Строка фиксированной длины `0` | Платформа молча меняет `Fixed` на `Variable` |
| Число `1/0`, `38/38` | Успешно, параметры сохранены |
| Число `0/0` | Успешно, параметры `0/0` сохранены |
| Число `39/0` | Платформа молча меняет разрядность на `38` |
| Число `15/16` | Платформа молча меняет дробную часть на `15` |

В API создания недопустимые для поддержанного сценария значения следует
отвергать до записи. Успешный разбор XML или код завершения импорта не доказывают
возможность применения конфигурации БД и сохранность заданных параметров.

## Имена, порядок и сведения о выгрузке

Платформа отвергает реквизиты со стандартными именами на обоих языках:
`Code`/`Код`, `Description`/`Наименование`, `Date`/`Дата`, `Posted`/`Проведен`,
`ThisObject`/`ЭтотОбъект`, а в табличной части — `LineNumber`/`НомерСтроки`.
При этом `ThisObject`/`ЭтотОбъект` допустимы именно у реквизитов табличной части:
их import → apply → export сохранил без изменений. Запрет зависит от владельца.
Имя существующей табличной части также нельзя использовать для реквизита
того же владельца: пространство имён у них общее.

`Code`/`Код` остаются запрещёнными при `CodeLength=0`,
`Description`/`Наименование` — при `DescriptionLength=0`.
`Parent`/`Родитель` запрещены и у неиерархического справочника,
`Owner`/`Владелец` — при пустом списке владельцев. В этих опытах настройки
ввода по строке и основного представления приведены в соответствие отключённым
полям, поэтому отказ относится к проверяемому имени.

Имена методов и других членов контекста нельзя автоматически приравнивать
к запрещённым стандартным реквизитам. Реквизиты справочника `Write`/`Записать`,
`DataExchange`/`ОбменДанными`, `AdditionalProperties`/`ДополнительныеСвойства`,
`Metadata`/`Метаданные`, `If`/`Если`, реквизиты документа `Write`/`Записать`
и реквизиты строки табличной части `Count`/`Количество` прошли
import → apply → export с сохранением имени и булева типа. Обращение к этим
именам из выполняемого BSL отдельно не проверялось.

Добавление реквизита после существующих табличных частей принято платформой.
Полный и частичный импорт одного изменённого дескриптора справочника успешно
добавили реквизит при неизменённом старом `ConfigDumpInfo.xml`. Файл сведений
о выгрузке не требуется переписывать ради этого изменения.

## Воспроизведение и границы

Коммитируемая синтетическая
[фикстура](../../tests/fixtures/metadata-creation-native/README.md) и игнорируемый
по умолчанию Rust-тесты воспроизводят положительную матрицу документа/справочника,
проверку значений по умолчанию и 60 созданий через настоящий CLI: 44 в конфигурации,
по восемь в EPF и ERF. Проверяются точный `dry-run` → сохранённый план → `--plan`,
переход между `ru-RU`/`en-US`, неизменность прочих исходников, комментарии,
синонимы, UUID, квалификаторы типов и полные описания `GeneratedType` после
нативного цикла. Каталог начинается с пустого самозакрытого `ChildObjects` и
BOM/CRLF, документ — без `ChildObjects`. Результаты дополнительных опытов сохранены
в [машиночитаемом отчёте](metadata-creation-native-2026-11-16.json).

Не проверялись Windows, серверная СУБД, заимствованные объекты расширения,
ссылки на объекты основной конфигурации из EPF/ERF и все возможные классы
метаданных. Реальный запуск созданных реквизитов через UI ещё не является
частью этого исследовательского отчёта.
