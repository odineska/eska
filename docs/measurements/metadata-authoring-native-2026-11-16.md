Дата: 16 ноября 2026 года. Платформа: 1С 8.3.27.2342, Linux ARM64,
ALT 10 в Distrobox. Входной формат — Designer XML. Все изменения выполнялись
публичным CLI ESKA в собственных каталогах соседнего `eska-playground`;

## Методика сравнения

Каждая мутация проходит `--dry-run --format json`, сохранение полного плана,
повторный просмотр сохранённого плана в другой локали и применение `--plan`.
Повторный просмотр должен возвращать те же назначения UUID и тот же JSON.
Исходные объекты не редактируются для получения клона.

Перед импортом сравниваются все принадлежащие объекту файлы побайтно. Разрешены
только новое имя, новые собственные идентификаторы и соответствующие внутренние
ссылки, а также явно переданные уникальные `HTTPService.RootURL` и
`WebService.DescriptorFileName`. Сохраняются BOM, окончания строк, неизвестный XML,
модули и бинарные ресурсы. Отдельные положительные проверки проверяют новые
владельцы в `GeneratedType`, `xr:Field`, типах и типизированных ссылках: обратная
подстановка имени сама по себе не обнаружила бы оставшуюся старую ссылку.

В собственные идентификаторы входят UUID объявлений метаданных, `TypeId` и
`ValueId` их `GeneratedType`, `ThisNode` плана обмена, ID предопределённых элементов
и UUID точек маршрута бизнес-процесса. Константы платформы `ClassId`, внешние
ссылки и локальные ID независимых форм не перенумеровываются глобальной заменой.
Проверяются UUID v4, уникальность внутри клона и между клонами, отсутствие
пересечения с UUID источника. Обратная выгрузка 1С должна сохранять назначенные
собственные идентификаторы.

Нативная цепочка: создать отдельную файловую базу → импортировать XML → применить
конфигурацию БД → сохранить CF → выгрузить XML. После удаления созданных объектов
выполняется повторная цепочка. Регистры, требующие регистратора, подключаются к
отдельному документу, созданному CLI только для теста; существующие документы
исходной конфигурации для этого не изменяются.
Для копии задачи аналогично создаётся отдельный бизнес-процесс со ссылкой на неё:
платформа предоставляет стандартные `BusinessProcess`/`RoutePoint` задачи только
при наличии такого процесса. Эти внешние связи создаются явно через CLI;
копирование не перенастраивает существующие регистраторы и бизнес-процессы.

## Подтверждённые результаты

- Публичная матрица копирования: **45 видов, 260 новых собственных UUID**;
  копирование, нативная загрузка/применение/выгрузка, удаление через CLI и повторная
  нативная проверка прошли успешно.
- Отдельная матрица полных копий наиболее насыщенных реальных объектов:
  **43 вида, 660 файлов, 1529 новых собственных UUID**. Побайтовое сравнение
  с разрешёнными подстановками не обнаружило расхождений. Нативная приёмка
  крупных исходников выполняется отдельно и не заменяется этой проверкой.
- Создание из минимальных шаблонов: **47 видов, 252 новых UUID корневых
  объявлений и GeneratedType**, дополнительно четыре ресурса регистров и
  подписка с конкретным типом документа. Обязательные связи задавались через
  CLI; импорт, применение, CF, обратная выгрузка, удаление всех новых объектов
  и повторная нативная проверка прошли. Отдельный ранний прогон завершился за
  42,10 с; ниже приведён заключительный прогон всего набора.
- Подписки на события проверены с `TypeSet` семейства `CatalogObject` и `Type`
  конкретного `DocumentObject`. Платформа сохранила события в обратном XML.
  Это проверка описания подписки; выполнение пользовательского BSL-обработчика
  в данном сценарии не проверяется.
- Новая конфигурация: `eska new` создаёт каркас, затем `metadata create
  --kind configuration` создаёт XML. Семь UUID `ContainedObject` различны
  и сохраняются платформой. Импорт, применение и обратная выгрузка прошли.

Все пять повторяемых нативных тестов прошли на зафиксированной итоговой
release-сборке с SHA-256
`1cade37c243c904326e07863db1f4ae5632c51a79ece3c0ff8ac6f91a8f3792b`.
Расширенный сценарий формы завершился за 15,74 с; четыре остальных сценария —
blank-матрица, дочерняя матрица, новая конфигурация и публичная матрица
копирования/удаления — за 67,88 с. Это два запуска одного и того же итогового
артефакта после последних исправлений. Каждая нативная цепочка включала CF.

Stalingrad: **35 видов, 348 файлов, 762 новых собственных UUID**; полный сценарий
копирования, побайтового сравнения, нативного `source` roundtrip, удаления через
CLI и повторного `source` roundtrip прошёл за 752,99 с. Ограничение применения
конфигурации к файловой БД приведено отдельно ниже.

Бухмфо: **42 вида, 2384 файла, 2905 новых собственных UUID**; все сложные копии
прошли побайтовое сравнение и нативные import/CF/export в режиме `source`.
Отдельно сверены **172 GeneratedType**: имя, категория, `TypeId` и `ValueId`
совпали с ожидаемыми после переноса владельца. Для задачи создан отдельный
тестовый бизнес-процесс; без этой связи платформа закономерно отвергала её форму,
использующую стандартные `BusinessProcess` и `RoutePoint`.

Для Бухмфо выбрано целевое удаление `WSReference` и крупного составного
`Catalog`. Первое закрывает единственный вид, отсутствующий в публичной
матрице и Stalingrad; второе проверяет удаление тяжёлого дерева вместе с файлами.
Остальные 40 клонов оставлены только в собственном стенде вместе с необходимыми
тестовыми владельцами. Полное удаление всех 42 клонов этой конфигурации
**не заявляется**. Совокупное покрытие удаления по трём источникам — все 47
корневых видов.

После этих двух удалений повторный нативный `source` roundtrip Бухмфо также
прошёл: импорт — 151,393 с, сохранение CF — 41,471 с, обратная выгрузка —
49,485 с. Проверено отсутствие всех принадлежащих удалённым экземплярам файлов
и в исходниках стенда, и в обратной выгрузке.

## Формы

Синтетическая управляемая форма создана через CLI. Проверены числовой реквизит,
`ValueTable` с колонкой, команда и параметр, обычная группа с `United`, поле,
страницы, таблица и привязки `DataPath`, изменение ширины и назначение `OnOpen`.
Затем группа скопирована, перемещена на другую страницу, свойство копии изменено,
параметр и поддерево удалены. Полная копия формы сохранила payload побайтно;
локальные ID двух самостоятельных форм не смешивались.

После нативного импорта, применения и выгрузки проверены структура, привязки,
событие, удалённые узлы и уникальность положительных ID элементов в пределах
одной формы. После удаления обеих форм через CLI повторная нативная проверка
прошла. Эта проверка относится к метаданным формы и не доказывает визуальную
идентичность либо выполнение кода её модуля.

Заключительный сценарий включает таблицу с кнопкой стандартной команды и
отдельную командную панель внутри копируемой группы. В обратной выгрузке
`CommandSource` и `Form.Item.…StandardCommand.Add` указывают на `CopyRows_Copy1`,
а команда внешней таблицы продолжает указывать на `Outside`. Исходная группа
после копирования удаляется без `--force`. Попытки удалить корневой
`AutoCommandBar`, `ContextMenu` и `ExtendedTooltip` через `removeProperty`
возвращают `structural_property` в обеих локалях без изменения файлов;
обычное свойство `Visible` удаляется успешно. Так проверены и перенаправление
команд копии, и запрет обхода структурной проверки ссылок.

Отдельно проверены две реальные сложные формы Stalingrad: общая форма с
4218 XML-узлами и форма справочника с 3021 узлом, глубиной вложенности 17 и 22
соответственно. Форма справочника копировалась внутри нового CLI-клона владельца;
защита исходного каталога не снималась. До смысловых изменений payload обеих
копий был побайтно идентичен исходной форме соответствующего владельца.
Через CLI добавлены реквизит и группа с полем, скопирована группа, выполнены
перемещение, изменение `United`/ширины и удаление исходной добавленной группы
без `--force`. Импорт, CF и обратная выгрузка прошли; итоговые привязки,
свойства и уникальность ID элементов внутри каждой формы подтверждены.

Этот сценарий выявил ложную зависимость: удаление поля ошибочно блокировалось
`DataPath`, ссылавшимся на сохранённый одноимённый реквизит. После разделения
пространств ссылок элементов, реквизитов и команд тот же запрос прошёл без
принудительного удаления. Нативное применение БД для этих форм ограничено
описанной ниже проблемой исходного CF, а не объявляется успешным.

## Дочерние объекты

Отдельная CLI-матрица содержит 18 поддерживаемых дочерних видов и вложенную
подсистему: `Form`, `Template`, `Command`, `Attribute`, `TabularSection`,
`AddressingAttribute`, `Dimension`, `Resource`, `EnumValue`, `AccountingFlag`,
`ExtDimensionAccountingFlag`, `Recalculation`, `Column`, `URLTemplate`, `Method`,
`Operation`, `Parameter`, `IntegrationServiceChannel`, `Subsystem`.
Каждый образец создан и скопирован через CLI; затем 1С успешно выполнила импорт,
применение, сохранение CF и обратную выгрузку.
Повторяемый Rust-тест дополнительно удалил оба экземпляра каждого вида через
CLI и выполнил второй полный нативный roundtrip. На итоговой release-сборке
все 19 сценариев прошли.

Зависимости также задаются через CLI: `BaseCalculationTypes` и режим зависимости
плана видов расчёта для перерасчёта; реквизит документа и `Column.References` для
графы журнала; группа команды, шаблон URL, HTTP-метод и обработчик; имя метода
Web-сервиса. Для копии HTTP-метода явно выбран другой HTTP-метод, для копии
шаблона — другой URL. Это необходимые различия копии, а не тихая правка свойств.

Необходимость этих двух различий проверена отдельно: одинаковый `HTTPMethod`
в одном `URLTemplate` и одинаковый `Template` в одном `HTTPService` отвергнуты
нативным импортом с кодом 255, в том числе для пустых шаблонов без методов.
Одинаковый метод в разных шаблонах и одинаковый URL у разных сервисов приняты
платформой. Значения `/native` и `/NATIVE` в одном сервисе также приняты:
уникальность URL-шаблона чувствительна к регистру. Проверки и discovery
используют непосредственного владельца, а не глобальный реестр.

Нативные значения по умолчанию различают отсутствие свойства и пустую строку:
отсутствующий `HTTPMethod` становится `GET`, отсутствующий `Template` — `/*`,
а явно заданный пустой `Template` сохраняется пустым. Отсутствующий шаблон
конфликтует с явно заданным `/*` у того же сервиса. Эти случаи проверены
независимыми CLI/native-пробами; значения не выведены из догадок по интерфейсу.

После исправления пять отрицательных CLI-проб вернули
`object_property_conflict` без изменения исходников: копия метода, копия
шаблона, отсутствующий шаблон против `/*`, повтор явно пустого шаблона и
отсутствующий метод против `GET`. JSON ошибок совпал в обеих локалях.
Положительный сценарий с явными `POST`/другим URL, разными владельцами,
пустым шаблоном и разным регистром прошёл импорт, применение, CF и выгрузку.
Discovery показывает `HTTPMethod`/`Template` в `uniqueProperties` и допустимые
HTTP-методы в `initialFields`. Копирование между разными владельцами не входит
в текущий контракт; одинаковые значения у разных владельцев проверены отдельным
созданием.

Нативная проверка выявила четыре пропуска минимальных шаблонов/схем:
`Operation.ProcedureName`, `Method.Handler`, `Column.References` обязательны,
а `Parameter` использует `XDTOValueType` вместо `TypeDescription`. Исправления
проверены повторным нативным импортом. При отсутствии `XDTOValueType` платформа
выбирает `xs:string`, `Nillable=false`, `TransferDirection=In`; текущий шаблон
явно задаёт стандартный строковый XDTO-тип. Отдельный отрицательный опыт показал,
что платформа принимает ссылку графы на реквизит документа, который не входит
в `RegisteredDocuments` журнала; дополнительный запрет не введён.

Удаление параметра выявило ещё одну ошибку: одноимённое объявление параметра
в копии другой операции принималось за неизвестную входящую ссылку. Общий
анализ XML теперь различает имена объявлений и ссылки, включая DOM и потоковый
путь. Повторный native-тест прошёл без `--force`.

Проверки имён выявили обход прежнего валидатора в общем конструкторе.
Платформа отвергает `Ref`/«Ссылка» у реквизита документа и `Ref` у табличной
части; `Period`/`Recorder` у полей регистров; `Ref`/`Date` у реквизитов адресации
задачи; `Ref`/`Description` у обычных признаков учёта. Для регистра сведений
запрет сохраняется при `Nonperiodical` и `Independent`: резервируются также
отключённые стандартные поля.

Границы пространств имён проверены отдельно. Реквизит задачи и реквизит адресации
не могут одновременно называться `Shared`; такой же конфликт возникает между
реквизитом плана счетов и обычным признаком учёта. Признак учёта субконто
(`ExtDimensionAccountingFlag`) имеет отдельное пространство: `Ref`,
`Description` и имя, совпадающее с реквизитом либо обычным признаком, приняты
импортом и применением. Команда с именем `Ref` также принята. Общий запрет
стандартных имён не распространяется на эти допустимые случаи.

После объединения проверки имени для создания, копирования и переименования
повторены 35 отрицательных запросов: 11 недопустимых имён в трёх операциях и
две коллизии соседних видов. Каждый проверен в обеих локалях с одинаковым JSON
и побайтно неизменными исходниками. Допустимые признаки учёта субконто,
команда и форма `Ref`, а также обычные новые поля приняты полной нативной
цепочкой с применением БД и CF.

Границы структурного CLI: `PredefinedItem` пока явно не создаётся/не удаляется
этим интерфейсом; `Requisite` не представлен отдельной доступной коллекцией;
таблицы, кубы и функции `ExternalDataSource` не входят в текущий словарь
редактируемых дочерних видов. Их существующие файлы и неизвестный XML
сохраняются при полном копировании владельца. Эти случаи не выдаются за
прошедшие самостоятельное создание.

## Ограничения исходных CF в файловой базе

Применение **неизменённого исходного CF** в новой файловой базе завершается
ошибкой платформы о превышении длины ключа индекса:

```text
_InfoRg3825_1 (_Period, _Fld3826RRef, _Fld3827, _Fld3828, _Fld3829, _Fld3830) UNIQUE
```

Вариант с клонами имеет ту же структуру проблемного индекса с изменённым
порядковым номером таблицы. Исходный бизнес-регистр не изменялся ради прохождения
теста. Для этой конфигурации используется явно обозначенный режим `source`:
импорт XML, сохранение CF и обратная выгрузка без `config apply`.
Успех такой цепочки нельзя трактовать как успешное создание структуры файловой БД.
Локальный лог baseline: `native-stalingrad/apply-original.log` внутри собственного
стенда приёмки; приватный CF и полный журнал в Git не публикуются.

Независимая проверка неизменённого `buhmfo.cf` дала такое же ограничение файловой
СУБД: загрузка CF успешна, `config apply` возвращает код 102 из-за длины ключа
индекса `_InfoRg60459_5@`. В индекс входят `_Fld3337`, `_Fld60464`, две ссылки,
компоненты составного `_Fld60462` и `_Fld60463`. Эта ошибка получена до каких-либо
изменений ESKA. Лог baseline сохранён в `apply-original.log` собственного
каталога `native-buhmfo-baseline-*`. Для копий этой конфигурации также отдельно
проверяется цепочка `source`; исходная схема БД ради теста не меняется.

## Обнаруженные различия платформы

- Для корневых и дочерних типов недостаточно одного UUID объявления:
  `GeneratedType` должен иметь правильное семейство, владельца и собственные
  `TypeId`/`ValueId`. Перерасчёт регистра расчёта хранится отдельным XML,
  а не встроенным объявлением.
- `ChildObjects` нужен у видов, поддерживающих дочерние объявления; добавлять
  его безусловно каждому виду нельзя.
- `Source` подписки должен предшествовать `Event`/`Handler`. При обратном
  порядке платформа теряла событие, хотя оно присутствовало в исходном XML.
- `RootURL` HTTP-сервиса и `DescriptorFileName` Web-сервиса требуют отдельного
  уникального значения. CLI не должен молча менять произвольные свойства копии.
- Минимальная самостоятельная управляемая форма может не иметь `MainAttribute`;
  это не означает, что она автоматически становится основной формой объекта.
- Числовой реквизит управляемой формы с разрядностью `0/0` принимается платформой
  и сохраняется при обратной выгрузке. Это контракт реквизита формы;
  проверка явно заданной разрядности реквизита метаданных остаётся `1..38`.

## Повторение проверок

### Независимое ревью CLI и IDE API

Дополнительно проверены несовпадение команды с операцией сохранённого плана,
несовпадение команды с JSON-запросом, неизвестные поля оболочки и вложенного
ключа типа. Все запросы отвергнуты до записи с одинаковым JSON в `ru-RU` и
`en-US`; смешивание `--object` с `--plan` завершается ошибкой синтаксиса CLI
с кодом 2. Help всех семи команд и human-ошибка коллизии используют обе локали.

Ревью кода подтвердило общие границы: отображаемые пути и содержимое preview
не становятся инструкциями записи; core пересобирает подготовленный запрос
под общей блокировкой и перепроверяет снимки после получения source lease.
IDE API 1.49 отделяет новые методы от старых клиентов, а запрет записи
распространяется на оба новых apply-метода. Они включены в существующее правило
подтверждения мутаций: поздняя отмена не скрывает уже выполненную запись.
Новых дефектов в слое CLI/AI/IDE при этом ревью не обнаружено.

Штатные `cargo fmt --check`, `cargo check` и Clippy для всех targets/features
прошли; полный `cargo test` завершился с 1769 успешными тестами, 0 ошибками и
59 явно пропущенными тестами. Нативные сценарии запускаются отдельно.
После уточнения только входного fixture формы форматирование и Clippy
нативного harness повторно прошли.

### Измеренная стоимость удаления большой конфигурации

Холодные вызовы CLI на выгрузке Бухмфо объёмом 8,12 ГБ:

| Вызов | До устранения повторной проверки в CLI | После исправления CLI |
| --- | ---: | ---: |
| `WSReference` preview | 173,607 с | — |
| `WSReference` saved-plan apply | 365,175 с | — |
| `Catalog` preview | 173,395 с | — |
| `Catalog` saved-plan apply | — | 189,635 с |

Измеренный исправленный артефакт имел SHA-256
`8fc7e7c5b35b14ced66d13e5b088278a8edc2bd2e4dfaa30b5bd441982aecc12`;
последующие исправления валидации отдельно проверены заключительной нативной
пятёркой на сборке, указанной в результатах.

Старый CLI перед применением сохранённого плана повторно выполнял preview,
после чего core снова проверял план под блокировкой. Убран только внешний
дублирующий проход; полная проверка core перед записью сохранена. Новый бинарник
подставлялся между командами, активная операция не прерывалась. Это разные
объекты, поэтому таблица не объявляется точным сравнительным benchmark одного
объекта. Однако сами абсолютные времена показывают существенную стоимость
поиска входящих ссылок даже после устранения повторного прохода.

Каждый из приведённых реальных вызовов завершился успешно и занял меньше
600 секунд. Суммарное время preview и apply нельзя сравнивать с таймаутом
одного запроса. Работа с постоянным backend Explorer здесь не измерялась;
показатели относятся к отдельным процессам CLI.

### Команды

Нативные тесты помечены `#[ignore]`: они требуют установленную лицензированную
платформу и явно выбранный источник. Обычный `cargo test` не обращается к 1С.
В начале сценария выбранный CLI копируется в собственный каталог стенда:
параллельная пересборка проекта не меняет контракт сохранённых планов посреди
проверки. Для больших конфигураций используется штатная release-сборка.
Источник `ESKA_NATIVE_METADATA_SOURCE` должен быть корнем Designer XML с
`Configuration.xml`; все мутации выполняются в новой собственной копии.
Для blank-матрицы источник также должен содержать корректные подписку на событие
и регламентное задание: их ссылки на существующие обработчики используются
как внешние зависимости. Для полного набора, включая дочернюю матрицу,
используйте указанный публичный fixture: дочерние сценарии ожидают наличие
всех своих видов владельцев.

```bash
cargo build --release --bin eska --bin eska-project
export ESKA_TEST_ROOT="$(realpath ../eska-playground)"
export ESKA_NATIVE_IBCMD="$(command -v ibcmd)"
export ESKA_METADATA_CLI="$(realpath target/release/eska-project)"
export ESKA_NATIVE_ESKA="$(realpath target/release/eska)"
export ESKA_NATIVE_METADATA_SOURCE="/path/to/read-only/designer-source"
cargo test --test native_metadata_objects -- --ignored --nocapture --test-threads=1
```

Ограничение набора копируемых типов: `ESKA_NATIVE_METADATA_KINDS` с разделёнными
запятыми CLI-ключами, например `catalog,document,common-module`.
`ESKA_NATIVE_METADATA_MODE=source` меняет только нативную цепочку копирования;
по умолчанию требуется полный режим с `config apply`.
Для Stalingrad и Бухмфо запускайте отдельно
`object_twins_survive_cli_copy_native_roundtrip_and_cli_delete` с этим режимом,
а не весь набор, рассчитанный на полный публичный fixture.

Тесты: `tests/native_metadata_objects.rs` и
`tests/support/native_metadata_objects/{mod,twins,verify,blank,children,forms}.rs`.
Это воспроизводимая приёмка контракта CLI и XML, а не тест бизнес-логики
пользовательской конфигурации, совместимости всех версий платформы или
визуального отображения каждого элемента формы.
