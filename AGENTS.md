# Инструкции для агентов разработки

Эти правила действуют для всех последующих задач в репозитории `eska`. Явное
указание пользователя имеет приоритет; при сомнении сохраняй пользовательские
изменения и не предпринимай рискованных Git-действий.

## Границы задачи и контекст проекта

- Перед значимыми изменениями сверяй фактический код с `README.md`,
  `docs/eska-roadmap.md`, `docs/roadmap/README.md`, относящимся к задаче файлом
  этапа и `docs/roadmap/working-agreement.md`.
- Roadmap задаёт контекст и очередность, но не разрешает реализовывать следующий
  milestone. Делай только явно запрошенный scope; не добавляй соседние команды,
  инфраструктуру или возможности «заодно».
- Сейчас поддерживается только Designer XML. Не добавляй EDT, `1cedtcli`, Java,
  конвертацию или параллельное хранение форматов без отдельной задачи. Не
  блокируй будущие форматы намеренно, но и не создавай абстракции ради них.
- Не меняй без отдельного запроса GitHub Actions, release/changelog automation,
  лицензию, настройки репозитория, branch protection и publication pipeline.
  Версией crate управляет существующая automation; вручную её не повышай.
- Документируй только фактическое поведение. При изменении публичного CLI или
  формата конфигурации обновляй соответствующую документацию в том же логическом
  изменении.
- Для работы с GitHub Issues и Projects соблюдай `docs/task-tracker.md`.
  Задачи и рабочие комментарии формируй на русском языке. Используй метки
  компонентов `cli`, `project`, `check`, `fmt`, `build`, `vcs`, `explorer`, `debug`;
  для общего входа `eska` предназначена метка `cli`. Перенесённые задачи
  ищи по исходному номеру через `docs/roadmap/github-issues.md`; текущие статусы
  веди в GitHub, требования и результаты проверок — в документах roadmap.
  Перенос дополнительных задач выполняй только по отдельному запросу пользователя.

## Ветки и сохранность рабочей копии

- Работай только в ветке, уже выбранной пользователем для задачи. Текущую ветку
  считай выбранной, если пользователь разрешил работать в ней. Не создавай и не
  переключай рабочую ветку вместо пользователя. В `main` файлы не изменяй:
  используй её только для чтения, если пользователь явно не распорядился иначе.
- До работы проверь ветку и `git status`. Все исходные незакоммиченные изменения
  считай пользовательскими: не удаляй, не перезаписывай, не форматируй без
  необходимости, не stash'ь и не включай в свои commits. Если безопасно отделить
  работу нельзя, остановись и объясни причину.
- Не переписывай историю. Без прямой команды пользователя не выполняй
  `git merge`, `git rebase`, `git reset`, `git cherry-pick`, `git revert`,
  `git branch -D`, `git push --force` и `git commit --amend`. Отдельную ошибку,
  найденную после commit, исправляй новым логическим commit.
- Не выполняй `git push` без отдельного явного запроса.

## Commits и changelog

- Планируй логические части значительной задачи до реализации и фиксируй каждую
  законченную часть отдельно. Один commit — одна законченная причина изменения;
  по возможности каждый commit оставляет проект собираемым и проверяемым.
- Не складывай несколько независимых пользовательски заметных возможностей в
  один финальный commit. Не дроби на commits отдельные строки, импорты,
  форматирование или мелкие исправления той же логической части.
- История Git служит источником автоматического changelog, поэтому сообщения
  должны точно описывать пользовательски значимые изменения.
- Используй Conventional Commits: `feat`, `fix`, `refactor`, `perf`, `test`,
  `docs`, `build`, `ci`, `chore`, `style`; при необходимости добавляй английский
  scope. Type и scope — на английском, заголовок и тело — на русском:
  `feat(project): Добавлен поиск корня проекта`.
- Заголовок должен быть конкретным и соответствовать diff. При необходимости
  русское тело объясняет что и почему изменено, архитектурные решения и важные
  ограничения, но не пересказывает каждый файл.
- Перед каждым commit проверь `git status`, `git diff` и `git diff --staged`.
  Не включай временные файлы, artifacts, editor files, unrelated или исходные
  пользовательские изменения. После законченной части выполни релевантные
  проверки, проверь staged diff и только затем создавай commit.

## Архитектура и качество Rust

- Пиши idiomatic Rust: понятные типы, небольшие функции, явные invariants и
  compile-time guarantees. Предпочитай ownership лишнему cloning и стандартную
  библиотеку новой dependency, пока решение остаётся простым.
- Идентификаторы и технические Rust doc comments пиши на английском. Комментарии
  должны объяснять причины, invariants и нетривиальные ограничения, а не
  повторять код.
- В production-коде избегай `unwrap()`, необоснованных `expect()`, `panic!()` для
  штатных ошибок, global mutable state, `unsafe`, чрезмерных generics и
  преждевременной оптимизации. Не подавляй lint через `#[allow(...)]`, если
  проблему разумно исправить.
- Core не зависит от `clap`, TTY и локализованных строк. CLI отвечает за parsing,
  presentation, exit codes, prompts и human/JSON output. Доменные ошибки должны
  быть структурированы, а их human-представление локализуется в presentation
  layer. Machine-readable output и его схема не зависят от locale.
- Не добавляй traits, generic abstraction, plugins, caches или crates без
  реального текущего потребителя. Перед новой dependency проверь стандартную
  библиотеку и текущие зависимости, поддержку crate, стабильную версию и
  минимальные features; удаляй ставшие ненужными зависимости.
- До стабильного публичного API не создавай compatibility layers для
  экспериментального недокументированного API. Изменение такого API отмечай в
  итоговом отчёте; документированные config schemas и JSON protocols считай
  публичными контрактами.

## Локализация

- Поддерживаемые локали: `ru-RU` и `en-US`. Любую новую human-readable строку
  (help, description, error, warning, progress, prompt, status) добавляй сразу в
  обе локали и проверяй совпадение ключей.
- Не локализуй command/option names, config и JSON keys, enum serialization,
  error codes и внутренние идентификаторы.

## VCS, безопасность и производительность продукта

- Для VCS используй `gix` как встроенную библиотеку; system Git допустим как
  compatibility fallback только через изолированный infrastructure layer. Не
  размазывай `Command::new("git")` по бизнес-логике и не разбирай локализованный
  human output Git.
- Высокоуровневый UX выражает намерение (`start`, `status`, `diff`, `save`,
  `sync`, `publish`, `finish`), а не копирует Git CLI.
- Потенциально разрушающие операции требуют preflight, понятного preview и
  явного `--force`, если безопасного пути нет. Не используй `reset --hard` как
  универсальное решение.
- Для больших конфигураций сначала учитывай changed paths и инкрементальную
  обработку, избегай ненужного полного обхода и subprocess. Сначала обеспечь
  корректность, затем измеряй; cache/index добавляй только по подтверждённой
  необходимости.

## Проверки и завершение задачи

* Playground проекта находится рядом с репозиторием `eska`, в той же родительской
  директории, под именем `eska-playground`.
* Не использовать жестко заданные абсолютные пути. Путь к playground всегда
  определять относительно корня репозитория `eska`:
  `<корень репозитория eska>/../eska-playground`
  Перед использованием при необходимости преобразовать его в абсолютный путь
  средствами текущей ОС.
* Ручные проверки CLI (`new`, `init` и остальных команд) выполнять только внутри
  `eska-playground`, в отдельных demo-каталогах.
* Не создавать тестовые проекты внутри репозитория `eska`.
* Существующие demo пользователя не изменять без явного запроса.
* Для автоматических CLI-тестов задавать `ESKA_TEST_ROOT` равным абсолютному пути
  к соседнему каталогу `eska-playground`.
* Автоматические тесты должны создавать и удалять только собственные уникальные
  подкаталоги внутри `ESKA_TEST_ROOT`.
* Если sandbox требует отдельного разрешения на запись в `eska-playground`,
  запрашивать это разрешение, а не переносить проверки в другую директорию.
- Добавляй соразмерные unit- и integration-тесты. Для CLI проверяй exit code,
  stdout/stderr и оба языка; для JSON — стабильность схемы и независимость от
  locale; Git-сценарии при необходимости проверяй на небольших временных
  repositories.
- Для изменений только CI/CD (workflows и служебные скрипты CI/release), если
  код приложения и зависимости не менялись, не запускай полный набор
  Rust-проверок. Выполняй только проверки затронутых сценариев: валидацию
  workflows, тесты изменённых скриптов, проверки упаковки, публикации или
  установщиков. При изменении параметров сборки в workflow проверяй затронутые
  сборки и запуск полученных бинарников.
- Перед завершением задачи, которая меняет код приложения, зависимости или
  конфигурацию сборки самого приложения, обязательно выполни полный набор:

  ```text
  cargo fmt --check
  cargo check
  cargo clippy --all-targets --all-features -- -D warnings
  ESKA_TEST_ROOT="$(realpath ../eska-playground)" cargo test
  ```

  Для промежуточного commit допустимы более узкие релевантные проверки, но не
  вместо полного финального набора.
- Для изменений только документации и других изменений, которые не влияют на
  поведение приложения, не запускай `cargo fmt`, `cargo check`, `cargo clippy` и
  `cargo test`. Выполняй только релевантные проверки изменённых файлов: например,
  `git diff --check`, проверку ссылок, структуры или формата документа.
- В итоговом отчёте кратко укажи: что реализовано; ключевые архитектурные
  решения; созданные commits (`<hash> <message>`); выполненные проверки и их
  результат; известные ограничения; оставшиеся незакоммиченные изменения и их
  владельца.

## Приоритет решений

При конфликте или сомнении соблюдай порядок:

```text
сохранность пользовательских изменений
> явное указание пользователя
> корректность
> спецификация проекта
> чистота архитектуры
> производительность
> удобство реализации
```
